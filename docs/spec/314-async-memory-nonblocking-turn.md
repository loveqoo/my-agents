# 314 — 자동 기억 저장 비차단화 + 완료 트레일링 이벤트

## 배경 / 증상

플레이그라운드에서 "**답변 텍스트는 다 나왔는데 그 뒤로 한참 '처리 중'이 지속**"되고, 인스펙터가 그
뒤에야 채워진다(사용자 보고). 인스펙터가 느린 게 아니라, **턴 종료(`done`)가 늦게 뜨는 것**이다.

## 진단 (측정 + 코드)

턴 종료 프레임 순서(`_final_frames`):
`trace 조립 → persist(DB) → mid 프레임 → memory.add(자동 기억 저장) → trace 이벤트 → done`.

- 측정(ASGI in-process, 프레임 도착 시각): 세션 메모리 에이전트는 `마지막토큰→trace/done` 간격이
  **0ms**, trace **~1.2KB**. 즉 trace 조립·전달은 병목이 아니다.
- 유일하게 시간을 먹는 동기 작업은 **`memory.add`(장기 메모리)** — mem0의 **실제 LLM 추출 호출**이라
  실모델이면 초 단위. mock 추출(personal-secretary)은 0ms라 빨랐다.
- 이 `memory.add`가 **`done` 앞을 막아** 답변 후 "처리 중"이 몇 초 이어진다. 인스펙터 데이터(trace)는
  그 뒤라 "인스펙터가 늦다"로 체감됐다.
- 참고: 외부 배포(A2A) 경로는 이미 trace를 안 만든다. 무거운 trace/자동저장은 **플레이그라운드
  `chat()` 경로 한정**이다.

## 설계

**핵심: `memory.add`를 `done` 뒤 백그라운드로 빼고, 완료를 트레일링 이벤트로 알린다. 폴링 미채택
(스트림이 이미 열려 있어 한 프레임만 더 보내면 됨 · 새 엔드포인트/주기 부하 불필요).**

### 순서 변경
```
답변 텍스트 → trace 이벤트 → done   (여기서 프런트 '처리 중' 즉시 해제 = 증상 해결)
            → [백그라운드] memory.add 실행
            → 완료 시 event: memory (저장된 기억 요약, mid 포함) → 스트림 닫힘
```

### 견고성 (전체 정합 — 끊겨도 안전)
1. **detached + shield 태스크**: `memory.add`를 요청 태스크의 자식이 아닌 분리 태스크로 실행하고
   모듈 레벨 집합으로 참조 유지(GC/취소 방지)+에러 로깅. 클라이언트가 중간에 떠나도 **저장은 완료**.
   트레일링 이벤트만 전달 안 될 뿐.
2. **완료 시 영속 trace 갱신**: 저장 결과를 그 assistant 메시지의 trace JSON(DB)에도 병합. 라이브
   이벤트를 놓쳐도 **새로고침하면 인스펙터가 다시 불러옴**(폴링의 "나중에 조회" 이점 흡수).

### 트레일링 이벤트가 늦고 사용자가 딴 화면일 때 — 조용히 무시 (사용자 요건)
- `event: memory`는 **mid(메시지 id)를 싣는다**. 프런트 패치 규칙: "현재 화면 메시지 목록에 그 mid가
  있으면 조용히 trace.memorySaved 패치, 없으면 no-op". 세션 전환·다른 메뉴면 목록에 없어 **자동 무시**.
- **토스트·포커스 이동·스크롤·에러 없음** — 순수 in-place 데이터 패치만.
- 컴포넌트 언마운트 시 스트림 리더 abort → **언마운트 후 setState 없음**(React 경고 방지). 백엔드
  detached 태스크는 그대로 완료.

### 프런트
- `done` = 턴 완료(스피너 해제). 그 후 스트림이 닫힐 때까지 계속 읽어, `event: memory`가 오면 위
  규칙대로 조용히 패치.
- 인스펙터에 **"자동 저장된 기억"** 섹션 신설 — 지금은 회상(recall)만 보이고 저장(add)은 안 보인다.
  저장 결과(요약·건수)를 노출해 관측성 향상(스펙 079 "행위를 계측한다"와 정합).

### 진행 중(pending) 상태 표시 (사용자 요건)
백엔드가 이 턴에 백그라운드 저장 태스크를 띄웠으면 **done 전 trace에 `memoryPending: true`**를 싣는다
(장기 메모리 미사용 턴은 이 플래그 없음 → 로딩 표시도 없음). 트레일링 `event: memory`가 오면
`memorySaved` 결과로 바뀌고 pending 해제.

1. **인스펙터 메모리 섹션**:
   - `memoryPending && !memorySaved` → antd `Spin`(빙글빙글) + "작업 중" 표시. **호버 시 `Tooltip`**으로
     안내("기억을 저장하는 중입니다 — 완료되면 자동으로 반영됩니다").
   - `memorySaved` → "자동 저장된 기억" 결과(요약·건수).
   - 둘 다 없음 → 기존(회상만/없음).
2. **채팅 턴의 인스펙터 링크/버튼**: 그 턴이 `memoryPending && !memorySaved`면 링크 뒤에 **로딩
   스피너**(antd `Spin` 소형/`Badge status="processing"`) — 이 턴에 아직 끝나지 않은 백그라운드 작업이
   있음을 알림. 완료 이벤트를 받으면 조용히 사라짐.
3. 완료 이벤트 수신 시 위 두 곳 모두 **조용히** pending→saved 전환(토스트·포커스 이동 없음). 딴 화면
   (mid 부재)이면 no-op.

### 받아들이는 트레이드오프
- 저장이 백그라운드라, 답변 직후 **아주 빠르게** 다음 턴을 보내면 방금 턴이 아직 기억에 안 들어가
  회상에 안 잡힐 수 있다. mem0 회상은 원래 퍼지하고 개인 도구라, 스냅한 완료감이 이 미세 일관성보다
  낫다고 판단(명시).

## 범위 밖 (OUT)
- **폴링 방식**: 미채택(위 근거). 필요 시 영속 trace 갱신 + 새로고침으로 대체됨.
- **배포 시 인스펙터 제거 옵션**: 지금은 가치 낮음(trace 이미 0ms/1KB · A2A 서빙은 이미 trace 없음).
  `chat()`을 사용자에게 직접 여는 미래에만 opt-in 플래그로. 지금 미착수.
- 트레이스 자체의 async 전달(trace는 가벼워 done 전 동기 전달 유지 — 지연 원인 아님).

## 검증 (사다리)
- **실측(핵심)**: 장기 메모리 에이전트로 고침 전/후 `마지막토큰→done` 간격 — 초 단위 → ~0ms 수치화.
- **기능 왕복**: 트레일링 `event: memory` 도착 → 인스펙터 "자동 저장된 기억" 반영 · 저장된 기억이
  실제 DB(mem0)에 존재 · 영속 trace에도 병합(새로고침 재현).
- **pending UI**: 저장 완료 전 인스펙터 열면 메모리 섹션 `Spin`+호버 툴팁, 채팅 인스펙터 링크에 로딩
  스피너 · 완료 이벤트 후 조용히 saved로 전환(스피너 사라짐).
- **조용히 무시**: 이벤트 도착 전 세션 전환/언마운트 → 에러·토스트 0, 저장은 여전히 완료(detached),
  새로고침 시 결과 노출.
- **적대(codex)**: 태스크 수명(끊김 durability)·비밀 마스킹(저장 기억 요약에 비밀 누출 0, `_sanitize`
  재사용)·영속 trace 갱신이 올바른 mid만 타깃(동시 편집 클로버 방지)·다음 턴 회상 경합 경계.

## codex 적대 검증 → 수정 (P0 1 + P1 3 + P2 2)
- **P0 저장 유실**: 저장 태스크를 `yield done` **뒤**에 만들면, done 직후 클라이언트가 끊어(제너레이터
  취소) yield 이후가 재개되지 않아 태스크 자체가 안 생겨 저장 유실. → **태스크를 `yield done` 앞에서
  생성·등록**(detached, 강참조). verify_314 ⑥가 aclose(이탈)로 재현·회귀.
- **P1 무한/장기 대기**: `await shield(task)`에 상한 없음 → mem0 hang 시 연결 무한 보유. → `wait_for`로
  트레일링 이벤트 대기 상한(_TRAILING_EVENT_TIMEOUT_S=60s, 초과 시 이벤트만 생략·태스크는 계속).
- **P1 stuck pending**: memoryPending을 영속하면 완료 못 할 때 새로고침 스피너가 영영 돎. → **pending을
  영속 trace에 넣지 않고 라이브 스트림에만** 싣는다(영속엔 memorySaved만 최종 병합). + `_bg_memory_add`
  내부 `wait_for(_MEMORY_ADD_TIMEOUT_S=30s)`로 hang 시에도 error 요약으로 마감(pending 해제 보장).
- **P1 mid=None**: persistHistory=false면 mid 없어 완료 이벤트로 pending 해제 불가. → **mid 있을 때만
  라이브 memoryPending 표식**(없으면 스피너 자체를 안 켠다).
- **P2 event 비마스킹**: memorySaved의 event 값 무마스킹. → `_sanitize` 적용(custom 백엔드 누출 차단).
- **P2 mid 클로버**: _finalize가 role 미확인. → **`role=='assistant'` 가드**(남의/다른 메시지 갱신 방지).

### 남은 경계(OUT)
- 서버 크래시가 persist(응답 저장)와 백그라운드 finalize **사이**에 나면 그 턴은 memorySaved가 안 남음
  (저장 자체는 mem0에 됐을 수 있음). 단일 워커·개인 도구 경계(스펙 312 stale 회수와 동류). 라이브
  pending은 미영속이라 스피너 잔존은 없음.
- mem0가 _MEMORY_ADD_TIMEOUT_S 넘겨 hang하면 `to_thread` 스레드가 유실(고아). 드묾·바운드(타임아웃 후
  pending은 해제됨). 근본 해결은 mem0 호출 자체의 취소 가능화(빚).

## 완료 조건
- 답변 후 `done`이 즉시(장기 메모리 유무와 무관), "처리 중" 지속 없음.
- 기억은 백그라운드에서 저장되고, 완료 시 인스펙터에 조용히 반영(딴 화면이면 무시).
- 새로고침해도 저장 결과가 인스펙터에 남음(영속). 비밀 누출 0. ruff/mypy/tsc/vite 클린.
- done 직후 끊겨도 저장·영속 완료(P0 회귀). codex P0/P1/P2 전부 봉인 또는 경계 문서화.
