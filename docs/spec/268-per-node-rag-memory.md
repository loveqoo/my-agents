# 268 — 노드별 RAG(컬렉션)·메모리 설계 초안 (검토 대기)

> 상태: **초안(사용자 검토 대기)** — 2026-07-09 사용자 요청 "RAG, Memory를 각 노드마다 설정할 수
> 있도록 고민이 필요합니다"에 대한 설계 제안. 승인 후 구현.

## 현재 상태 (제약의 뿌리)
- **RAG**: 플랫폼이 배선된 컬렉션 *전체*를 하나의 `search_documents` 도구로 묶어 빌드(runtime.
  build_rag_tool) → 노드는 이 단일 도구를 켜고 끌 수만 있음. 컬렉션 구분 불가.
- **메모리**: 회상(mem0 검색)은 플랫폼이 턴 시작에 1회 수행해 **에이전트 페르소나에 합침** → 노드형은
  노드가 각자 프롬프트를 쓰므로 이 경로를 안 타 회상이 노드에 닿지 않음(259 정직 기록).

## 제안

### P1 — 노드별 RAG: 컬렉션별 검색 도구로 쪼갠다
- 플랫폼(chat.py)이 노드형 에이전트에 한해 **컬렉션마다 검색 도구 1개**를 빌드: 이름
  `search_documents__<컬렉션>`(_safe_name 규칙 재사용 — 265 이름 체계 그대로).
- UI 노드 도구 선택지: "문서 검색 (컬렉션 전체)" 대신 **"문서 검색 · docs-kb"** 처럼 컬렉션별 항목.
- 풀 파생: vectorTables = 노드들이 참조한 컬렉션 합집합(기존 파생 로직 확장).
- 하위호환: 구저장 `search_documents`(민이름)는 기존 전체-컬렉션 도구로 계속 해석(무회귀). 엔진은
  이름 필터 그대로라 **무변경** — 변경은 플랫폼 도구 빌드 + UI 옵션 두 곳.
- 효과: "검색 노드는 A컬렉션만, 검증 노드는 B컬렉션만" 가능. ragMinScores도 컬렉션별이라 자연 정합.

### P2 — 노드별 메모리: 회상 주입을 노드 단위로
- 노드에 `memories: string[]`(기존 기억 블록 목록에서 선택, 직접형 "기억" 그룹과 같은 선택지).
- 회상 검색은 지금처럼 **턴당 1회**(쿼리=사용자 입력, 결과는 이미 `ctx.memories`로 엔진에 주입됨) —
  비용 불변. 엔진(pipeline)은 `memories`가 비어있지 않은 노드의 시스템 프롬프트에만
  "# 관련 기억(회상됨)" 블록을 덧붙임.
- 풀 파생: 에이전트 memories = 노드 선택 합집합(도구 파생과 동형).
- 효과: 259의 "memories 소비 선언했으나 미사용" 정직성 흠도 함께 해소(진짜 소비하게 됨).
- **열린 질문(v2 후보)**: 노드마다 *다른 검색 쿼리*로 회상(예: 앞 노드 결과로 재검색)은 턴당 N회
  검색 비용 — v1은 "같은 회상을 어느 노드가 받을지"만.

## 구현 스케치 (승인 후)
- chat.py: 노드형이면 rag_collections를 컬렉션별 도구로 분리 빌드 + 노드 memories 파생 검증.
- pipeline.py: 노드 memories 정규화 + 회상 블록 주입(ctx.memories 재사용).
- NodeListEditor: 도구 옵션에 컬렉션별 항목 + "기억" 멀티선택(노드 카드 한 줄 추가).
- 검증: 단위(노드별 도구 분리·회상 주입 노드 한정) + 실모델 e2e(두 노드가 다른 컬렉션 검색) +
  인스펙터 표면(266 규율 — 기록+표면).

## 검증 계획 요약
발화 필수 단언(151): 노드1이 A컬렉션만·노드2가 B컬렉션만 검색함을 호출 기록의 컬렉션 스코프로 단언.
메모리는 회상 블록이 선택 노드의 sentMessages에만 존재함을 단언.
