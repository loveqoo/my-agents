## 무엇이 실제로 있었나(신선-입력 실측)
1. **서버(rapid-mlx)는 정상** — 스트리밍 reasoning_content 델타 발화(신선 질문 500델타). 파서 적용
   상태 개발자 확언과 일치.
2. **411 배선(chat_template_kwargs)도 정상** — 신선 질문에서 ctk 단일 배선으로 reasoning 500델타.
3. **앱 파이프라인 전 구간 정상** — 세션 오버라이드(enable_thinking 켬)로 앱 SSE reasoning
   341프레임, UI 사고 과정 패널 라이브 표시(스샷), 재로드 접힘(424)과 결합 검증 6/6
   (tests/browser/verify-425-thinking-live.mjs).

## 오진의 근인 2개(재발 방지 핵심)
- **프로브 오염 — 서버 프롬프트 캐시 재생**: 같은 질문을 재사용한 프로브는 캐시 재생을 맞아
  reasoning이 생략된 응답(본문 선두 `\n\n` 잔흔, 소수 델타 즉시 도착)을 받는다. 이것이 "스트리밍
  미지원"·"root 키만 인식"이라는 **거짓 차등**을 만들었다(같은 요청이 직전엔 354델타, 직후엔 0).
  → **모델 동작 프로브는 입력을 매회 고유하게**(nonce 접미). 재생 징후(즉시 도착·선두 공백)를
  캐시 히트로 의심할 것.
- **층 오사용 — 스펙 370 핀**: 레지스트리 모델 params를 PUT해도 실행 중 에이전트는 **핀 스냅샷**을
  쓴다(capabilities만 라이브 — 설계 그대로). "설정을 켰는데 반영 안 됨"은 결함이 아니라 버전
  모델의 정상 동작이고, 지금 살리는 통로는 **세션 오버라이드**다.

## 패턴 회고(개발자 지적 — 같은 허위 보고 3회째)
"인프라(서버) 탓" 결론 직전에 반드시: ①내 프로브 입력이 오염 가능한가(캐시·상태) ②층을 옳게
썼는가(핀/라이브) ③사용자 실증과 어긋나면 **사용자 쪽이 맞다는 가정으로** 내 측정을 재설계.
스펙 410의 교훈(조사>프로브)에 더해, 이번 것은 **프로브 자체의 오염 축**이다.
