## 배경 / 버그 (사용자 보고, 2026-07-14)

"검색 결과에서 수정 버튼을 누르니까 전체 임베딩 데이터가 나옵니다" — 스펙 333의 정밀 진입이
엔티티 **객체 data** 행에서 조용히 실패. 근인: 히트 텍스트는 `entity_text()`의 평탄화 결과
(`key: value` 줄들)라 원본 JSONL(JSON 직렬화)에 그 문자열이 없다 → locate 3후보(원문/JSON
내부형/ASCII 이스케이프) 전부 불일치 → 우아한 강등 = 파일 첫 줄부터 표시("전체가 나옴").
333 e2e는 문자열 data만 써서 이 여집합을 놓침(회고 308 "저장 표현의 변주" 교훈의 미완).

## 설계 — 텍스트 매칭 대신 결정적 좌표

- **검색 코어**: 히트에 `Chunk.ordinal` 동반(1행=1청크 — ordinal이 곧 비어있지 않은 행의 순번).
  `SearchHit.ordinal: int | None` additive(비노출 핀 H5 무영향 — _hits_detail 화이트리스트 불변).
- **에디터**: `locateLine?: number` — 본문에서 **n번째 비어있지 않은 줄**(파서와 같은 규칙 —
  빈 줄 스킵)을 통째 선택+가운데 스크롤. 엔티티 히트는 ordinal로 이 경로, 문서형은 기존 텍스트
  후보 경로 유지(청크=원문 부분 문자열이라 유효).
- SearchDrawer: 엔티티면 `locateLine=hit.ordinal`, 문서형이면 `locate=hit.text`.
