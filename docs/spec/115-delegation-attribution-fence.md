# 115 — 위임 결과 attribution 견고화 (nonce 펜스, codex 102 설계한계 봉합)

## 배경 / 왜

스펙 102 codex가 설계한계로 남긴 것: 다중 위임 결과를 `fold_results`가 `## 능력: name (id)` 라벨로
구분해 이어붙이는데, 위임 텍스트가 이스케이프 없이 붙어 **악의적 결과가 가짜 `## 능력:` 헤더를 심어
출처를 스푸핑**할 수 있었다(라벨은 데이터 채널 *내부* 표식). 신뢰 경계(untrusted 데이터 채널 격리,
스펙 100)는 견고하나 그 *안의 출처 표식*이 위조 가능했다. 사용자 "1~4 루프"의 3번.

## 설계

### 위조 불가 경계 = 요청별 랜덤 nonce 펜스

각 결과 콘텐츠를 `⟦BEGIN {nonce}⟧…⟦END {nonce}⟧`로 감싸고 **`## 능력:` 라벨은 펜스 밖**(신뢰 —
오케스트레이터가 설정)에 둔다. `nonce`는 delegate 노드가 요청별 `secrets.token_hex(8)`로 생성해
**위임 능력에 절대 노출하지 않는다**. untrusted 콘텐츠는 nonce를 알 수 없어 펜스를 조기 종료하거나
진짜처럼 보이는 새 라벨 구획을 만들 수 없다 → 콘텐츠 내 가짜 `## 능력:`/`⟦END⟧`는 진짜 펜스 안에 격리.

`fold_results`는 **순수** 유지 — `fence`를 인자로 받아 결정적(nonce 생성은 노드가 담당, 테스트는 고정
fence). 단일 위임도 fence 주면 펜스(지침 일관성). fence 없는 레거시 호출은 구 라벨-only 폴백(문서화 경계).

### codex 적대(rung 3) 봉합

- **[P1] 라벨 자체가 위조 가능** — 라벨은 펜스 밖(신뢰)인데 `cap.name`/`cap.id`가 자원명(MCP/RAG/agent
  이름, 소유자가 정함)이라 개행 + `## 능력:`을 심으면 라벨 줄을 위조. → `_label_safe`로 name/id 개행을
  공백으로 접고 펜스 브래킷 제거(한 줄·펜스 위조 불가). **경계는 그 신뢰 구성요소까지 정규화해야 성립**.
- **[P2] 단일 raw + 지침 불일치** — 단일 위임은 raw인데 합성 지침은 항상 "출처=⟦BEGIN⟧ 앞 라벨"을 말해
  악의적 단일 결과의 가짜 펜스를 출처로 오인 가능. → 단일도 펜스 + 지침은 **`⟦BEGIN `가 실제로 있을
  때만** 출력(구조가 있을 때만 그 규칙을 설명).

## 검증

- **3런**: 단위(fold_results 세그먼트 파싱: 주입 가짜 라벨/틀린 nonce 종료표식이 body에 격리·결정성·
  라벨 개행 정규화 U4) + 통합(실 랜덤 nonce에서도 격리·delegate 노드 nonce 주입 소스 계약) + codex 적대.
  verify_102 무회귀.
- 조작적 정의: `_segments(out, nonce)`가 진짜 nonce로만 세그먼트를 파싱 — 이것이 "위조 불가 경계".

## 비목표 (OUT)

- 완전 구조화 출력(JSON array of {capability, content})로 텍스트 fold 대체 — 최종적으로 LLM 프롬프트로
  평탄화되므로 nonce 펜스가 더 직접적. 필요해지면 별개.
- LLM이 펜스를 **완벽히** 준수함의 보장 — 이는 모델 품질 문제(모든 프롬프트 인젝션 방어와 동일). 이
  스펙은 **진짜 경계를 위조 불가로** 만든 것(구조적 하한).
- fence='' 레거시 폴백을 예외로 강제(codex P2 제안) — 노드는 항상 nonce 주입, 직접 호출 테스트 편의로 잔존.
