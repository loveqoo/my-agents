# 350 — `approvals` 회수 + 폴링 비용 (전체 목록을 2.5초마다 받아오던 것)

## 왜 (감사 실측)

누수가 **둘** 붙어 있다.

1. **저장 누수**: 위험 도구 호출마다 `approvals` 1행이 쌓이는데 **삭제 코드가 리포 전체에 없다**.
   `resolve`는 status만 바꾸고, 스펙 346의 스윕은 `expired`로 표시할 뿐 행을 지우지 않는다.
   게다가 `session_id`가 **FK가 아니라 문자열**이라 세션을 지워도 승인 행은 남는다(고아).
2. **요청당 비용 누수**: 플레이그라운드가 승인 **1건의 상태**를 알려고
   `GET /approvals`(**전 상태·전 기간·LIMIT 없음**)를 **2.5초마다 최대 60회** 부른다
   (`Playground.tsx`). 행이 쌓일수록 폴링 한 번의 비용이 같이 커진다 — 저장 누수가 대역폭 누수로
   증폭되는 구조.

## 설계

### 1. 저장 — 배치 잡 `approval-cleanup`
- **처리된 승인만** 회수: `status != 'pending'` AND `resolved_at`(없으면 `requested_at`)이 보존기간을
  넘긴 것. **pending은 절대 안 지운다** — 그건 **재개의 근거**다(회고 038의 resume 고아 교훈).
  방치된 pending은 스펙 346의 스윕이 24h 뒤 `expired`로 바꾸므로, 그 뒤 이 잡의 대상이 된다(수명 사슬).
- 보존기간 노브: `approval_retention_days`(기본 **30일**, 관리자가 화면에서 조정·NULL이면 비활성).
- dry-run 지원 · 파괴적 노브 바닥(0/음수 = 비활성, learning 037).

### 2. 폴링 — **O(전체 테이블) → O(1)**
`GET /approvals/{approval_id}` 단건 조회를 신설하고, 플레이그라운드가 그것만 폴링한다.
목록을 받아 그 안에서 찾던 것을 **필요한 1건만** 받는다(같은 인가 규칙 — 볼 수 없는 건 404).

## 완료 조건 (수치)

- **A1** 오래된 **처리된** 승인만 삭제. **pending은 0건 삭제**(재개 근거 보존).
- **A2** dry-run은 세기만 하고 삭제 0.
- **A3** 보존기간 NULL/0이면 잡 비활성(delete-all 금지).
- **A4** 단건 조회 라우트가 동작하고, 플레이그라운드가 **더 이상 전체 목록을 안 부른다**(코드 스캔 +
  실제 폴링 요청의 응답 크기가 승인 행 수에 **비례하지 않음**).
- **A5** 인가: 남의 승인은 단건 조회에서 **404**(존재 비노출 — 기존 목록 스코핑과 동일 규칙).
- **A6** 게이트: `approvals` leaking → reclaimed, **스코어보드 5 → 4**.
- 무회귀: verify_066(승인 인가) · 041(HIL) · 게이트 347.
