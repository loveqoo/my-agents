# 357 — 삼킨 add 위 파괴적 삭제·거짓 확인 봉합 (버그 #2의 미청산 형제)

## 왜 (전수조사 확증 — deep-reasoner + 직접 라인 확인)

`Mem0Backend.add`는 임베더 장애·차원 불일치 등에서 예외를 `except`로 삼켜 `[]`를 돌린다
(`mem0_backend.py:284-286`). 이 삼킴 자체는 채팅 graceful 경로(메모리 부재가 채팅을 죽이지 않음)에선
by-design이다. 문제는 **삼킨 실패를 검사하지 않고 파괴/보고를 진행하는 소비자**들이다 — 고친 버그 #2
(삼킨 add)의 직계 형제.

### P1 — 통합 잡이 삼킨 add 실패 위에서 원본을 삭제 (데이터 유실)

`batch/jobs.py` 통합 잡 순서: ① 원본 `MemorySnapshot` 박제·commit(롤백 앵커) → ② `memory.add`로
통합본 적재(**반환 무시**, 354-357) → ③ 원본 삭제(무조건, 359-361).

- `get_all`(후보 선정)은 순수 SQL이라 임베더 없이 성공하지만 `add`는 임베딩이 필요 → **임베더만 죽은
  상태에서 후보 선정·삭제는 되고 저장만 실패**하는 비대칭이 성립.
- 결과: 통합본은 라이브 스토어에 없는데 원본은 삭제 + `batch_runs`는 `status:"ok"`로 성공 위장
  (**silent green**). 스냅샷 덕에 영구 소실은 아니나 **자동 복원 경로가 없어** 수동 개입 필요.
- 근거: learning 061 — graceful degradation은 뒤따르는 파괴 연산의 원자성을 못 넘는다. 삭제라는
  비가역 앞에선 정직한 fail-closed(삭제 스킵 + 실패 보고)가 옳다.

### P2 — 삼킨 add 위의 거짓 "저장됨" 확인 (유실 아님, 거짓 보고)

- `broker/providers/memory.py:239-249` — 백엔드 부재(`resolve_backend is None`)만 거르고 `add` 반환은
  무시한 채 `"장기 기억에 저장했습니다"` 반환. add-시점 임베더 실패가 삼켜지면 **저장 안 됐는데
  저장했다고 통보**.
- `agents/memory_routes.py:156-162` — 에이전트 자가기록 add 반환 무시 후 `{"ok": True}`.

## 설계 — 파괴/보고를 add 성공에 게이트

세 소비자 모두 `infer=False`에 **실제 사실 문자열**을 넘긴다. mem0는 infer=False에서 사실을 그대로
저장하고 **생성된 행(≥1)** 을 돌려주므로, 정규화 후 **빈 반환 = 실패 신호**다(0-추출은 infer=True에서만
발생 — 이 세 경로엔 없음). 빈 반환을 실패로 판정하면 세 경로 모두 안전한 방향으로 에러한다
(통합잡: 삭제 스킵 → 중복이지 손실 아님 / 브로커·라우트: no-op를 실패로 = 안전한 오보고).

- **P1(jobs.py)**: 각 fact의 add 반환을 모아 하나라도 비면 그 유저 **삭제를 건너뛰고**(`continue`)
  `log.error` + `failed_users`에 기록. 잡 반환 status는 실패가 있으면 `"degraded"`(+`failed` 목록),
  없으면 `"ok"` — silent green 제거.
- **P2(memory.py 브로커)**: add 반환이 비면 `"저장했습니다"` 대신 `error="장기 기억 저장에
  실패했습니다"` 반환(trust=untrusted 유지).
- **P2(memory_routes.py)**: add 반환이 비면 `{"ok": True}` 대신 `HTTPException(502, "메모리 저장 실패")`.
- `add`의 삼킴 계약은 **바꾸지 않는다**(채팅 graceful 유지) — 봉합은 소비자 측 게이트로.

## 완료 조건 (수치)

- **C1** 통합 잡: add가 빈 반환이면 그 유저 원본 삭제 0건 + status `"degraded"` + `failed`에 uid.
- **C2** 통합 잡 정상 경로 무회귀: add 성공 시 기존대로 삭제·status `"ok"`.
- **C3** 브로커·라우트: add 빈 반환 시 거짓 "저장됨" 0건(에러 경로).
- **C4** 전체 기능점검(구남님 지시): `make test` 씨앗 그물 초록 + 실제 채팅 정상 + 통합 잡 dry-run·run 정상.
- **C5** 적대 검증(codex): "add 성공했는데 삭제 스킵" 같은 역방향 오판·경계 여집합 확인.

## OUT

- `add` 자체를 raise-on-failure로 바꾸는 것(채팅 graceful 계약 파괴) — 소비자 게이트가 옳다.
- 자동 복원 파이프라인(스냅샷→라이브 재적재) — 별개 스펙 후보(지금은 유실 방지가 먼저).
