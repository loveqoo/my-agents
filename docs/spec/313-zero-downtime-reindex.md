# 313 — 무중단 재인덱싱 (검색 잠금 해제, MVCC 기반)

## 배경

스펙 312가 컬렉션 재인덱싱/재청킹을 도입하면서, 재인덱싱 중 컬렉션은 **배타 잠금**
(`status='reindexing'`)으로 검색·인제스트·수정·삭제를 전부 409로 막았다. 검색까지 막힌 이유는
(1) 당시 "다른 사람이 접근 못 하게"라는 명시 요구, (2) "벡터 교체 중 부분결과(옛+새 혼출)" 위험에
대한 과대평가였다.

에이전트·평가는 컬렉션을 **읽기**로 쓴다. 모델·청크를 A/B로 바꿔가며 검색 품질을 튜닝하는 게
재인덱싱의 목적인데, 튜닝 중 검색이 409로 멎으면 그 사이 에이전트/평가가 멈춘다. → **무중단
재인덱싱**: 재인덱싱이 진행돼도 검색은 계속 서비스.

## 핵심 통찰 — MVCC가 이미 무중단을 성립시킨다 (세대 컬럼 불필요)

`_do_reindex`의 두 경로(모델교체·재청킹)는 이미 **① 새 벡터를 HTTP로 전량 계산 → ② 한 트랜잭션으로
삭제+삽입(또는 UPDATE)+커밋**이다(코드 주석: "새 벡터를 먼저 전량 계산(txn 미보유) 후 한 트랜잭션으로
원자 스왑").

Postgres MVCC(스냅샷 격리)에서 동시 검색(리더)은:
- **계산 단계(①)**: 옛 청크가 커밋 상태 그대로 → 검색은 **옛 결과**. ✓
- **스왑 트랜잭션(②) 진행 중**: 미커밋 삭제/삽입은 다른 트랜잭션에 안 보임 → 검색은 여전히 **옛 결과**. ✓
- **커밋 순간**: 검색이 **새 결과**로 전환. 절대 반쪽(옛+새 섞임)을 못 봄. ✓
- 리더는 라이터를 기다리지 않음(MVCC) → 검색이 스왑에 **블로킹되지 않음**. ✓

즉 **원자 단일 트랜잭션 스왑 + MVCC = 무중단이 이미 구조적으로 성립**해 있다. 스펙 312가 검색을 막은
건 요구/과대평가 탓이지 부분결과가 실제로 가능해서가 아니다. 따라서 무중단은 **검색의 잠금 검사만
제거**하면 된다 — 세대(generation) 컬럼·스키마 변경 불필요(갈래 A 기각, YAGNI/과설계).

사용자 멘탈모델("옛 걸로 서비스하며 새 걸 만들고 순간 교체")과 정확히 대응한다 — 그 "순간 교체"가 곧
스왑 트랜잭션의 커밋이고, "옛 걸로 서비스"가 곧 MVCC 스냅샷 읽기다.

## 범위 (IN)

1. **`runtime.py search_collections`**: 재인덱싱 잠금 검사(`status=='reindexing'`→`RagSearchError("locked")`)
   **제거**. 검색은 커밋된 것을 읽는다(옛→스왑→새). 무중단 근거를 주석으로 남긴다(MVCC 원자 스왑).
2. **`rag.py` 검색 엔드포인트**: 도달 불가능해진 `kind=="locked"`→409 매핑 제거. 그 외는 502 유지.
3. **`rag.py _do_reindex`**: 원자 스왑이 MVCC 전환점임을 주석 명시. 모델교체 경로를 "텍스트 읽기(짧은
   txn) → 커밋 → HTTP 임베딩 → 짧은 쓰기 txn"으로 다듬어 트랜잭션 보유 시간 단축(재청킹은 이미 계산
   후 짧은 스왑이라 그대로).
4. **프론트 `ReindexModal` 카피**: "재인덱싱 중 접근 잠금" → **"검색은 무중단(진행 중엔 이전 결과, 완료
   순간 새 결과)"**. 인제스트·편집·삭제는 잠깐 대기(쓰기끼리만 조율)라는 안내로 교정(긍정문).

## 유지 (변경 없음)

- 인제스트·수정·삭제의 `_reject_if_reindexing` 가드 + `_persist_chunks` 조건부 UPDATE(F1) + 재인덱싱
  상호배타 CAS 잠금 — 인제스트·재인덱싱은 DB 행 잠금/조건부 UPDATE로 **직렬화**(F1 유실·중복 재인덱싱
  방지). **검색만** 잠금을 안 본다. (단 `update_collection`/`delete_collection`/`delete_document`는
  point-in-time 가드라 잠금 직전 통과 후 늦게 커밋하는 TOCTOU 창이 남는다 — 스펙 312 F4의 기존 경계
  `rag.py` 주석 참조. 본 스펙이 새로 만든 게 아니라 그대로 승계.)
- 부팅 시 stale `reindexing` 회수(`_recover_stale_reindex`) — 단일 워커 경계 그대로.

## 범위 밖 (OUT)

- **무중단 인제스트**: 재인덱싱 중 인제스트는 여전히 409(F1 유실 방지 — 동시 인제스트는 새 문서가
  스왑 후 사라지거나 모델 혼합). 무중단 대상은 **검색(읽기)**. 인제스트 무중단은 델타 이중쓰기가
  필요해 빚으로 남긴다.
- **초대형 컬렉션의 단일 트랜잭션 부담**: 청크 수만 개면 스왑 txn이 커진다(WAL·락 시간). 개인 도구
  규모에선 무해. 필요 시 세대 기반 다중 커밋(갈래 A)으로 에스컬레이션.
- **다중 컬렉션 검색의 전역 단일 스냅샷**: `search_collections`는 한 호출에서 컬렉션별 SELECT를 순회하고
  Postgres 기본 격리가 READ COMMITTED(문장별 스냅샷)라, A 읽은 뒤 B 읽기 전 B의 재인덱싱이 커밋되면
  한 호출 안에서 A=옛 세대·B=새 세대가 될 수 있다(codex 항목 6). **이는 단일 컬렉션 내 혼출·409·빈결과가
  아니다** — 각 컬렉션은 원자적으로 옛→새로 전환하고, 두 상태 모두 유효한 커밋 상태다. 무중단(검색이
  안 막힘·부분결과 없음)은 성립. "호출 전체가 하나의 시점"까지 원하면 검색 세션을 REPEATABLE READ로
  올리면 되나(전역 스냅샷), 재인덱싱 중 컬렉션별 신선도가 살짝 어긋나는 건 정확성 위반이 아니라 빚으로
  남긴다(YAGNI — 개인 도구, 에이전트는 대개 단일 컬렉션 검색).
- 차원 변경(1024↔768) · RAG 모델·청크 비교 격자 · 멀티워커 stale lease · 관리 CRUD 원자 배타(F4) —
  스펙 312 OUT 그대로.

## 검증 (무중단을 *증명* — 사다리 3단)

- **실동시성 통합**(핵심 rung): `asyncio.gather`로 실제 재인덱싱(mock→e5, HTTP 수초)과 동시에 검색
  버스트 실행 → **모든 검색이 200·hit≥1**(절대 409·빈결과 아님), hits가 스왑 전후로 옛→새 유사도로
  전환됨을 단언. 이 rung만이 "검색이 재인덱싱에 블로킹되지 않고 부분결과도 안 본다"를 실측한다.
- **단위 시맨틱**: `status='reindexing'`인 컬렉션을 검색하면 잠금 에러 없이 결과 반환(옛 청크).
- **적대(codex)**: "검색이 옛+새 섞인 부분결과를 보는 창이 있나?" 반증 시도 — MVCC 단일 txn 스왑이
  막는다는 주장을 공격. 여집합: 스왑이 여러 트랜잭션으로 쪼개지는 경로가 있나(있으면 무중단 깨짐).

## 완료 조건

- 재인덱싱 중 검색이 200을 반환(409 아님)하고, 진행 중엔 옛 결과·완료 후 새 결과, 반쪽 결과 0.
- 쓰기(인제스트·수정·삭제·재인덱싱)끼리는 여전히 직렬화(F1 회귀 없음).
- 프론트 카피가 무중단을 정직하게 안내(검색 계속·쓰기 잠깐 대기).
- ruff/mypy 클린, tsc 0, 기능 왕복 통과, codex 적대 통과.
