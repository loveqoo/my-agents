# 스펙 434 — 재인덱싱 잠금: 취소에도 반드시 해제(433 P2 마감)

## 문제(codex 433 P2 — 선재)

재인덱싱은 CAS로 `status='reindexing'` 잠금을 잡고 try/except로 푼다. 그런데 핸들러가
**`except Exception`**이라 `asyncio.CancelledError`(BaseException 계열)가 **안 잡힌다** —
클라이언트 이탈·서버 종료 신호·태스크 취소가 오면:

- 데이터는 안전(미커밋 스왑이 롤백 — 원 청크 온전, 스펙 312 원자성).
- 그러나 **status는 `reindexing`에 갇힌다** → 그 컬렉션의 편집·업로드·삭제·재인덱싱이 **전부 409**.
- 회수 주체는 **부팅 스윕(`_recover_stale_reindex`)뿐** → **서버 재기동 전까지 고착**.

개인 도구에서 "한 번 맞으면 재기동해야 하는" 부류라 우선 마감.

## 불변식(먼저)

**"잠금을 잡은 코드는 어떤 종료 경로로 나가든 반드시 푼다."** 취소는 예외의 특수 사례가 아니라
*정상적인 종료 경로 중 하나*로 다뤄야 한다([[policy-at-the-chokepoint]] — 해제를 한 지점에서 보장).

## 결정 — 소유자 해제(취소 포함), TTL 스윕은 기각

### A. `except BaseException` 해제 경로 추가
`reindex.py`의 try에 취소·기타 BaseException 핸들러를 더해 **잠금을 반드시 해제**:
- 데이터는 롤백(스왑 미커밋) → 상태는 **`ready`**가 정확(부팅 스윕과 같은 근거: 원 상태 온전).
- 취소 컨텍스트에선 현재 세션이 이미 죽었을 수 있으므로 **새 세션 + `asyncio.shield`**로 해제
  (스펙 403 `shielded_release` 선례 — 취소 중 정리 작업 보호).
- **발자국 남기기**([[431 관측]]): 재인덱싱 이력에 `status='error'`, error="취소됨(클라이언트 이탈·
  서버 종료)"을 best-effort 기록 — 사용자가 "왜 사라졌나"를 이력에서 본다.
- 해제 후 **원래 예외를 그대로 재전파**(취소 의미 보존 — 삼키지 않는다).

### B. TTL 주기 스윕은 **기각**(안전 위반 위험)

"오래된 reindexing 잠금을 주기적으로 푼다"는 안전망은 매력적이지만 **살아있는 잠금을 뺏을 수 있다**:
대형 컬렉션 재인덱싱이 TTL을 넘기면 스윕이 status를 ready로 돌리고, 그 틈에 인제스트가 청크를
커밋한 뒤 재인덱싱의 DELETE-전량 스왑이 그걸 지운다(= 데이터 손실). 안전하려면 heartbeat/lease가
필요한데, A가 실질 전 경로를 덮으므로(취소=A, 프로세스 사망=부팅 스윕) 지금은 **불필요한 위험**.
필요해지면 별도 스펙(heartbeat 컬럼 + lease).
