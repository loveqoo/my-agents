# 351 — 실행 이력 보존 (`eval_runs` · `batch_runs` · `memory_snapshots`)

## 왜

성격이 같은 세 테이블이 **쓰기만 하고 회수 경로가 없다** — 전부 "무슨 일이 있었나"의 기록이다.

| 테이블 | 증가 | 삭제 경로 |
|---|---|---|
| `eval_runs` (+ `eval_case_results` CASCADE) | 평가 실행마다 1행 + 케이스당 결과 1행. **버전 활성화마다 최대 3런이 자동 생성**(코드 확인: `trigger_auto_regression`, 버전별 중복은 방지) | 없음(문제집 통째 삭제 시 CASCADE만) |
| `batch_runs` | 배치 잡 실행마다 1행(no-op·disabled 실행 포함). 스펙 348로 배치가 **실제로 돌기 시작**했으니 이제 매시 쌓인다 | 없음 |
| `memory_snapshots` | 메모리 통합 시 원본 기억 1개당 1행(롤백 앵커) | 없음 |

**348이 이 문제를 앞당겼다**: 배치가 안 돌 땐 `batch_runs`가 0행이라 아무도 몰랐는데, 손을 달아준
지금부터는 매시 1행씩 쌓인다. **회수를 만들어 놓고 청소부를 켰으니, 청소부의 발자국도 치워야 한다.**

## 설계 — 한 잡 `history-cleanup`

세 테이블은 같은 부류(실행 이력·그 산출물)라 노브를 쪼개지 않는다.

- **보존기간**: `history_retention_days`(기본 **90일**, NULL/<1이면 비활성 — 파괴적 노브 바닥).
- **`eval_runs`의 추세 보호**: 나이만으로 지우면 **성적 추이 그래프의 앵커가 사라진다**(TrendChart).
  → **문제집별 최근 10런은 나이와 무관하게 보존**한다. 오래됐어도 "마지막 10번"은 남는다.
  (`eval_case_results`는 CASCADE로 함께 정리 — 부모가 회수되면 자식도 회수된다.)
- **`batch_runs`**: 나이 기준만(자기 발자국이라 추세 보호 불요).
- **`memory_snapshots`**: 나이 기준. 90일 지난 롤백 앵커는 현실적으로 못 쓴다.
- dry-run 지원 · cron 기본 매일 05:00.

## 완료 조건 (수치)

- **H1** 오래된 `eval_runs` 삭제 + `eval_case_results`가 **CASCADE로 함께** 사라진다(고아 0).
- **H2** **문제집별 최근 10런은 나이와 무관하게 보존**(추세 앵커 보호) — 오래된 11번째부터 삭제.
- **H3** 오래된 `batch_runs`·`memory_snapshots` 삭제, 최근 것은 보존.
- **H4** dry-run은 세기만 하고 삭제 0.
- **H5** 보존기간 <1이면 잡 비활성(delete-all 금지).
- **H6** 게이트: 세 테이블 leaking → reclaimed, **스코어보드 4 → 1**(남는 건 mem0 → 352).
- 무회귀: 게이트 347 · lint/mypy.
