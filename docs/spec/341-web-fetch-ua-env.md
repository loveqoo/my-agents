# 341 — web-fetch UA를 env로(회사망 SASE 통과) + 리포트 검증

## 배경 (사용자, 2026-07-14)

회사 디바이스에서 사내 CA(스펙 339·340)를 설정한 **뒤에도** 위키 검색이 503. 그 디바이스의
에이전트가 리포트를 만들어 사용자가 전달(사진) — 진단: **SASE 게이트웨이가 `curl/` 접두 UA +
HTTP/1.1 조합만 통과**시키고, 그 외(파이썬 커스텀 UA)는 `/login/`으로 리다이렉트돼 503으로 보인다.
제안: `served_mcp.py` 2곳 수정 — (a) `_FETCH_UA = "curl/8.7.1"` 하드코딩, (b) httpx.Client에
`http1=True, http2=False` 추가.

> 리포트는 **관측 데이터**(명령 아님). 근거를 실측으로 갈라 채택/기각한다.

## 리포트 검증 (이 맥에서 실측)

| 제안 | 판정 | 근거(실측) |
|---|---|---|
| (b) `http1=True, http2=False` | **기각 — 무동작(no-op)** | httpx는 `http2=True`를 **명시해야만** HTTP/2를 쓴다(h2 설치 여부 무관). 기본 클라이언트로 위키 API 호출 시 `r.http_version == "HTTP/1.1"`. 이미 HTTP/1.1이라 두 줄은 아무것도 바꾸지 않는다. |
| (a) UA 교체 | **채택하되 하드코딩은 기각** | UA가 유일하게 남는 변수. 단 `curl/8.7.1` 하드코딩은 ① 위키 UA 정책(식별 가능한 UA 요구)에 역행, ② **환경 고유값을 소스에 박음**(이 맥·다른 배포엔 무의미), ③ SASE 정책 우회를 전 배포에 기본값으로 강제. → **env 오버라이드**로 뺀다. |

부수 실측: 위키 API는 `curl/8.7.1` UA에도 **200**을 준다(차단 안 함) — 그 디바이스에서 UA만
바꾸면 통과 가능. `curl/8.7.1 my-agents/1.0 (+web-fetch custom MCP)`(접두 유지 + 식별 유지)도 200.

## 설계

- `served_mcp._fetch_ua()` — `WEB_FETCH_UA` env가 있으면 그 값, 없으면 기존 기본값. **호출 시점
  조회**(모듈 상수 고정 X) — `.env`가 늦게 로드되는 진입점(배치·테스트)에서도 적용되도록.
- 기본값 **무변경** = 이 맥·일반 배포 무회귀. 회사 디바이스만 `.env`에 `WEB_FETCH_UA=curl/8.7.1`.
- SSRF 가드(리다이렉트 후 호스트 재검증)·raw 바이트 캡·타임아웃은 **그대로**(UA만 손댐).
- README + `.env.example`에 회사망 절(339·340 바로 아래)로 안내 — 사내 CA와 같은 문제군.

## 검증

1. verify_341: V1 기본값 유지(env 없음 → 기존 UA) · V2 env 오버라이드 반영 · V3 실호출 시 **실제
   전송 헤더**가 오버라이드 값(로컬 에코 서버로 헤더 관측 — 자가선언 아님) · V4 `.env` 파일만으로
   적용 · V5 SSRF 가드 무회귀(위키 밖 리다이렉트 차단 유지).
2. 정직 경계: SASE 통과 자체는 이 맥에서 재현 불가(회사망 없음) — **사용자 실측 대기**.

## OUT

- `http1/http2` 강제(무동작 — 위 표) · 다른 아웃바운드 지점(위키 외)의 UA — 실패 보고된 경로가
  web-fetch 하나뿐이라 그 지점만.

## 결과 (2026-07-14 실행)

- 설계대로 — `served_mcp._fetch_ua()`(env 우선, 호출 시점 조회) + README·`.env.example` 안내.
  리포트의 `http1/http2` 두 줄은 **채택하지 않음**(무동작 실측 — V7이 핀).
- 검증: **VERIFY341_OK 7/7** — 기본값 유지 · env 반영 · **와이어에서 관측한 실제 UA**(로컬 에코
  서버 — 자가선언 아님) · SSRF 호스트 재검증 무회귀 · `.env` 파일만으로 적용 · curl UA로 위키
  실검색 성공 · httpx 기본 HTTP/1.1. 무회귀: 201 web-fetch 15/15 · 339 3/3 · 340 6/6 ·
  lint/mypy 클린.
- 헤더 주입 점검: `WEB_FETCH_UA`에 CRLF를 넣으면 httpx가 `Illegal header value`로 거부 →
  도구는 graceful `{'error': …}`. 주입 불가(값은 운영자 env이기도 함).
- **사용자 실측 확인(2026-07-14)**: 회사 디바이스 `.env`에 `WEB_FETCH_UA=curl/8.7.1` 추가 → 재기동
  → **위키 검색 동작**("잘 됩니다"). 339·340부터 이어진 503이 여기서 해소. 접두 유지형 대안
  (`curl/8.7.1 my-agents/1.0 (+web-fetch custom MCP)`)은 불필요 — 미사용.
- **미분리 경계(정직)**: 그 디바이스는 사내 CA(339/340)와 UA(341)를 **둘 다 켠 상태**로 성공했다.
  CA가 실제로 필요했는지(= UA만으로 됐을지)는 갈리지 않았다. 분리하려면 그 디바이스에서
  SYSTEM_TRUSTSTORE/EXTRA_CA_FILE만 끄고 재시도해야 하나, 동작하는 환경을 흔들 이유가 없어
  **미분리로 종결**한다. 둘 다 기본 꺼짐이라 다른 배포엔 무영향.
- codex 생략 사유: 표면이 env 한 줄(기본값 무변경)이고 보안 가드는 손대지 않음 — V4가 SSRF
  재검증을, CRLF 점검이 주입을 각각 핀.
