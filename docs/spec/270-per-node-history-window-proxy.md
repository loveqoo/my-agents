# 270 — 단기 기억 프록시: 노드별 대화 히스토리 창(HistoryWindowProxy)

> 3부작 중 2/3. **269 어휘(완료) → 270 단기 프록시 → 271 공용 컴포넌트.**
> 사용자 설계(회고 244): 프록시가 원본 대화를 쥐고 **노드마다 다른 N개를 떼감** — mem0를 노드별
> 키워드로 조회하는 것(스펙 268)과 **동형**. "모델에 넘기는 주체만 다르고 프롬프트 구성은 동일."

## 배경 — 내가 깼던 asymmetry

269 논의에서 나는 "단기 기억은 대화 단위라 노드에 못 쓴다"고 단정했고 사용자가 뒤집었다: 대화는
공유 자원이지만 **몇 개를 떼느냐(N)는 노드마다 다를 수 있다**. mem0 저장소가 공유 자원인데 노드마다
다른 키워드로 조회하듯(268), 대화 히스토리도 프록시가 한 번 쥐고 노드별로 슬라이스+캐시하면 된다.

## 현재 구조 (측정)

- 파이프라인 그래프는 `{"messages": _window(대화, 에이전트 historyDepth)}`로 시드된다
  (`chat.py:1019-1041`). 즉 **에이전트-레벨로 이미 윈도된 대화 전체**가 초기 상태.
- 노드는 그 위에 누적(carry)하거나 격리(clean)한다(`pipeline.py:_step`). 그래서 **대화 히스토리와
  턴내 노드 출력이 한 `messages` 리스트에 뒤섞인다** — 노드가 "대화만 N개"를 떼려 해도 경계가 없다.
- 회상 프록시(`_MemoryRecallProxy`)는 이미 이 패턴의 선례: 턴 스코프 생성·키워드 캐시·기록
  (`chat.py`), 엔진은 `ctx.memory_recall`로 주입받아 노드 첫 진입에 호출(`pipeline.py:208 _recall_block`).

## 설계 모델 — 두 축을 분리한다

핵심: **대화 히스토리(턴 가로지름)와 턴내 노드 흐름을 개념적으로 분리**한다. 지금은 한 리스트에
섞여 노드별 제어가 불가능하다.

| 축 | 무엇 | 제어 | 스코프 |
|---|---|---|---|
| **단기 기억** (신규) | 이전 *대화* 턴(이번 턴 이전) 몇 개를 볼지 | 노드별 `historyDepth` | 턴 가로지름(프록시 보유) |
| **이전 결과 받기** (기존) | 이번 턴 *앞 노드 출력*을 볼지 | 노드별 `context` carry/clean | 턴 내(누적 상태) |

두 축은 **직교**한다. 단기 기억 = 대화(과거 턴), 이전 결과 받기 = 이번 턴 노드 흐름. 269 표의 그
"완전 대칭"을 여기서 실현한다.

### 기계 변경 — 대화를 누적 상태에서 분리

1. **시드 축소**: 파이프라인 그래프를 **현재 턴 입력만**으로 시드(`messages[-1:]`). 이전 대화는
   누적 상태에 넣지 않는다.
2. **프록시 보유**: 이전 대화(윈도 상한까지)는 `HistoryWindowProxy`가 쥔다.
3. **노드별 주입**: `_step`이 프롬프트를 `[sys+회상] + [프록시(node_depth) 슬라이스] + [턴내 msgs]`로
   조립. 대화 슬라이스는 **누적되지 않고** 노드마다 새로 주입 → carry/clean은 턴내 흐름만 관장(불변).

### HistoryWindowProxy (MemoryRecallProxy 형제)

- **턴 스코프 생성**: 요청당 1개, 이전 대화(`prior_messages`)를 생성 시 캡처(스코프 고정 = RBAC/격리,
  브로커·회상 선례).
- **depth 키 캐시**: `proxy(depth)` → 이전 대화의 마지막 `depth`개. 같은 depth = 같은 슬라이스 공유
  (`_window` 시맨틱 재사용: 0=이번 턴만→빈 대화, None/음수=전체).
- **기록**: `(node, depth, count)` → `trace["historyWindows"]`(인스펙터 관측 — 조회 프록시가 관문이라
  관측 공짜, 082/266 자동 충족). 마스킹은 형제 규약 상속(내용 아닌 건수만 기록 → 누출 0, 243 ③ 교훈).

- `pipeline.py:_step`: 노드 depth로 프록시 호출해 대화 슬라이스 주입. clean과의 상호작용은 아래 결정.
- **sent_messages 캡처**(`_build_sent_messages`, `chat.py:1025`)가 시드 축소로 과소보고되지 않게
  노드별 실제 조립(슬라이스+msgs)을 반영 — 캡처 계약(131) 유지.

### P3. 3주입 미러 (learning 149 규율 — 재개는 세 번째 반복, 회고 243 ②)

  "메인에 축 더하면 재개·A2A에 같은 축" 규율.

## 무회귀 (기본 상속이 관건)

- 노드가 `historyDepth`를 **지정 안 하면 에이전트-레벨 값 상속** → 기존 파이프라인은 **모든 노드가
  동일 대화 창**을 봄 = 오늘과 콘텐츠 등가. 시드 분리는 내부 재배치일 뿐 노드가 보는 대화 집합은 불변.
- 비파이프라인(직접/조율/산출물)은 이 경로를 안 탄다 — `history_window=None`, 기존 `_window` 그대로.
- clean 노드의 대화 슬라이스: 기존 clean은 "앞 결과만"이라 대화도 안 봄 → **clean이면 대화 슬라이스도
  생략**(clean의 격리 의미 보존)이 기본안. (이전 결과 받기=carry일 때만 단기 기억 창 적용.)

2. 같은 depth 두 노드 → 프록시 **캐시 공유**(실슬라이스 계산 1회, 268 캐시 패턴과 동형 단언).
3. `historyDepth` 미지정 노드 = 에이전트-레벨 값 상속(무회귀 — 기존 268 e2e 재실행 GREEN, 노드가 보는

## 검증 (사다리 3단)

- **단위**: 프록시 슬라이스/캐시(depth별 길이·공유·0=빈대화·전체), 엔진 노드별 주입(depth 다른 3노드가
  각자 슬라이스 받음·clean은 대화 생략·미지정=상속), 스키마 화이트리스트 왕복.
- **실인프라 e2e**(실모델): 노드별 대화 창이 실제 모델 입력에 반영됨을 `historyWindows` + 응답 근거로
  단언(예: 앞 턴 사실을 depth 큰 노드만 참조). 268 무회귀 재실행.
- **적대(codex)**: 시드 분리가 대화를 이중 주입/누락하지 않는지, 재개 prior 재구성이 원 턴과 일치하는지,
  clean·capture·마스킹 계약 유지, 상속 기본이 정말 무회귀인지.

## 확정된 결정 (사용자 검토 완료)

1. **[확정] 대화-누적 분리 모델** — 대화를 프록시로 들어내고 노드별 슬라이스 주입. "단기=대화"
   시맨틱에 맞는 유일한 길. 대안(누적 리스트 재윈도)은 경계 모호로 반려.
2. **[확정 (가)] clean이면 대화 슬라이스도 생략** — "이전 결과만"은 말 그대로 앞 결과 하나만(대화도
   격리). 라벨 정직·모델 단순. **단기 기억(N개) 설정은 carry("대화 전체와 함께")일 때만 의미** →
   노드가 clean이면 UI에서 단기 기억 컨트롤을 **비활성**(맥락 컨트롤이 하위 어포던스 승계).
3. **[확정] 노드 "단기 기억" 첫 옵션 = "상속(에이전트 설정)"** — 미지정=상속이 기본, 대부분 상속.
