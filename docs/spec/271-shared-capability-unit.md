# 271 — 공용 역량 단위(Capability Unit) 컴포넌트: 에이전트·노드가 같은 설정을 공유

> 3부작 중 3/3. **269 어휘(완료) → 270 단기 프록시(완료) → 271 공용 컴포넌트.**
> 269·270이 단기/장기 대칭을 심었으니, 이제 겹치는 facet을 **에이전트·노드 공용 컴포넌트**로 추출.

## 개념 — 노드는 미니 에이전트, 둘 다 "역량 단위"다

269 논의에서 확립: 에이전트(단순/조율)와 파이프라인 노드는 **같은 6개 facet**을 공유한다. 사용자 말:
"모델에 넘기는 주체만 다르고 프롬프트 구성은 동일."

| facet | 에이전트(직접/조율) | 노드 | 현재 렌더 방식(불일치) |
|---|---|---|---|
| 모델 | ✅ | ✅ | 둘 다 Select(일치) |
| 프롬프트(페르소나) | ✅ | ✅ | 에이전트=페르소나 Select / 노드=프롬프트 textarea+불러오기 |
| 도구(MCP) | ✅ | ✅ | 에이전트=PickerGroups / 노드=인라인 multi-Select |
| 문서(RAG) | ✅ | ✅ | 에이전트=**별도** PickerGroup / 노드=**도구에 접힘**(268 P1) |
| 장기 기억(mem0) | ✅ | ✅ | 에이전트=PickerGroups / 노드=인라인 multi-Select |
| 단기 기억(히스토리) | ✅ | ✅ | 에이전트=세부 ③ Select / 노드=카드 Select(270, 일치) |

## 현행 비대칭 (측정 — 통합이 풀어야 할 것)

1. **렌더 패러다임**: 에이전트=`PickerGroups`(카탈로그 접이식+검색+카운트, 100+ 항목 대비 스펙 107/109) /
   노드=인라인 multi-Select(카드 간결). 두 방식이 도구·문서·기억에서 갈린다.
2. **문서 위치**: 에이전트=도구와 **별도** facet / 노드=도구 옵션에 **접힘**(`문서 검색 · <컬렉션>`, 268 P1).
3. **프롬프트 표현**: 에이전트=페르소나 **선택**(blocks 카탈로그) / 노드=프롬프트 **직접 작성**(+페르소나 불러오기).
4. **배치**: 에이전트=3스텝 분산(모델·페르소나=①, 도구·문서·기억=②, 단기·temperature=③) / 노드=단일 카드.

이 넷이 "공용 컴포넌트"가 흡수·정렬해야 할 대상이다. 특히 269가 단기를 세부 ③에 남긴 **과도기 어긋남**을
여기서 바로잡는다(단기·장기가 한 자리에서 읽히게).

## 설계 방향 — 세 가지 안 (사용자 결정 필요)

### 안 A. 완전 단일 컴포넌트 (`<CapabilityUnitEditor>`)
6 facet을 한 컴포넌트로. 에이전트·노드가 같은 컴포넌트 렌더, 각자 고유 컨트롤(에이전트=종류·저장·
temperature·추천명령·위임 / 노드=이름·이전결과·형식·회상기준)로 감쌈.
- 장점: 최고의 DRY·완전 일관. 단점: PickerGroups(카탈로그 스케일)와 카드 간결성이 충돌 — 한쪽 UX 훼손
  위험. 큰 리팩터(에이전트 폼 스텝 구조 재편). **고위험·고보상.**

### 안 B. facet별 공용 컨트롤 추출 (권장)
6 facet 각각을 작은 공용 컴포넌트로(`<ModelField>`·`<PromptField>`·`<ToolsField>`·`<DocumentsField>`·
`<LongTermMemoryField>`·`<ShortTermMemoryField>`). 에이전트·노드가 **같은 컨트롤을 조립**(라벨·옵션·
도움말·검증 한 곳). 밀도는 각 컨트롤이 `density`/`variant` prop으로 흡수(에이전트=넉넉, 노드=간결).
- 장점: facet마다 일관(라벨·문구·옵션 drift 0)·**증분·facet별 검증 가능**·PickerGroups/카드 각자 밀도 보존.
  단점: 레이아웃까지 100% 동일하진 않음(각 surface가 배치는 소유). **저위험·중보상, 사용자 "깔끔함"의 실질.**

### 안 C. 정렬만(추출 없음)
두 surface를 라벨·옵션·순서만 일치시키고 컴포넌트는 안 뽑음. 최저 위험이나 DRY 0(코드 중복 잔존) — 반려 후보.

## 권장 및 근거

**안 B 권장.** 269·245 교훈("한 자료구조가 두 축 겸하면 독립제어 불가"의 UI판): facet을 **작은 단위로
쪼개** 각자 일관시키면, 큰 리팩터 없이 "정돈된 UI"(사용자 미감 기준=신뢰)를 얻는다. 안 A는 PickerGroups
스케일과 카드 간결성 충돌을 한 컴포넌트가 떠안아 오히려 한쪽을 훼손할 위험(design-focus-before-layout
메모리 — 배치 통일을 진단 없이 밀면 안 됨). 안 B는 facet별로 "집중 대상→가림→배치"를 개별 판단.

**비대칭 해소 방침(안 B 기준):**
- **문서**: 노드도 에이전트처럼 문서를 **별도 facet**로 승격(도구 접힘 해제) — 개념 일치. 저장은 노드 tools에
  `search_documents__<컬렉션>` 유지(268 P1 무회귀), UI만 분리 표기. (또는 반대로 에이전트도 접기 — 결정 필요.)
- **단기 기억**: 에이전트 폼에서도 세부 ③ → **장기 기억 옆**으로 이동(269 과도기 어긋남 해소). 단기/장기가
  한 "기억" 구획에 함께.
- **프롬프트**: 노드=직접작성 유지, 에이전트=페르소나 선택 유지(성격이 다름 — 강제 통일 안 함). 공용
  컨트롤은 "프롬프트 원천"을 prop으로(select vs textarea) 흡수하거나 별개 유지.

## 확정된 결정 (사용자 검토 완료)

1. **[확정] 안 B — facet별 공용 컨트롤**: 큰 리팩터 없이 facet마다 일관. PickerGroups/카드 밀도는 각자 보존.
2. **[확정] 범위 = 기억 구획부터**: 271은 **단기+장기 기억 공용 컨트롤**만. 나머지 facet(모델·프롬프트·
   도구·문서)은 후속 스펙(272+). 기억이 269·270의 직접 후속이라 가장 자연스러운 첫 조각.
3. **[확정] 에이전트 단기 기억 이동**: 세부 ③ → 장기 옆 "기억" 구획으로(269 과도기 어긋남 해소).
4. **[보류→후속]** 문서 facet 승격은 이번 범위 밖(도구 facet 다룰 때 함께, 272+).

## 이 스펙의 범위 (기억 facet 공용화)

- **공용 컨트롤 추출**: `<ShortTermMemoryField>`(단기=historyDepth Select)·`<LongTermMemoryField>`(장기=mem0).
  라벨·옵션·도움말을 **한 곳**에 정의 → 에이전트·노드 drift 0. 269가 단기(세션)을 뺐으므로 장기는 이제
  **단일 옵션**(장기 기억 mem0)이라 에이전트 PickerGroup(기억)도 간결 토글/Select로 정합 가능.
- **에이전트 폼**: 단기 기억을 세부 ③ → **"기억" 구획**(장기 옆)으로 이동. 단기/장기가 한 자리에서 읽힘.
- **노드 카드**: 이미 단기(270)+장기(268)가 카드에 공존 → 같은 공용 컨트롤로 교체(표기 일치).
- **밀도**: 컨트롤이 `variant`/`compact` prop으로 흡수(에이전트=넉넉·노드=간결).

## 완료 조건 (측정 가능)

- 단기·장기 기억 라벨·옵션이 **에이전트·노드에서 동일**(정의 1곳 — 공용 컨트롤에서 grep 시 중복 0).
- 에이전트 폼에서 **단기 기억이 "기억" 구획**(장기 옆)에 위치(세부 ③에서 사라짐, e2e 단언).
- 무회귀: 저장 payload·백엔드 **무변경**(UI 재배치만) — 기존 에이전트·노드 저장 왕복 GREEN(historyDepth·
  memories 값 불변).
- tsc 0·모바일 오버플로 0(ui-audit 관련 화면).

## 검증 (사다리 3단)
- 단위/타입: 공용 컨트롤 props·옵션 파생 순수함수.
- e2e: 에이전트 폼·노드 카드 양쪽에서 단기/장기가 같은 라벨·옵션·저장 왕복(기능적 — 실제 저장·재로드로
  historyDepth·memories 불변 단언).
- 적대(codex): 추출이 저장 payload를 바꾸지 않는지, 단기 이동이 historyDepth 배선을 안 끊는지, 밀도 prop이
  한 surface를 훼손 안 하는지.

  없음(이동)·단기 컨트롤 쓰기 배선(요약 40 반영)·노드 카드 공용 컨트롤·저장 왕복(historyDepth 40·
  memories 보존). 회귀: 269 e2e(공용 컨트롤 옵션에 맞게 갱신)·270 e2e(노드 per-node 대화 [0,1,2])·
  268 e2e(노드 장기 공용 컨트롤 회상 캐시) ALL GREEN. tsc 0.
- **적대(codex)** — 2건 Low, 처리:
  - **[Low·수정] 단기가 기억 소비게이트에 결합**: `surfaceVisible('기억')`가 단기(historyDepth)까지 가려
    memories 미소비 커스텀 impl서 단기 편집 불가. 단기=모델 컨텍스트라 **항상 렌더**, 장기만 게이트로 분리.

  - 확인(수확): historyDepth/memories/memoryQuery 배선·ephemeral 미선택-잠금·직접형 한정 이동(내장 4종
