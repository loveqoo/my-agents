# 스펙 228 — 허용 호스트: SSRF 설명 추가 + 레이아웃 정돈

## 배경 (사용자 지적 2026-07-08)

1. "SSRF에 대해 경고하지만 정작 SSRF에 대한 설명은 없네." — 경고 배너·부제가 "SSRF 예외"라 하는데
   정작 SSRF가 무엇인지 설명이 없어, 비기술 관리자는 왜 위험한지 모른다.
2. "스타일과 컴포넌트 배치를 수정해야 할 것 같아."

## 변경 (admin/src/admin/views/AllowedHostsView.tsx)

### SSRF 평이한 설명
- 경고 Alert description을 문자열 → JSX 2단락으로: (1) **SSRF(Server-Side Request Forgery, 서버 측 요청
  위조)** 정의 — 공격자가 서버를 속여 내부망·클라우드 메타데이터(169.254.169.254)·로컬 서비스로 요청을
  보내게 만드는 공격, 그래서 서버가 사설·루프백·메타데이터 대역을 **기본 차단**한다. (2) 여기 등록한 host는
  그 차단의 **예외** — 신뢰 대상만.

### 레이아웃
- **추가 시각**: raw `new Date().toLocaleString()`("2026. 7. 3. 오후 7:31:28") → **`fmtDateTime`**("7월 3일
  19:31:28"). 앱 포맷터 통일 + 감사 정밀도(보안 예외 개방 시각).
- **호스트 추가 폼**: 짧은 두 필드(호스트·메모)를 **나란히**(flex gap 24, wrap) — 세로 여백 압축.

## 검증
- 브라우저: SSRF 풀네임·"서버 측 요청 위조"·"기본 차단"·"메타데이터" 노출, 추가 시각에 '오후' 없고 초 포함
  (fmtDateTime), 폼 두 필드 나란히. tsc 0.

## 비고
- 교훈: 보안 경고는 **왜 위험한지(위협 모델)**를 평이하게 함께 설명해야 관리자가 옳게 판단한다 — 용어만
  던지면 경고가 공허하다([[explain-plainly-not-one-sided]]).
- 시각 표기: 감사성 목록(보안 예외 개방)은 fmtDateTime([[verification-ladder-three-rungs]]·회고 211).
