# 289 — 연동 계약 정비: 서버가 기억하고, 서버가 파생하고, 상태는 미리 보인다

## 배경

스펙 288 조합 스위트가 실측으로 드러낸 "미문서 계약" 중 3건은 **외부 클라이언트가 연동을 포기하게
만들 수준의 전제조건**이다(사용자 판단, 2026-07-11):

1. 대화 히스토리를 클라이언트가 매 턴 전부 재전송해야 한다(안 하면 단기 기억이 조용히 무동작).
2. 노드형의 도구·문서·기억 **풀**을 클라이언트(편집 폼)가 계산해 저장해야 한다(안 하면 노드 도구가
   조용히 미바인딩 — learning 151).
3. 위임 가능 여부(대상 서빙 상태)를 실행해 봐야 안다(토큰만 소모, 신뢰 없음).

업계 관행 기준: 원시 모델 API(OpenAI Chat Completions류)는 히스토리 재전송이 표준이지만, **에이전트
플랫폼**(OpenAI Assistants/Responses, A2A contextId, LangGraph thread)은 "세션 ID + 새 메시지"가
계약이다. 우리는 플랫폼을 표방하므로 플랫폼 계약으로 승격한다. 서버는 이미 대화를 전부 영속하고
있어(세션·메시지 행) 갭은 "저장한 것을 메인 경로가 읽게 하는" 크기다.

## 목표 (완료 기준 — 측정 가능)

1. **P1 히스토리 서버 재구성**: `sessionId` + 새 메시지 1개만 보내는 클라이언트가 이전 대화를
   이어받는다 — 조합 스위트에 신규 시나리오(서버 모드 2턴 비밀코드 회수)가 초록.
   기존 클라이언트(플레이그라운드, 대화 전체 전송)는 무회귀 — 기존 31개 시나리오 전판 초록.
2. **P2 노드형 풀 서버 파생**: 편집 폼 없이 **API로만** 만든 노드형(풀 미지정)이 노드 도구·문서·
   기억을 정상 발동 — 스위트 픽스처에서 풀 명시를 제거해도(`vectorTables`/`memories` 삭제) 관련
   시나리오 전부 초록. 저장 입구 전수(생성·초안 저장·오버라이드)는 grep으로 닫힌 집합 확정
   (learning 149 — 자가 열거 금지).
3. **P3 위임 상태 표면화**: (a) 위임 구조 미리보기(그래프)에 미서빙 대상 마커 + "위임 후보에서
   제외" 안내(폼·상세 양쪽), (b) 위임 0건 턴의 trace에 사유(후보 0 — 미서빙/발견 실패) 기록 —
   스위트 신규 시나리오(미서빙 대상 위임 → brokerCalls 0 + 사유 존재)가 초록.
4. 전체: 조합 스위트(기존+신규) 전판 초록 + 스펙 288 "구현 확정" 노트의 해당 항목을 계약 변경으로
   갱신(문서-코드 정합).

## 설계

### P1 — 히스토리 서버 재구성 (chat 메인 경로)

- **판정 규칙(auto — codex 적대 리뷰로 1차안에서 조임)**: 재개에 성공한 소유 세션이고(`sessionId`
  매칭 — 기존 소유권 게이트 그대로, 067/068) **body가 정확히 user 메시지 1개**면 서버 모드:
  `conversation = _load_session_conversation(session) + body.messages`. 그 외 형태(누적 전송 등)는
  전부 클라이언트 관리 모드(body가 진실) — 플레이그라운드는 대화 전체를 보내므로 자동으로 이 모드(무회귀).
  1차안("assistant 부재")은 codex 289 #1~#3이 반증: 빈 배열(재구성분만으로 직전 턴 재실행),
  user-only 누적 클라(이중 카운트), assistant 위조(모드 오판) — "새 턴 1개"가 계약 그 자체라 이 형태로
  판정한다. 명시 플래그는 OUT(모호 사례 실증 전 최소주의).
- 재구성 대화에도 `historyDepth` 절단(_window)은 동일 적용. **노드형도 자동 승계**(사용자 확인
  질문, 2026-07-11): 노드별 대화 창 프록시(270)의 원천이 이 conversation 하나라, 재구성분이
  들어가면 첫 노드부터 모든 노드가 이어진 대화를 본다. 노드의 "단기 안 씀"·"이전 결과만" 설정은
  그대로 우선. 검증=노드형 서버 모드 시나리오에서 trace `historyWindows` 건수>0 단언.
- **소유권 경계(보안)**: 재구성은 "재개 성공" 이후에만 — 타인 sessionId는 기존대로 새 세션 발급
  (열거 오라클 봉인 유지)이라 재구성 자체가 일어나지 않는다. 적대 시나리오로 확인.
- persist 무변경: 현행 persist는 마지막 user 턴+응답만 저장하므로 서버 모드에서도 이중 저장 없음.
- **캐시 레이어는 두지 않는다**(사용자 질문 → 합의, 2026-07-11): 턴 비용은 실모델 추론(5~30s 실측)이
  지배하고 세션 메시지 조회는 ms 수준 — 절약폭 없음. 반면 다중 프로세스(상시 서버·리로드·in-process
  러너·재개 경로)에서 캐시 무효화 실패 = 모델이 낡은 대화를 봄(조용히 틀림). 대신 조회를 **최신
  N개(필요 최대 depth) LIMIT**로 걸어 세션이 자라도 읽기량 상수 고정(노드 "전체 보기"만 전량 폴백).
  재구성 소요 ms를 기록해 실측 — 병목으로 측정되면 그때 캐시 재론(측정 우선, 스펙 160 결).
- 무변경 경로: A2A 서빙(061 — v1 무상태 단발 계약 유지), 승인 재개(이미 DB 재구성), 비영속(세션 없음).

### P2 — 노드형 풀 서버 파생 (저장·오버라이드 입구)

- 파생 규칙(폼 derivePipelinePool과 동일 의미): 노드 `tools`의 서버 접두(`srv__tool` → srv 합집합)
  → `mcps`, 문서 도구(`search_documents__<col>` → col 합집합) → `vectorTables`, 노드 `memories`
  합집합 → `memories`. impl=pipeline일 때 서버가 저장 직전 **재계산·대체**한다(파생 필드는
  denormalization이라 관리자 저작 의미 없음 — merge-preserve 불요 근거 명시).
  민이름(bare, 구저장 'echo'류)은 **전역 유일할 때만** 서버 매칭(codex 289 #4 — 동명 도구가 여러
  서버에 있으면 전부 열려 불필요 MCP 접속. 모호=제외, 런타임 _resolve_tool 모호 스킵(265)과 동일 결).
  `_safe_name` 60자 절단 충돌(codex #5)은 289 밖 전역 네이밍 이슈 — 백로그 등재(부분 방어=모호 fail-closed).
- 입구: ① `POST /agents`(생성) ② 초안 저장/게시 경로 ③ chat `overrides.nodes`(오버라이드에 nodes만
  있고 풀이 없으면 서버가 파생 — API 오버라이드 호출자도 안전). 입구 열거는 config를 쓰는 지점
  grep 전수로 확정.
- 폼은 그대로 둔다(같은 규칙의 이중 파생 = 무해·수렴). 비-pipeline impl 일반화는 OUT.

### P3 — 위임 상태 표면화

- **정적(사전)**: DelegationGraph(257)에 대상의 서빙 상태 마커 — 미서빙(activeVersion 없음)이면
  회색+「미서빙 — 위임 후보에서 제외」. 조율형 폼 미리보기·에이전트 상세 양쪽 자동 승계(공용 컴포넌트).
- **동적(사후)**: orchestrate discover 관측에 후보 수를 남기고, 위임 0건이면 trace에 사유
  (`delegation: {candidates: 0, reason: "no-candidates|no-serving|no-lexical-match"}` 수준) —
  인스펙터에서 "왜 위임이 안 됐나"를 실행 직후 확인.

## 검증

- 조합 스위트 신규 시나리오 4+: 서버 모드 2턴 회수 / 클라 모드 무회귀 대조 / 타인 세션 재구성 불가
  (적대) / API-only 노드형 도구 발동(픽스처 풀 제거) / 미서빙 위임 사유. 기존 전판 무회귀.
- UI(P3a)는 browser e2e(verify)로 마커 존재·문구 단언.
- codex 적대 검증: 계약 경계(세션 소유권 재구성 유출·auto 판정 우회·풀 파생의 권한 상승 여부 —
  파생은 노드 참조의 합집합이라 필터 대상=자기 자신, 구조적 비상승 논거 검증).

## OUT (이번에 안 함)

- 비-pipeline impl의 풀 파생 일반화, lexical 발견을 시맨틱 발견으로 교체(별도 방향).
