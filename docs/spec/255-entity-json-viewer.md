② 플레이그라운드 인스펙터의 RAG 검색 이력 히트도 같은 처리 필요.

## 변경

- **EntityFields 공용화**: parseEntityText+2열 표+빈 필드 한 줄을 admin/EntityFields.tsx로 추출 —
  검색 시험(RetrievalTestPanel)과 인스펙터 HitCard가 공유(두 벌=드리프트).
- **백엔드 프리뷰 개행 보존**(runtime._hits_detail): "\n"→" " 치환 제거 — 라인 경계가 있어야
  구조화 렌더 가능. 평문 청크는 pre-wrap이라 무해. 캡·비밀 마스킹 규율은 그대로.

## 후속 — 멀티라인 필드 값이 원시 폴백되던 버그 (사용자 보고, 2026-07-09)

**증상**: 플레이그라운드/검색 시험에서 RAG 엔티티 히트가 "예전처럼"(원시 텍스트 블롭) 나오는 경우.
**근인**: `parseEntityText`가 **한 줄이라도 `key: value` 형식을 벗어나면 통째 null 반환**(문서 청크
방어). 그런데 위 "개행 보존"(preview-newline)이 들어오면서 `description` 같은 **멀티라인 필드 값**의
연속 줄이 `key:` 형식이 아니라 파서가 통째 포기 → 원문 폴백. 개행을 살린 그 수정이 파서의 옛 가정
(모든 줄=한 필드)을 깬 것 — 데이터를 더 보존한 변경이 하류 파서를 깼다.
**수정**: 연속 줄(비-`key:`)을 **직전 필드 값의 다음 줄로 이어붙인다**(멀티라인 값 복원). 시작 전이거나
이어붙일 필드가 없으면(문서 청크) 여전히 null(원문). 연속 줄 허용으로 헐거워진 만큼 **필드 2개 미만은
엔티티 아님**으로 조여 "우연히 word:로 시작하는 문서"를 방어. EntityFields 값 span에 `whiteSpace:
pre-wrap` 추가(개행 표시).
**검증**: parseEntityText 단위 4케이스(멀티라인→구조화·문서→원문·단일라인 무회귀·word:문서→원문 가드)
+ **브라우저 e2e**(`shot-entity-multiline-256.mjs`): 멀티라인 description 엔티티 인제스트→검색→구조화
렌더("빈 필드:" 신호·3줄 값 정렬·meta JsonTree) 실측 4/4. admin tsc 0.
**교훈**: "더 많이 보존하는" 수정(개행 살리기)이 그 데이터를 소비하는 파서의 옛 형태 가정을 깰 수 있다 —
데이터 형태를 넓히면 소비자 전수 점검.
