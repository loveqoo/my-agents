# 315 — 파이프라인 실행 노드 도구 루프 상한 + 우아한 마무리

## 배경 / 증상 (사용자 보고 + 실측)

`plan-execute-demo`에 "스트리밍 UI 최신 동향을 검색해줘"라고 하면 오래 멈추고 답이 이상하게 나온다.

실측(trace):
- 계획 노드는 정상(1~2초에 3단계 계획 출력).
- **실행 노드가 `wiki_search`/`wiki_page`를 14회 반복 호출**(수렴 실패) — 매 반복이 35B 모델 생성
  (2.5~10초). ~55초에 **모델 서버(rapid-mlx)가 연결을 끊음**(`peer closed connection without sending
  complete message body`) → 답이 불완전/이상.

## 근본 원인

1. **"최신 동향"은 위키피디아가 잘 답 못 하는 개방형 질의** — 모델이 만족스러운 근거를 못 찾아 계속 재검색.
2. **실행 노드 ReAct 루프에 상한이 없다** — `pipeline.py`의 `실행→실행__tools→실행` self-loop가
   LangGraph 기본 recursion_limit(25)에만 의존. 모델이 멈출 때까지 반복.
3. 누적된 검색 결과로 **컨텍스트가 커지자 모델 서버가 연결을 끊어** 답이 깨짐.

※ 스펙 314(자동 기억 저장 비차단)와 무관 — 파이프라인·도구·모델 경로 미변경. 기존부터 있던 문제
(사실 질문은 1~2회에 수렴, 개방형 질의에서 러너웨이).

## 사용자 지적

계획 노드는 프롬프트에 "wiki_search로 찾으라"고 써 있으나 tools=[] — **관찰은 맞으나 원인 아님**.
계획 노드는 실행이 아니라 계획만 세우는 노드라 도구가 불필요하고, 실제 실행 노드엔 도구가 붙어 14회
호출됐다(전부 ok). 멈춤은 "도구 미추가"가 아니라 실행 노드 루프 러너웨이.

## 결정 (사용자 승인: 루프 상한 + 우아한 마무리, 전 파이프라인 대상)

- **도구 루프 상한** `_TOOL_ROUNDS_CAP=6`(라운드=도구 호출을 낸 모델 턴 수). 상한 도달 시 그 노드는
  **도구를 떼고(unbound 모델)** 답을 강제 → tool_calls를 못 내 `_route`가 다음 노드로(루프 종료).
- **우아한 마무리**: 상한 시 시스템 프롬프트에 `_CAP_NUDGE`("이미 여러 번 검색했습니다. 추가 도구 호출
  없이 지금까지 찾은 것으로 답하고, 확인 안 된 건 정직하게 밝히세요") 주입 → 에러/연결끊김 대신 정직한 답.
- **라운드 계산**은 상태 스키마 변경 없이 순수 계산(`_count_tool_rounds`): 메시지 꼬리를 거꾸로 훑어
  연속된 `[AI(tool_calls) ← ToolMessage]*` 구간의 tool_calls AI 개수. 도구 없는 일반 메시지(앞 노드
  결과·사용자 입력)를 경계로 멈춤 → 노드 간 carry에도 안전.

## 범위 밖 (OUT)
- 그래프 recursion_limit 백스톱: 노드별 캡이 수렴을 강제하므로 불필요(전역 config가 타 플로우에 영향).
- 모델 연결 끊김 자체의 재시도/처리: 캡으로 컨텍스트가 작아져(≤6회) 끊김 확률이 크게 줄어 근인 해소.
  잔여 끊김은 기존 에러 프레임 경로로 표면화(조용한 실패 아님).
- 계획 노드 프롬프트-도구 표기 정합(데모 seed): 기능 무해라 미변경(설명만).
- 캡 값의 per-node 커스터마이즈: YAGNI(모듈 상수 6, 필요 시 후속).

## 검증
- **단위(결정적)**: `tests/verify_315_tool_loop_cap.py` — 항상 tool_call 내는 모델(수렴 실패)도 도구
  호출이 6회로 상한·상한 후 에러 없이 최종 답(강제 수렴)·조기 수렴 모델은 상한 전 정상 종료(무회귀).
- **실 인프라**: plan-execute-demo에 같은 질의 → 이전 180초+/연결끊김이 **27초 정상 완료**(도구 6회·
  끊김 0·최종 답 스트림)로 정상화.
- **적대(codex)**: 라운드 계산의 노드 간 경계·clean 컨텍스트·병렬 tool_calls 오카운트 여부.

## codex 적대 검증 → 수정
- **P1 캡 airtight 아님**: 캡 발동 시 `active=model`(unbound)로 바꾸지만, 느슨한/커스텀 provider가
  unbound인데도 tool_calls를 내면 `_route`가 다시 tools로 보내 캡을 넘길 수 있음. → **`_force_final_if_capped`**:
  캡 응답에 tool_calls가 있으면 떼어 강제 종료(본문 비면 정직 폴백 문구). verify_315 T4(rogue unbound)로 회귀.
- **경계(수용)**: 병렬 tool_calls는 라운드 1로 세므로 "도구 실행 총량"은 캡 안 됨(최대 ~6×N). 캡은
  라운드(=비싼 모델 턴)에 거는 게 목적 — 멈춤의 원인인 모델 생성 반복을 막으므로 정직 경계로 수용.
- P0 0. 노드 간 오카운트·clean·경계값(off-by-one)은 전부 "막힘"으로 확인.
