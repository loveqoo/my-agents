# 368 — 채팅 핫패스 빌드 비용 측정 하네스 + 베이스라인 (스펙 367-A)

## 왜

스펙 367(버전 모델 재설계)의 D(복합 버전 키 캐시)는 "매턴 그래프 재빌드가 비싸다"는 전제 위에 선다.
그 전제를 **숫자로 고정**해야: (1) 캐시 설계가 실제 병목을 겨냥하고, (2) D 완료 시 前/後 비교로 이득을
증명한다. 측정 자체가 자산 — 하네스는 재실행 가능하게 남긴다(사용자 지시 2026-07-15).

## 무엇을

### 계측 (핫패스 단계별, 구성 비용 분해)
`chat.py _build_turn_runtime`의 하위 단계를 perf_counter로 재서 `turn["build_ms"]`에 싣고,
`_final_trace`가 `trace.buildMs`로 노출(SSE trace 프레임 → 하네스·인스펙터 겸용):
- `memory` — `_memory_inputs`(회상: 매턴 정당한 입력, 캐시 대상 아님 — 대조군)
- `mcp` — `build_mcp_tools`(**매턴 MCP 실연결+도구 목록 조회** — 캐시 후보 1순위)
- `rag` — `_rag_tools_for`(도구 래퍼 생성)
- `broker` — `build_broker`(+pipeline이면 agent_capabilities)
- `graph` — `impl.build_graph`(모델 클라이언트 신규+compile — 캐시 후보)
- `total` — `_build_turn_runtime` 전체

### 하네스 (`tests/measure_build_hotpath.py` + `make perf-build`)
실서버(8000)에 로그인 → 축별 에이전트 생성 → 채팅 N턴 → trace.buildMs 수집 → 표 출력 → 정리(삭제).
- **MCP 축**: 바인딩 0개 / 1개(calc-tools) / 3개(calc-tools·local-tools·web-fetch — 시드 served 전부).
- **동시성 축**: 순차(1) vs 동시(8) — asyncio 동시 요청으로 경합 시 빌드 비용 변화.
- 모델=mock-llm(결정적·모델 지연 배제 → 빌드 비용이 순수하게 드러남).
- 출력: 축별 p50/p95(ms) 표 — total과 단계별 분해.

## 완료 조건 (수치)

- **C1** trace.buildMs가 매 완료 턴에 실림(단계 5키+total) — 실측 1턴으로 확인.
- **C2** `make perf-build` 한 명령으로 표 재현(축: MCP {0,1,3} × 동시성 {1,8}).

### 읽기 (367-D 우선순위를 재편)

1. **매턴 빌드 비용 ≈ MCP 디스커버리 그 자체다.** 웜 상태에서 graph(모델 클라이언트+compile)는 ~1.6ms에
   불과 — 예상했던 "compile-매턴·클라이언트-매턴"은 웜에선 사실상 공짜(콜드 첫 턴만 ~137ms, lazy import).
   반면 MCP 연결+도구 목록 조회가 서버당 ~11ms(순차)로 빌드 비용의 사실상 전부.
2. **동시성이 MCP 비용을 ~5배 증폭한다.** 동시 8에서 mcp=1: 12→59ms, mcp=3: 34→166ms(p95 201ms).
   서버 수 × 동시성으로 곱해지는 구조 — 트래픽 우려가 정확히 여기서 현실화된다.
3. **따라서 367-D의 1순위 = MCP 도구 목록 캐시**(agent_version 키). 그래프/클라이언트 캐시는 부차
   (웜 ~1.6ms 절감뿐). 회상·브로커는 이 축에선 0(대조군 역할 확인).
