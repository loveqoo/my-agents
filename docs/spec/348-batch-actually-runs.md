# 348 — 배치 가동 경로 (설치 ≠ 가동: 청소부에게 손을 달아준다)

## 왜

스펙 346에서 TTL 스윕을 만들고 cron(`0 * * * *`)까지 설정했는데 — **그 cron을 읽어 실행할 프로세스를
아무도 안 켠다.** 실측: `batch_runs` **0행**(이 서비스가 생긴 이래 배치 잡이 **한 번도 안 돌았다**).

- `uv run batch serve` CLI는 **완성돼 있다**(스펙 038). 문제는 아무도 그걸 켜지 않는다는 것.
- API lifespan(`main.py`)은 스케줄러를 안 켠다. Makefile·docker-compose에도 없다.
- 그래서 **세션 정리·메모리 통합·체크포인트 스윕이 전부 죽은 코드**다(설정만 켜져 있고 손이 없다).

memory `installed-guard-isnt-covering-guard`("보안장치 설치 ≠ 적용 범위 전체 덮음")의 재발이다.
이번엔 더 나쁘다 — **장치가 아예 안 돌고, 안 돈다는 사실이 어디에도 안 보인다.**

## 설계

### 1. 손을 단다 — **인프로세스 스케줄러 + Postgres advisory lock**
API lifespan이 스케줄러를 켠다(`BATCH_SCHEDULER=inproc` 기본). 별도 프로세스(`batch serve`)를 띄우는
운영도 그대로 지원한다(`BATCH_SCHEDULER=off`로 앱 내 스케줄러를 끄면 됨).

**advisory lock이 핵심**: 워커/레플리카가 여럿이어도 **정확히 하나만** 스케줄러가 된다
(`pg_try_advisory_lock`). 락을 못 잡은 프로세스는 잡을 등록하지 않는다 —
크론 이중 발화(같은 잡이 N번 삭제 실행)를 구조적으로 막는다. 백로그 k8s P1③(좀비 스윕 lease)의
같은 문제를 배치 축에서 먼저 갚는다.

- `--reload`/롤링 재시작으로 락 보유 프로세스가 죽으면 락은 자동 해제(세션 종료) → 남은 프로세스가
  **주기적 재시도**(60초)로 승계한다. "한 번 실패하면 영영 스케줄러 없음"이 되지 않게.

### 2. 안 돌면 **보이게** — 상태를 표면화
`GET /admin/batch/scheduler` → `{mode, leader, jobs:[{name, next_run_time}], last_runs:{...}}`.
admin 배치 화면 상단에 배너: **가동 중(다음 실행 시각)** 또는 **미가동(경고)**.
청소부가 죽어 있으면 **화면이 그렇게 말한다** — 조용한 무동작이 불가능해진다.

## 완료 조건 (수치)

- **B1** 부팅 후 스케줄러가 **리더**로 뜨고, cron이 설정된 잡이 등록된다(`next_run_time` 존재).
- **B2** **실제로 발화한다**: cron을 1분 주기로 두면 90초 내 `batch_runs`가 증가한다(살아 있는 손의 증거).
- **B3** **이중 발화 없음**: 두 번째 프로세스는 리더가 아니며 잡을 등록하지 않는다(advisory lock).
- **B4** 리더가 죽으면 다른 프로세스가 **승계**한다(락 재시도).
- **B5** admin 배치 화면에 스케줄러 상태가 뜬다(미가동이면 경고).
- 무회귀: 게이트(347) · lint/mypy/tsc.

## 결과 (2026-07-15 실행)

- **인프로세스 스케줄러 + advisory lock**: API lifespan이 켠다(`BATCH_SCHEDULER=inproc` 기본).
  락을 못 잡은 프로세스는 잡을 등록하지 않는다 → 워커·레플리카가 여럿이어도 **정확히 하나만 발화**
  (크론 이중 발화 = 삭제 잡이 워커 수만큼 실행되는 파괴 배수를 구조적으로 차단). 리더가 죽으면 락이
  자동 해제되고 남은 프로세스가 60초 주기 재시도로 **승계**한다.
- **설정 즉시 반영**: cron을 화면에서 바꾸면 `reload_schedules()`가 스케줄러에 즉시 재적재한다.
  (이게 없으면 "설정은 켰는데 다음 재시작까지 안 돎"이라는 **같은 함정의 축소판**이 된다.)
- **가동 상태 표면화**: `GET /admin/batch/scheduler` + 배치 화면 상단 배너 —
  "자동 실행 중 — 이 서버가 스케줄러입니다 (등록 1개) / 다음 실행: checkpoint-cleanup → …".
  스케줄러가 꺼져 있으면 **경고 배너**가 뜬다(조용한 무동작 불가능).
- **VERIFY348_OK 5/5** — 리더 가동 · 잡 등록(next_run_time) · **실제 발화**(cron 매분 → `batch_runs`
  2 → 3, **0행에서 벗어남**) · 이중 발화 차단(2번째 프로세스는 락 실패) · 락 실재(승계 근거).
  UI: 배너 실측 통과. 무회귀: 게이트 347 · lint/mypy/tsc 클린.

### 함정 하나 더 밟았다 — **낡은 프로세스가 응답하고 있었다**
B2(실제 발화)가 처음엔 실패했다. 원인은 코드가 아니라 **재기동 실패**였다: 이전 uvicorn이 포트를
붙들고 있어 새 프로세스가 `Address already in use`로 죽었고, **옛 코드가 계속 응답**하고 있었다
(그래서 재적재 훅이 없는 것처럼 보였다). 포트 기준으로 죽이고(`lsof -ti:8000 | xargs kill -9`)
**부팅 로그에 새 코드의 흔적**("배치 스케줄러 리더 — 등록 작업 1개")이 찍히는지로 확인한 뒤에야
측정이 진실을 말했다. 스펙 346의 "계측이 거짓말했다"와 **같은 형태**(이번엔 계측 대상 자체가 낡음).
