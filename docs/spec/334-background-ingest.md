# 334 — 인제스트 배경 잡화 + 행 캡 완화(사용자 승인 수치)

## 배경 / 결정 (사용자, 2026-07-14)

- 스펙 149의 행 수 캡 5,000이 **미승인 수치**였음을 사용자가 지적("저는 이 수치를 승인한 적
  없습니다") — 회고: 사용자 가시 한계는 승인 항목(메모리 등재).
- 함께 확인된 사실: 인제스트는 동기 요청이라 (a) 캡 없인 한 요청이 임베딩 N회를 붙듦,
  (b) CPU 동기 구간(PDF 추출·행 파싱·검증)이 이벤트 루프를 순간 정지시킴.
- **사용자 결정: 배경 잡화로 캡 대폭 완화** — 업로드 즉시 접수(201)+백그라운드 인제스트,
  행 캡 기본 **50,000**(env `RAG_ENTITY_MAX_ROWS`)으로 상향.

## 설계

### C1. 업로드 = 접수, 인제스트 = 배경
- `POST /documents`: 지금처럼 Document(status=parsing)+blob 영속 후 **즉시 201 반환**(청크 없이).
  파싱→검증→임베딩→적재는 `background.spawn` 잡으로. Document.status(parsing|embedding|ready|error)
  전이는 **기존 상태 축 그대로**(UI 태그도 기존 — 상태 기계가 이미 이걸 위해 있었다).
- 배경 잡 안에서 **CPU 동기 구간은 `asyncio.to_thread`**(PDF 추출·행 파싱·스키마 검증·청킹) —
  이벤트 루프 순간 정지(질문 2의 스파이크)도 함께 해소.
- 실패는 기존 `_mark_ingest_error` 재사용(status=error+사유 박제, no silent death).
- 엔티티 행 계약 위반: 지금은 400 즉시 거절(문서 행 안 남김) — 배경화 후엔 400을 줄 수 없으므로
  **파싱·검증까지는 동기 유지**(빠름, to_thread로 스파이크만 회피)하고 **임베딩+적재만 배경**.
  → 형식 오류는 지금처럼 업로드 응답에서 행 번호와 함께 400(계약 보존), 오래 걸리는 건 임베딩뿐.
- 251(비용) 가드: 컬렉션당 동시 인제스트 잡 직렬화는 기존 `_persist_chunks` 조건부 UPDATE가
  재인덱싱 경합을 이미 봉인 — 동시 업로드 자체는 허용(집계 원자 증분).

### C2. 임베딩 배치화 (캡 상향의 전제)
- 현재 `_embed_chunks`는 전 청크를 **한 HTTP 요청**으로 보냄 — 5만 행이면 본문이 거대해 실
  provider가 거부. **배치 분할**(기본 128행/호출, env `RAG_EMBED_BATCH`) 후 순서 보존 병합.
  재인덱싱(`_do_reindex`)·편집(331/332)도 같은 헬퍼라 함께 견고해짐.

### C3. 캡 상향 + 표면화
- `ENTITY_MAX_ROWS`: 5,000 → **기본 50,000**, env `RAG_ENTITY_MAX_ROWS`로 조정 가능.
- 업로드 안내문에 한계 명시(파일당 행 수·크기) — "거부 순간에만 보이는 한계" 해소.

### C4. 재시작 좀비 스윕
- 배경 임베딩 중 서버 재시작 → status=embedding 고아. 부팅 스윕(eval 좀비 스윕 패턴 미러):
  parsing/embedding 문서를 error("서버 재시작으로 중단 — 다시 업로드하세요")로 박제.
  (blob은 남아 있으므로 향후 "재시도" 씨앗 — OUT.)

### C5. 프론트
- 업로드 핸들러: 201 즉시 "접수됨 — 처리 중" 토스트, 목록 재조회. **처리 중 문서가 있으면 목록을
  폴링(5초)**해 상태 전이(parsing→embedding→ready/error)를 자동 반영(에벌 문제집 폴링 결).
