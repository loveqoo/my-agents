# 352 — mem0 기억: 도달 불가 고아 회수 (마지막 누수 테이블)

## 왜

`mem0_memories`는 자원 대장의 **마지막 `leaking`**이다. 턴마다 장기기억이 추가되는데
회수 경로는 `memory-consolidation` 배치뿐이고, 그건 **임계치 기본 NULL = OFF**다(게다가 통합은 LLM이
필요해서 모델 미설정이면 no-op). 즉 실질 회수 0.

**그런데 여기서 "다 지우면 된다"는 답은 틀렸다.** 기억은 제품의 **토대 기능**이고, 살아있는 유저의
기억을 나이나 개수로 잘라내면 **회수가 기능을 죽인다**(스펙 351의 추세 앵커와 같은 교훈).

## 통찰 — 도달 불가(unreachable)만 지운다

회상은 **오직 세 축**으로만 일어난다(`memory/backend.py`의 `SCOPE_AXES`):

| 축 | 값 | 살아있음의 근거 |
|---|---|---|
| `user_id` | `str(user.id)` | `"user"` 테이블에 그 행이 있음 |
| `run_id` | `sessions.session_id`(`sess-…`) | `sessions`에 그 행이 있음 |
| `agent_id` | `agents.agent_id`(`agt-…`) | `agents`에 그 행이 있음 |

한 기억 행이 지닌 축이 **전부 죽은 소유자**를 가리키면, 그 행은 **어떤 질의로도 영영 회상되지
않는다** — 벡터 공간만 차지하는 유령이다. 유령만 지운다. **살아있는 유저의 기억은 한 행도 안 지운다.**

### 유령을 만든 건 우리 청소부들이다

`mem0_memories`는 mem0 소유의 별도 pgvector 테이블이라 **우리 테이블과 FK가 없다.** 그래서
`user-cleanup`이 유저를 지워도, `session-cleanup`이 세션을 지워도, 관리자가 에이전트를 지워도
그 기억은 그대로 남는다. 스펙 348로 청소부들이 **실제로 돌기 시작했으니** 이제부터는 유령이
꾸준히 생산된다 — 351(`batch_runs`)과 같은 가족: **청소부의 발자국도 치워야 한다.**

## 설계 — 배치 잡 `memory-cleanup`

**삭제 조건(셋 다 만족해야 함)**

1. 행이 지닌 축이 **하나 이상** 있고, 그 축들이 **전부 죽었다**(위 표의 근거로 판정).
2. `payload->>'created_at'`이 **유예 기간**보다 오래됐다 — `memory_orphan_grace_days`(기본 **7일**).
3. `created_at`을 못 읽으면(없음/포맷 이탈) **보존**한다(346의 "나이 불명은 안 지운다" 규칙 재사용).

**유예 기간이 왜 필요한가(비자명)**: `persistHistory=false` 대화나 서비스 프린시펄(API 키) 턴은
`sessions` 행을 만들지 않는데도 기억은 남긴다. 세션 행이 없다고 즉시 유령으로 판정하면
**살아있는 대화의 기억을 지운다.** 유예가 그 창을 막는다(유저가 로그인 상태면 `user_id` 축이 살아
있어 애초에 보존되고, 유예는 `user_id`가 없는 경로까지 덮는 두 번째 그물).

- 파괴적 노브 바닥(learning 037): 유예 <1이면 **잡 비활성**(0 = 즉시 삭제 아님).
- dry-run 지원 · cron 기본 매일 05:30(다른 청소부들 뒤).
- payload JSONB 스키마 결합은 `memory/` 패키지 안에 **격리**한다(`mem0_backend.list_page`와 같은 규율) —
  배치 잡에 SQL을 흩뿌리지 않는다.

## 완료 조건 (수치)

- **M1** 죽은 유저의 기억 삭제 · **살아있는 유저의 기억은 0건 삭제**(같은 나이여도).
- **M2** `user_id`가 죽었어도 **`run_id`(세션)나 `agent_id`가 살아 있으면 보존** — 한 축이라도 살아
  있으면 회상 가능하므로 유령이 아니다.
- **M3** 유예 기간 내 행은 **0건 삭제**(살아있는 미영속 대화 보호).
- **M4** `created_at` 불명 행은 **0건 삭제**.
- **M5** dry-run은 세기만 하고 삭제 0.
- **M6** 유예 <1이면 잡 비활성(delete-all 금지).
- **M7** 삭제가 판정과 **한 문장** — 판정↔삭제 사이에 소유자가 되살아나도 안 지운다(codex P1 TOCTOU).
- **M8** 게이트: `mem0_memories`의 `leaking` 해소 → **스코어보드 1 → 0**(캠페인 완료 조건).

### 적대 검증(codex)이 잡은 것 — 셋 다 실제 결함이었다

1. **P1 TOCTOU(고침)**: `SELECT id` → `DELETE WHERE id = ANY(:ids)`로 나눠 놨더니, **그 사이에**
   유저·세션·에이전트가 되살아난(복구·import·수동 작업) 기억을 **되살아난 뒤에 지운다.**
   → 삭제를 **판정과 한 문장**으로 합쳐 삭제 시점에 조건을 재평가하고, `RETURNING`으로 **실제 rowcount**를
   센다(`len(ids)` 추정 아님). 구조 회귀는 M7 핀이 막는다.
2. **P3 대량 삭제(고침)**: 후보 전체를 앱 메모리에 올려 배열 파라미터 하나로 지우면 유령이 수십만일 때
   터진다 → `LIMIT` 배치 루프.
3. **P2 보조 테이블 사각(게이트로 승격)**: mem0가 설정에 따라 만드는 보조 테이블(`*_entities`)은
   `models.py`에 없으니 **대장이 아예 못 본다**. 이 DB엔 실재하지 않았지만(측정), 사각 자체가 문제라
   게이트에 **G5**를 추가했다 — **살아있는 DB의 public 테이블 집합**을 직접 읽어 대장과 대조한다.
   이제 라이브러리가 몰래 만든 테이블도 분류를 강요당한다.

또 하나(fast-worker가 발견): 내 잡만 dry-run 상태를 `ok`로 반환해 **다른 8개 잡과 계약이 어긋나** 있었다
(화면이 잡별로 분기할 뻔) → `dry_run`으로 통일.

## OUT — 정직하게 남기는 것

- **살아있는 유저 기억의 상한은 이 스펙이 정하지 않는다.** 그건 사용자 자산(`messages`와 같은 부류)이고,
  개수/나이 상한은 **제품 가시 한계라 관리자 승인 사항**이다. 지금의 회수 수단은 (a) 유저가 화면에서
  삭제, (b) `memory-consolidation` 배치(관리자가 임계치를 켜면 동작), (c) 이 스펙의 고아 회수.
  스코어보드 0은 **"모든 테이블이 회수 경로 또는 정당한 유저 자산으로 분류됐다"**는 뜻이지
  "무한 증가가 없다"는 뜻이 아니다 — 그 구분을 흐리면 대장이 거짓말을 시작한다.
