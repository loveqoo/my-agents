# 199 — '능력 부여' UI 진단 (구현 보류)

> **상태: 진단만.** 사용자 결정(2026-07-07) — "먼저 진단만, 구현은 나중." 이 문서는 문제를 명확히
> 기록해 두는 재료다. 구현 착수는 별도 결정 시.

## 배경 (사용자 피드백)
> "관리자 > 유저 메뉴에서 '능력 부여'가 어렵습니다. 어떻게 설정해야 하는지 잘 모르겠어요. 저도
> 모르는데 일반 사람들은 얼마나 어려울까요?"

만든 사람(설계자)조차 설정법이 헷갈린다 = 발견성(discoverability) 실패. 스펙 177 P3에서 넣은
`능력 부여 (정책)` 카드(`UsersView.tsx:296-350`)가 대상이다. 메모리 `permission-model-redesign-direction`의
핵심 목표가 **"쉽게 쓰기"**였는데 정반대가 됐다.

## 현재 흐름 (화면 캡처 기준)
`UsersView` 하단 `능력 부여 (정책)` 카드 — 한 줄에 필드 4개를 조합해 정책 문자열을 만든다:
1. **대상** Select — `역할: admin/member` + `유저: <email>`이 한 목록에 섞임.
2. **능력 종류** Select — `mcp` / `rag` / `agent`.
3. **이름/서버(선택)** — **자유 입력 Input**("비우면 전체").
4. 미리보기로 `capability:mcp:…` **코드 문자열**을 그대로 노출 → [부여] 버튼.
결과: `grantPolicy({ subject, object: 'capability:<kind>:<name>', action: 'invoke' })`.

## 진단 — 왜 어려운가 (근본 원인)
1. **[P1] 무엇을 줄 수 있는지 안 보인다(발견성 0).** 종류(mcp/rag/agent)만 고르면 끝이고, 실제 등록된
   MCP 서버·RAG 컬렉션·에이전트 목록이 나오지 않는다. 이름을 **외워서 정확히 타이핑**해야 한다 — 뭐가
   있는지 모르는데 이름을 쳐야 하고, 오타 한 번이면 존재하지 않는 능력을 부여한다(무효 정책). **스펙
   195에서 rag_source_contains 파일명 자유입력을 등록 파일 Select로 바꿨던 문제와 동일**하며, 스펙
   106/107(능력 피커)에서 이미 "카탈로그에서 고르게" 했던 원칙이 이 관리자 화면엔 적용 안 됐다.
2. **[P2] 개발자 코드가 UI에 노출된다.** `capability:mcp:…`는 내부 식별자 문법이지 사람이 읽는 말이
   아니다. 일반 사용자에겐 의미 불명.
3. **[P3] 대상에 역할과 유저가 한 목록에 섞임.** 역할 기반 권한인지 개인별인지 정신모델이 안 선다.
   (역할에 부여 = 그 역할 전원, 유저에 부여 = 그 사람만 — 이 차이가 UI에 안 보임.)
4. **[P4] 맥락·결과 안내 부족.** "member는 부여 전엔 능력을 쓸 수 없습니다(기본 거부)" 한 줄뿐. *왜*
   유저 메뉴에서 하는지, 부여하면 *무슨 일이 일어나는지*(에이전트가 그 도구를 쓸 수 있게 됨) 흐름이 없다.

## 개선 방향 후보 (구현 보류 — 결정 시 채택)
- **A. 자유입력 → 목록 선택**: 종류를 고르면 등록된 실제 카탈로그(MCP/RAG/에이전트)를 체크박스/멀티셀렉트로
  렌더(스펙 106/107 능력 피커·195 파일명 Select 재사용). "비우면 전체"는 명시 옵션("모든 mcp")으로.
- **B. 코드 숨기기 → 문장화**: `capability:mcp:web_search` → "member 역할에게 **web_search 도구**를 쓸
  수 있게 합니다"처럼 사람이 읽는 문장. 코드는 툴팁/상세로만.
- **C. 대상 분리**: 역할 부여와 유저 부여를 시각적으로 구분(탭 또는 라벨)하고 각 효과를 한 줄로 설명.
- **D. 맥락 헤더**: "능력이란 에이전트가 쓸 수 있는 도구·지식·하위 에이전트입니다. 기본은 잠겨 있고,
  여기서 역할/유저에 열어줍니다." 수준의 도입 문장.

## RBAC 경계 (트리거 — 구현 시 필수)
- **트리거됨**: 정책(`grantPolicy`/`revokePolicy`)은 인가 데이터를 직접 쓴다. 단, 이 스펙은 **진단만**이라
  경계 설계는 구현 스펙에서 답한다. 구현 시 체크리스트(입구 열거·per-cap 인가·404 접기·검증 사다리
  3런)를 스펙 112(per-cap authz)·177 기준으로 반드시 채울 것. UI 개선이 부여 가능한 object 집합을
  넓히지 않는지(카탈로그 선택이 곧 화이트리스트가 되는지) 특히 확인.
