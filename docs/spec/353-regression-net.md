# 353 — 회귀망 씨앗 (죽어 있던 검증 스위트를 상시 그물로)

## 왜 (실측)

테스트 스크립트가 **359개**(verify 179 + browser 180)인데 **상시 도는 건 `make resource` 하나뿐**,
CI 워크플로우는 0개다. 각 스펙 때 한 번 수동으로 돌리고 방치하니 회귀망이 죽어 있고, 노후가 소리 없이
쌓인다(캠페인 중 049·034·098이 깨진 걸 우연히 발견).

순수 무의존 45개 표본 실측: **82% 통과(37) · 드리프트 18%(8)**. 드리프트를 조사하니 **전부 테스트·자산
노후지 코드 회귀가 아니다**(시드 이름 `mock-chat`→`mock-llm` 미반영, 인덱스↔파일 번호 불일치,
파일 경로 하드코딩 노후). **제품은 멀쩡하고 그물만 끊겨 있다.**

## 설계 원칙

1. **지금 통과하는 것만 그물에 넣는다.** 드리프트는 그물에 넣지 않고 **격리 목록(`KNOWN_DRIFT`)**으로
   분리 — 넣으면 그물이 늘 빨개서 "무엇이 새로 깨졌나"를 못 본다. 격리 목록은 **줄어드는 것이 목표**
   (초록으로 위장하지 않고 "N개 격리 중"을 정직하게 출력).
2. **측정 도구 = 상시 그물, 같은 엔진.** `tests/run_suite.py` 하나가 기준선 측정과 CI 그물을 겸한다.
   카테고리별(순수/DB/서버/브라우저)로 돌리고 통과/실패/에러를 집계, 그물(비격리)이 전부 통과하면
   exit 0 — CI·`make`가 그대로 문다.
3. **인프라 요구로 계층화.** 순수(무의존)→DB→서버(HTTP)→브라우저 순으로 요구가 커진다. `make test`는
   빠른 순수층을, `make test-all`은 전층을. 느린 층을 빠른 층이 기다리지 않게.

## 완료 조건 (수치)

- **R1** `tests/run_suite.py`가 카테고리별로 verify를 돌려 통과/실패/에러를 집계하고, 그물(비격리)이
  전부 통과하면 exit 0, 하나라도 깨지면 exit 1.
- **R2** 순수층 그물이 **초록**(현재 통과분 등록, 드리프트는 `KNOWN_DRIFT`로 격리).
- **R3** `make test`(순수층)·`make test-all`(전층) 타깃 추가.
- **R4** 격리 목록이 **명시적으로 출력**된다(몇 개가 왜 격리됐는지 — 은폐 금지, learning의 "no silent caps").
- **R5** 기준선 문서화: 각 카테고리 통과율을 스펙 결과에 기록(다음 라운드가 줄일 표적).

## 결과 (2026-07-15 실행)

- 러너 `tests/run_suite.py` — 카테고리 자동 분류(unit/db/http)·격리 목록·그물 통과 시 exit 0.
  Makefile: `make test`(씨앗=unit+db) · `make test-unit`(최속) · `make test-all`(http 포함, 참고용).
- **씨앗 그물 초록**: `SUITE_OK` — 통과 64(unit 37 + db 27)가 상시 그물, **격리 23개**는 사유와 함께
  명시 출력(보이지 않던 부채를 가시화 — 358개 방치 대신 23개 명시 목록).

### 측정이 그물의 경계를 그어줬다 (실측 기반 설계 결정)

- **unit(45)**: 무상태·병렬 안전 → 씨앗의 핵심. 37 통과·8 격리.
- **db(42)**: 직렬이면 상호 간섭 적음(각자 SessionLocal로 자기 데이터 마킹) → 27 통과·15 격리.
- **http(91)**: 깨끗한 서버·DB를 전제하는데 한 서버에 순차로 던지면 서로(그리고 자기 재실행)를
  **오염**시킨다(verify_037은 앞 실행이 남긴 컬렉션에 400, 346은 상태 오염 StopIteration). 각자
  단독+정리 또는 격리 DB가 필요 → **일괄 러너에 부적합**, 기본 그물에서 제외(`all`로만 명시 실행).

### instrument-first가 두 번 걸렀다 (측정 도구부터 의심)

1. 첫 러너는 db를 6-병렬로 돌려 **거짓 실패**를 만들었다(verify_038이 단독 exit 0인데 병렬 판에선
   error — 같은 DB·시드를 밟음). → db/http는 직렬로 고침.
2. "coroutine raised StopIteration" 4건은 테스트 결함이 아니라 http **상태 오염**이었다(346은 캠페인
   때 통과했는데 http 스위트가 데이터를 남긴 뒤 실패). → http를 그물에서 뺀 근거.

### 정직한 정정

- 최초 진단 "상시 도는 건 1개"는 과장이었다 — `make metrics`가 시나리오 스위트(스펙 288)와 resource
  게이트(347)를 이미 돈다. 그러나 **흩어진 179개 verify는 그물 밖**이라는 핵심은 유효했고, 이 스펙이
  그중 상태 격리 가능한 65개를 그물로 편입했다.
- 격리 23개는 조사 결과 **전부 테스트·자산 노후지 코드 회귀가 아니다**(캠페인 346~352와 무관 확증:
  `_create_approval` user_id는 스펙 291에 추가·테스트 미갱신, 나머지는 캠페인 모듈 import조차 없음).

## OUT

- 드리프트 격리 23개를 이번에 다 고치지 않는다 — 그물을 **연결**하는 게 이 스펙, 격리분을 **줄이는** 건
  후속(고쳐서 통과하면 러너가 "격리 해제 후보"로 알려준다). http층 격리 DB화도 후속.
- CI(GitHub Actions) 실제 연결은 회사 이식 맥락과 얽혀 별도(지금은 `make`로 로컬 그물만).
