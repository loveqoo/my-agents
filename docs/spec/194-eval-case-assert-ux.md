# 194 — 채점 기준(assert) 편집 UX 개선: AND 명확화 + 유형별 안내 카드

## 배경 (실사용 문의)
평가 케이스 편집(`CaseForm`/`AssertEditor`)에서 채점 기준 추가가 어렵다:
1. **각 기준마다 UI가 달라 뭘 넣을지 모른다** — 유형 Select + 조건부 Input(placeholder=hint) 하나뿐이라,
   유형별 입력 형식(도구 접두 `rag:` / 숫자 `2` / 소수 `0.4` / 파일명 / 판정 문장)이 placeholder 힌트에만
   의존한다. "좋은 기능인데 복잡한 UI에 막힌다."
2. **AND/OR가 헷갈린다** — 실제 채점은 **전부 AND**(`eval_harness.py:103` `all(ok for …)`)인데, 화면엔
   작은 회색 문구뿐이라 조건 관계가 안 보인다.

## 사용자 결정 (2026-07-06)
- 조건 관계: **AND 유지 + 명확히 표시**(추천 선택). OR은 도입 안 함(필요하면 문제를 둘로 — UI 단순 유지).
- **입력은 "문장형 인라인 폼"으로**(사용자 제안): 읽으면 그대로 자연어가 되게 요소를 쪼갠다 —
  예 "RAG 결과 [3]개 [이상▾]". 숫자 비교형은 **연산자(이상/이하)를 select**로.
- 연산자 select에 "이하"가 있으면 **실제 채점돼야 정직**(learning 119 조용한 초록 금지) → 백엔드
  `_lte`(이하) 확장 포함.

## 설계 (프론트 문장형 UI + 백엔드 lte 확장)

### A. AND를 눈에 보이게
- 채점 기준 섹션 상단에 **배지/헤더**: "✓ 아래 **모든** 기준을 만족해야 이 문제가 통과합니다 (AND)".
- 기준 카드가 2개 이상이면 카드 사이에 **"그리고" 커넥터**(중앙 작은 라벨 + 라인)로 AND 체인을 시각화.
- 기준 0개 = 자동 실패 경고 유지(fail-closed, learning 119).

### B. 문장형 인라인 폼 (핵심 — 읽으면 그대로 자연어)
각 기준 = **한 문장**으로, 입력 위젯을 문장 안에 끼워 넣는다(mad-libs 식). 유형은 문장 앞 select로
바꾸고(카테고리 그룹), 나머지 요소가 유형에 따라 문장을 완성한다.
- **유형 select 그룹**(antd `options` group): 답변 검사 / 도구 검사(agent) / RAG 검사(rag) / AI 판정.
- **유형별 문장 템플릿**(요소=[입력 위젯]):
  - output_contains: `답변에 [문구] 가 포함되어야 통과`
  - output_nonempty: `답변이 비어있지 않아야 통과` (입력 없음)
  - no_error: `실행 오류가 없어야 통과` (입력 없음)
  - trace_has(agent): `[도구▾: rag:/mcp:/memory:used] 가 호출되어야 통과` (프리셋 칩/select)
  - trace_lacks(agent): `[도구] 가 호출되지 않아야 통과`
  - **rag_hits(rag)**: `검색 결과가 [N]건 [이상/이하▾] 여야 통과` — 숫자 InputNumber + 연산자 select
  - **rag_score(rag)**: `최고 유사도가 [0.40] [이상/이하▾] 여야 통과` — 0~1 InputNumber(step .05) + 연산자
  - rag_source_contains(rag): `근거 파일명에 [파일명] 이 있어야 통과`
  - llm_judge: `AI 판정: [문장] (심판 모델이 PASS/FAIL)` — TextArea
- **연산자 select(이상/이하)**는 숫자 비교형(rag_hits·rag_score)만. 저장 시 type을 `_gte`/`_lte`로 매핑
  (UI는 문장, 저장은 닫힌 type). 다른 유형은 연산자 없음(있음/없음/판정은 type 자체가 표현).
- 유형별 아이콘·색으로 한눈에 구분.

### C. 백엔드 lte(이하) 확장 (P2)
현재 `rag_hits_gte`·`rag_score_gte`(이상)만. 연산자 select "이하"가 실동작하려면:
- `build_asserts`에 `rag_hits_lte`·`rag_score_lte` scorer 추가(gte의 반전, 같은 관측 `obs.rag`).
- fail-closed 규율 유지(관측 부재·NaN·범위 밖 거부 — 스펙 140 그대로). ASSERT_TYPES·api.ts 타입 동기.
- 기존 `_gte` 저장값 무변경(하위호환) — 문장 UI가 gte↔lte를 연산자 select로 왕복.

### D. 추가 흐름 단순화
- "채점 기준 추가"를 누르면 유형 select가 열린 빈 문장 카드가 붙는다(유형 고르면 문장 완성).
- 기본 케이스는 지금처럼 [오류 없음 · 답변 비어있지 않음] 프리필(무변경).

### E. 저장된 케이스 카드의 표시도 문장형 (편집=표시 일관 — 사용자 추가 문의)
문제를 저장하면 케이스 카드의 assert Tag가 **raw type**(`no_error`·`rag_hits_gte: 1`)을 그대로 노출한다
→ 사람이 못 읽는다. **편집 문장과 같은 어휘로** 요약해 보인다:
- assert→사람 문장 변환 **단일 함수 `assertLabel(a)`**(순수)를 편집 폼·케이스 카드가 **공유**(드리프트 0 —
  한쪽만 바뀌면 어긋난다). ASSERT_TYPES와 같은 파일.
- 예: `오류 없음` · `답변 비어있지 않음` · `"환불" 포함` · `rag: 호출됨` · `danger: 호출 안 됨` ·
  `검색 결과 3건 이상` · `유사도 0.40 이하` · `근거 파일 "AB테스트.md"` · `AI 판정: 정중한 존댓말인가`.
- Tag 색은 유형 카테고리(답변/도구/RAG/AI)로 유지(스캔성).

## 검증 (사다리)
- **단위**(P2 백엔드): build_asserts가 `rag_hits_lte`·`rag_score_lte`를 만들고 채점(경계값 이상/이하,
  관측 부재·NaN·범위 밖 fail-closed). gte 무회귀.
- **e2e**(브라우저): 케이스 편집 폼에서 (a) AND 배지·"그리고" 커넥터, (b) 유형 그룹 select, (c) 유형 전환
  시 문장/위젯 바뀜(숫자+연산자↔문구↔도구 칩), (d) 이상↔이하 연산자 select → 저장 시 gte↔lte 왕복 보존.
- **무회귀**: 기존 평가 e2e(137 CRUD·193)·admin tsc 0.
- 자가검증 지양 — 스샷으로 시각 확인(사용자 원칙).

## RBAC 경계 (트리거 판정)
- **비트리거**: 프론트 표시/입력 UI + 채점 scorer 종류 확장(lte). 소유권 경로·저장 입구·all(=AND) 판정
  전부 무변경. lte는 gte의 순수 반전(같은 관측). 새 쓰기 입구 0.

## 경계
- OR 미도입(사용자 결정) — 필요 시 문제 분리 안내로 흡수.
- assert 종류/의미는 그대로(백엔드 닫힌 집합) — 이번은 **입력 UX만** 재설계.
