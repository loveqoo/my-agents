# 370 — 마이그레이션 왕복은 "런타임 저작 데이터"가 생기는 순간 손실 왕복이 된다

**맥락**: 복합 에이전트 버전(스펙 370) 검증이 게이트 통과 후 재실행에서 갑자기 깨짐(시드 pins가
비어 있음). `updated_at`이 원본 그대로 = ORM이 만진 적 없음 → **컬럼이 drop/재추가**된 것.
근인 = `verify_343_downgrade`(마이그레이션 왕복 상주 핀, **자체 헤더가 virgin DB 전용을 명시**)를
run_suite가 라이브 DB에 직접 실행. 343 시절엔 왕복이 무손실(컬럼 개명 수준)이라 무해했지만,
369/370이 **런타임에 저작되는 데이터**(블록 이력 append·pins freeze)를 도입하자 downgrade가 그
데이터를 지우는 **손실 왕복**으로 조용히 변질 — 부트 백필이 "현재 head=v1"로 재생성해 초록으로
가렸다(진짜 이력은 소실).

## 교훈

1. **스키마 왕복의 손실성은 데이터 성격이 정한다** — 컬럼 개명·추가만 있던 시절의 "왕복 멱등" 핀은,
   나중 리비전이 append-only 저작 데이터를 들이는 순간 그 전제부터 무효가 된다. downgrade에
   `삭제되는 데이터가 무엇인가`를 리비전 docstring에 명시하고(우리는 "손실 있는 근사"로 적음),
   왕복 테스트는 **반드시 격리 DB**에서.
2. **테스트 자신의 전제(헤더)와 러너의 실행 방식이 어긋나면 전제는 장식이다** — 헤더가
   `_throwaway_db.py` 사용을 명시해도 run_suite는 몰랐다. 봉합 = 러너가 파일 본문의
   `_throwaway_db.py` 마커를 읽어 격리 러너로 자동 래핑(11개 전부 virgin-DB 명시 테스트).
   전제는 사람이 읽는 주석이 아니라 **러너가 집행하는 마커**여야 한다([[installed-guard-isnt-covering-guard]]
   동형 — 선언≠집행).
3. **백필이 초록을 만들면 소실이 안 보인다** — 부트 멱등 백필(치유 장치)이 파괴를 가리는 이중성.
   "백필 N건" 로그가 부팅마다 크게 나오면 그건 치유가 아니라 **반복 파괴의 신호**다(이번에 41→50→73건
   증가가 그 흔적이었는데 처음엔 지나침). 백필 건수는 0으로 수렴해야 정상.
4. 부수 배당: 마커 래핑으로 "처녀 DB 전제"라 격리됐던 테스트 2개(verify_059·345)가 소생 —
   [[366 되살린 테스트]]와 같은 계보(전제를 집행하니 그물이 넓어짐).
