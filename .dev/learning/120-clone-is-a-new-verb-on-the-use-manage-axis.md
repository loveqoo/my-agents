# 120 — 복제는 use/manage 축의 새 동사 — 권한·렌더를 그 축으로 맞춰라

스펙 120(에이전트 복제)에서 배운 것. (작은 기능이지만 축 판단이 핵심.)

## 1. 새 동사를 추가할 땐 "이건 사용이냐 관리냐"부터 판정한다

스펙 112가 세운 축 = **사용(공유 가능·RBAC) vs 관리(소유자/특권만)**. **복제**라는 새 동사를 붙일 때
먼저 이 축 위에 놓는다: 복제 = **읽기 + 새 생성**이지 원본 변경이 아니다 → 원본의 **관리 권한 불요**,
*가시하면 복제 가능*. 그래서 (a) 백엔드는 `assert_may_manage`를 원본에 걸지 **않고** 존재만 404-fold,
(b) 프론트 복제 버튼은 `can_manage` 게이트 **밖**에 둔다(비소유 공유 에이전트도 복제 가능 — 그게 재사용의
핵심). 새 동사를 기존 게이트에 습관적으로 묶으면(삭제·편집 옆이라 can_manage로 감싸는 실수) 재사용을
막는다. **동사마다 축을 다시 판정**하라.

## 2. 생성형 동사는 소유권을 새로 스탬프(승계 금지)

복제본은 **복제자**가 소유(069 no-takeover) — 원본 소유자를 승계하지 않는다. 복제·포크·import 등
"기존 것에서 새 것을 만드는" 동사는 전부 생성 시점 소유자 스탬프. 원본의 owner를 물려주면 "내가 만든
내 복제본을 내가 관리 못 함" 같은 모순이 난다.

## 3. 복사는 "행위 설정"만 — 등록·비밀 스냅샷은 떼어낸다

원본 config를 복사하되 **등록 특화 키(`card` 등)는 제거**하고, 비밀(endpoint/token)은 애초에 별도
컬럼이라 config 복사에 안 딸려온다 → 복제본은 안전한 ui 행위 에이전트. "복사"의 대상은 *무엇을 하는가*
(페르소나·모델·능력)이지 *어디에 등록됐나/무슨 크레덴셜*이 아니다. 복사 범위를 행위로 좁혀라.

## 4. 같은 버튼이 여러 렌더 변형에 있으면 전부 배선(하나만 하면 놓친다)

상세 드로어가 소스별(ui/code/external) 3개 변형이라, 복제 버튼을 ui에만 달면 원격 에이전트 재사용이
빠진다. **세 변형 모두**에 배선했다(스펙 114 "브라우저가 놓친 렌더 지점" 교훈의 사전 적용). 새 액션은
"이 UI가 몇 개의 렌더 경로를 갖나"를 먼저 세고 전부 덮되, 브라우저로 실제 렌더를 확인(놓침 방지).

## 적용
- 새 동사(복제·공유·import 등)는 use/manage 축에 먼저 놓고 권한·UI 게이트를 그 축으로.
- 생성형 동사는 소유권을 새로 스탬프(승계 금지, 069).
- 복사 범위는 행위 설정로 좁히고 등록·비밀 스냅샷은 떼어낸다.
- 같은 액션의 렌더 변형을 세어 전부 배선 + 브라우저로 실렌더 확인.
