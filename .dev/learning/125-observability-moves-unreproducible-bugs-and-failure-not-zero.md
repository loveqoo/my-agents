# 125 — 관측성으로 재현불가 버그를 옮기고, "실패≠0건"을 UI로 구분하라

## 트리거
검색/시험 도구가 "결과가 안 나온다"인데 (a) 실패 사유가 하나로 뭉개져(None/빈결과) 안 보이거나,
(b) 버그가 **재현 불가 환경**(다른 배포·다른 기기·사용자 인프라)에서만 나거나, (c) 예외가 사라지는
토스트로만 뜰 때. 특히 백엔드 가용성이 설정에 좌우되는 기능(임베딩·외부 API·mem0).

## 사례 (스펙 125)
사용자: "다른 노트북 배포에서 메모리 유사도 검색이 안 됨 + 왜 0건인지 알 방법 없음."
- 근인: `recall_probe`가 미가용 3사유(mem_cfg 없음·llm/embedder 누락·초기화 예외)를 `None` 하나로
  뭉갬 + 검색 중 예외를 500으로 던져 UI엔 사라지는 토스트. 관측성 0.
- 처방: `recall_diag`(예외 안 던지고 `{configured, backend_ready, embedder_model, error, results}`로
  구조화) + `MemorySearchOut.diag` + 프론트 **지속 진단 패널**(오류면 자동 펼침).

## 배운 것 ① (본질 — 재현불가 버그를 관측성으로 옮긴다)
**로컬에서 못 고치는 환경 버그는 "왜 실패인지"를 *그 화면에* 띄우게 만들어 사용자에게 옮긴다.** 다른
노트북의 임베딩 설정을 내가 못 고치지만, 진단이 "임베딩 미설정 / 초기화 실패 / 검색 실행 실패: …"를
그 배포 화면에 명시하면 사용자가 자가진단한다. "설정 자체 고치기"는 비목표로 명확히 두고 **관측성만**
출하 — 재현 불가를 이유로 손 놓지 말 것. 로컬 스샷으로 "정상·회상 0건"을 찍어 **0건이 진짜 없음임을
증명**(백엔드 정상)하면, 다른 환경의 "다른 상태"가 대비로 근인을 가리킨다.

## 배운 것 ② (실패≠0건 — 삼킨 예외를 0건으로 위장 금지)
진단 도구가 예외를 **삼켜 구조화**(500 대신 200+error)하면 편하지만, `enabled=True·results=[]·error=set`
상태가 UI의 기존 "결과 없음" 경로(토스트·빈 메시지)를 타면 **실패가 정상 0건으로 위장**된다(스펙 084
P2a "0건도 일어난 일"의 역방향 함정). UI 상태 분기 추가 시 **기존 표시 경로를 전부 점검**: "회상 없음"
토스트·emptyMessage 둘 다 `error` 있으면 억제하고 진단 패널이 실패를 말하게. (한 곳만 막으면
[[installed-guard-isnt-covering-guard]]처럼 틈이 남는다.)

## 배운 것 ③ (비밀 정제 — 정확 치환 우선, 정규식은 백스톱)
예외 문자열을 노출할 땐 비밀이 샌다. **정규식 추측 마스킹 단독은 반드시 놓친다**(codex H1: `api_key:
<hex>` 공백형·`x-api-key`·라벨 없는 40자 토큰). 근본 처방은 **가진 실제 비밀값(mem_cfg api_key)을 정확
문자열 치환**(형태 무관 확실 제거) + 라벨/토큰 정규식은 백스톱. 테스트도 hex·공백라벨·정확치환 케이스로
고정(happy `sk-` 하나만 보면 초록이 거짓).

## 배운 것 ④ (단일 권위 계약 — 진단이 프로덕션 경로를 우회하면 갈린다)
`recall_diag`를 `configured`로 조기 반환했더니 verify_084가 red — 테스트가 `resolve_backend`를 패치해
백엔드를 주입하는데 그 위에서 우회했다. **가용성의 단일 권위(`resolve_backend`)를 항상 통과**시키고
파생 플래그(`configured`)는 *부가 정보/문구 선택*에만 써라. 프로덕션 경로(recall_probe)와 같은 관문을
써야 계약이 안 갈린다(drift 0).
