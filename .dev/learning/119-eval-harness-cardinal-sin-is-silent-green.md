# 119 — 평가/신호 도구의 대죄는 "조용한 초록" — 모든 경로가 fail-closed여야

스펙 119(에이전트 평가 하네스, 결정적 수치)에서 배운 것.

## 1. 신호 도구는 "거짓 초록"이 "신호 없음"보다 나쁘다

평가 하네스가 내는 수치는 자율 루프(Ralph)가 **최적화하는 대상**이다. 그래서 실수/실패가 점수를
*올려* 보이게 하는 모든 경로("조용한 초록")는 치명적이다 — 루프가 그 거짓을 향해 최적화하기 때문.
없느니만 못한 숫자. 하네스의 모든 경로는 **fail-closed**여야 한다:
- **빈 asserts → 자동 통과 금지**: `all([]) == True`라 assert 없는 case가 무조건 pass. 데이터셋 실수
  하나가 점수를 올린다 → 빈 asserts는 **명시적 실패**로.
- **숨은 실행 실패 → error로 표면화**: 러너(run_fn)가 HTTP 401/500·비-SSE를 status 확인 없이
  `error=False`+빈 출력으로 돌려주면, negative case(`trace_lacks`+`no_error`)가 **거짓 통과**. 실행
  실패는 반드시 error로.
- **scorer 예외 → 그 assert 실패(전체 중단 아님)**: malformed obs·커스텀 scorer 버그가 `run_eval`을
  통째로 raise시키면 수치 산출이 깨진다. 개별 scorer 예외는 그 assert만 실패로 접고 평가는 계속.
- **run_fn 예외 → error 관측으로 접고 뒤 case 계속**: 한 케이스 실패가 전체 평가를 멈추면 안 됨.

## 2. codex(적대 타자)는 신호 도구에 특히 값지다 — "조용한 초록"은 happy-path 테스트를 정의상 통과

이 네 구멍은 모두 정상 케이스 테스트를 **통과**한다(그래서 "조용한"). 통과 케이스만 있는 verify로는
드러나지 않는다. 적대 리뷰가 "실수가 점수를 올리는 경로"를 찾아 넷을 짚었다. 신호/게이트/검증 도구를
만들 땐 반드시 **판별력을 실측**(틀린 assertion·실패 관측이 점수를 *내리는가*)하고, 적대 타자에게
"조용한 초록 경로"를 맡겨라. 판별 테스트 = 통과 case + **의도적 실패 case**를 함께 둬 숫자가 움직임을 봄.

## 3. 결정적 수치의 하한은 행위·구조 신호(LLM 생성 텍스트 아님)

LLM 출력 텍스트는 비결정이라 그대로 채점하면 수치가 흔들려 자율 루프 신호가 못 된다. **행위(trace 노드
= 어느 능력을 호출/위임했나, 스펙 085/100 관측 재사용)·구조·error 신호를 하한**으로(learning 110 "LLM
무관 경로는 mock 결정화"의 연장). LLM-judge는 비결정 별도 축으로 후속. 결정성이 곧 자율의 전제.

## 4. 재사용 규약 = 데이터셋 × 실행함수 분리

`run_eval(cases, run_fn)` — scorer/집계(generic)와 실행 어댑터(run_fn)를 분리하면 어떤 실행 경로(HTTP
채팅·그래프 직접·미래의 다른 표면)든 **run_fn만 갈아끼워** 같은 수치 틀로 평가. 자율 루프는 데이터셋 +
run_fn만 바꿔 재사용. 단 run_fn 어댑터가 실패를 숨기지 않게(위 ①) — 규약의 약한 고리는 어댑터다.

## 적용
- 평가/게이트/신호 도구는 모든 경로 fail-closed(빈 조건·숨은 실패·예외 전부 점수를 *내리게*).
- 판별력을 실측(의도적 실패 case로 숫자가 움직임 확인)하고 "조용한 초록"을 적대 타자에 맡겨라.
- 결정적 수치는 행위·구조 신호를 하한으로(비결정 LLM 텍스트 채점 지양).
- 재사용은 데이터셋 × 실행함수 분리, 단 어댑터가 실패를 숨기지 않게.
