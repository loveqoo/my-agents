# 114 — 게이트된 동작은 *모든* 렌더 지점을 막아야 / 세션서 못 만드는 상태는 응답 인터셉트로 검증

스펙 114(소유 표시 + 비소유 관리 버튼 숨김)에서 배운 것.

## 1. 백엔드가 판정을 소유, 프론트는 필드만 읽는다 (drift 0)

`can_manage`를 프론트가 재계산하면 casbin admin 역할을 모른다(프론트는 `is_superuser`만 보임) → 오판.
**백엔드가 each Out 객체에 `can_manage`를 실어** 내려주고, 프론트는 `item.can_manage`만 읽는다. 판정
술어는 `ownership.may_manage`(assert_may_manage의 불리언 형제, 단일 술어) — 라우트가 list/get서 계산.
새 프롭 스레딩 불요(필드가 객체에 있으니).

## 2. 게이트된 동작은 **모든 렌더 지점**을 막아야 한다 (112 "입구 열거"의 UI판)

`can_manage=false`에 따라 버튼을 숨길 때, **한 곳만 막으면 샌다**. 나는 상세 드로어의 삭제/편집은
막았지만 **목록 행의 액션 컬럼(삭제 휴지통)을 놓쳤다** — 비소유 행에 삭제 버튼이 그대로 남았다.
백엔드 게이트가 있어 눌러도 404지만, UI가 "할 수 있는 척"하는 건 거짓 affordance다. **같은 동작이
여러 표면(리스트 행·상세 드로어·버전 패널·문서 패널)에 렌더되면 전부 열거해 각각 가드**하라. 이건
112의 "변경 입구 전수 열거"가 UI로 옮겨온 것 — 주 표면 하나만 보면 샌다.

## 3. 현재 세션에서 못 만드는 상태는 **응답 인터셉트로 결정적 검증**

admin은 superuser 세션이라 `can_manage=false`가 자연히 안 나온다(전부 관리 가능) → "비소유 숨김"을
실제로 볼 수 없다. Playwright `page.route`로 `/agents` 실제 응답을 받아(`route.fetch()`) 한 항목에
`owner_id=타인·can_manage=false`를 **주입**해 그 렌더 경로를 결정적으로 태웠다. member 계정을 만들지
않고도 프론트 게이팅을 실측. **도달 어려운 상태는 실 데이터를 인터셉트·변형해 재현**(전부 목킹은 취약,
한 필드만 변형이 견고).

## 4. 브라우저 검증이 자가검토가 놓친 걸 잡았다

스크린샷에서 비소유 행에 휴지통이 남은 걸 눈으로 보고서야 리스트 액션 누락을 깨달았다(코드만 보면
"드로어 막았으니 됐다"고 넘어갔을 것). **UI 게이팅은 반드시 브라우저로 눈으로 확인** — 렌더 지점
누락은 텍스트 검색·타입체크로 안 잡힌다(verify-ui-in-browser-proactively).

## 적용
- 백엔드 불리언을 each 객체에 실어 프론트는 표시만(재계산 금지, 판정 술어 단일화).
- 게이트된 동작의 *모든* 렌더 지점을 열거해 각각 가드(리스트·상세·서브패널) — 하나만 막으면 샌다.
- 세션서 자연 발생 안 하는 상태는 응답 인터셉트로 한 필드 변형해 결정적 검증.
- UI 게이팅은 브라우저 스샷으로 눈 검증(누락은 정적 검사로 안 잡힘).
