# 359 — 한 스펙이 두 기능을 다른 메커니즘으로 지으면 관측성이 갈린다

## 맥락

플레이그라운드 인스펙터에서 노드형 에이전트의 메모리 **회상 내용이 안 보였다**("mem 4"만, 내용은
프롬프트 탭에만). 사용자가 "RAG도 같은 문제냐?" 물었고 — **아니었다.**

## 핵심 통찰

스펙 268이 "노드별 RAG·메모리"를 **한 스펙**으로 지었지만 두 절반을 **다른 메커니즘**으로 지었다:
- **RAG = 도구**(컬렉션별 `build_rag_tool`): 결과를 calls_sink에 기록할 때 `hitsDetail`(내용)까지 실음
  → 인스펙터가 여느 도구처럼 히트 카드로 내용 표시.
- **메모리 = 캐싱 프록시**(`_MemoryRecallProxy`): "조회 행위"(node·query·hits·cached)만 기록하고
  내용(format_memory_hits)은 프롬프트에 주입만 하고 **버림** → 인스펙터는 카운트만.

즉 같은 스펙 안에서 **도구 경로는 "내용 기록" 관례를 물려받았고, 프록시 경로는 "행위만 기록"**이라
관측성이 비대칭이 됐다. 사용자에겐 "회귀"로 보였지만 실은 노드형 확장 때 메모리만 내용이 빠진
처음부터의 갭(에이전트가 표준 그래프→노드형으로 바뀌며 드러남).

## 왜 중요한가

- 스펙 082는 "조회 **행위**를 계측하라(결과만 싣지 말고)"였다. 프록시는 그 절반(행위)만 지키고
  나머지 절반(**내용**)을 빠뜨렸다 — 행위 계측이 내용 계측을 대체하지 않는다.
- 병렬 기능을 서로 다른 메커니즘(도구 vs 프록시, 동기 vs 배경, 라우트 vs 브로커)으로 지으면,
  한쪽이 가진 횡단 속성(관측성·마스킹·감사)이 **자동으로 다른 쪽에 오지 않는다**. 한 스펙이라고
  대칭이 보장되지 않는다.

## 다음에 적용

- "X와 Y를 함께 짓는다"는 스펙이면, 각 횡단 속성(관측성·마스킹·에러표면·감사)을 **X·Y 양쪽에서
  따로** 확인하라(learning 088 입구 닫힌집합의 기능-쌍 버전).
- "RAG도 같은 문제냐?" 같은 형제 질문엔 **메커니즘이 같은지부터** 보라 — 같은 증상도 다른 메커니즘이면
  다른 답이다(여기선 도구=OK, 프록시=갭).
- 수정은 대칭 복원으로: 프록시가 이미 계산·캐싱하는 내용을 record에 실어 **표준 경로와 같은 컴포넌트**
  (MemoryRow)로 렌더 → drift 0.
