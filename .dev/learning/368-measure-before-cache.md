# 368 — 캐시 설계 전 측정이 우선순위를 뒤집었다 (직감의 병목 ≠ 실제 병목)

**맥락**: 매턴 그래프 재빌드(스펙 367 동기)를 캐시하기 전에 베이스라인 측정(367-A). 코드 정독만으로
세운 가설은 "MCP 연결·모델 클라이언트 신규·compile 셋 다 비싸다"였다. 102턴 실측이 이를 교정했다.

## 실측이 가설을 교정한 지점

1. **웜 compile+클라이언트는 공짜였다** — graph 단계(build_chat_openai+create_agent) 웜 ~1.6ms.
   "매턴 compile·매턴 새 커넥션풀"은 코드상 낭비로 보였지만 숫자로는 무시 가능. 콜드 첫 턴만
   ~137ms(lazy import) — 워밍업 1턴 버리기가 하네스에 필수였던 이유.
2. **빌드 비용 ≈ MCP 디스커버리 그 자체** — 서버당 ~11ms(순차). memory/rag/broker는 0(대조군).
3. **동시성이 병목을 ~5배 증폭** — 동시 8에서 mcp=3: 34→166ms p50(p95 201ms). 순차 측정만 봤으면
   "35ms, 견딜 만"으로 오판했을 것. **병목은 부하 축과 곱해질 때 정체를 드러낸다** — 순차/동시 두 축
   측정이 설계를 갈랐다(캐시 1순위=MCP 도구목록).
4. **지연 축만 보고 "작다=부차"로 강등하지 말 것(개발자 교정)** — 그래프 빌드 1.6ms를 지연으로만 보고
   강등했다가, CPU 축 재측정(0.50ms CPU/턴·CPU/wall 95%·동기=이벤트 루프 블록)으로 철회. wall이 작아도
   순수 CPU·루프 블록은 처리량 천장을 깎는다. 게다가 ROI는 절감량 단독이 아니라 **한계 비용**으로 판단
   — 선행 리팩터(구성/호출 분리)를 어차피 하고 키(agent_version_id)가 불변이면 무효화 공짜라 캐시의
   한계 비용 ≈ 0. "절감 작음"과 "얹는 비용 0"이 만나면 하는 게 맞다.

## 재사용 규칙

- **캐시/최적화 설계 전에 단계 분해 계측 먼저** — 직감이 지목한 비용(눈에 띄는 코드 낭비)과 실측
  병목이 다를 수 있고, 다르면 설계 우선순위가 통째로 바뀐다. [[verify-premise-before-designing]]의
  성능판: 전제(무엇이 비싼가)를 1측정으로 확정하고 설계하라.
- **부하 축(동시성)을 반드시 포함** — 단일 요청 지연만 재면 곱셈 구조(서버수×동시성)를 놓친다.
- **측정을 자산으로**: 계측은 핫패스에 상주(trace.buildMs — 인스펙터에서도 열람 가능), 하네스는
  `make perf-build`로 재실행 — 최적화 前/後 비교가 언제든 한 명령. 워밍업 표본은 버려서 콜드 노이즈 격리.
