# 124 — 게이트 뒤 하드 필터가 기능을 조용히 무력화 + 테스트가 버그 동작을 굳힌다

## 트리거
보안/권한 게이트(allowlist∩RBAC 등) **뒤에** 후처리 필터(어휘·관련성·품질)를 둘 때. 특히 그 결과를
다른 기능(오케스트레이션 discover 등)이 소비할 때.

## 사례 (버그, 스펙 124)
사용자: "**조율형 에이전트가 도구·문서·기억을 못 쓴다.**"
- 근인: `PolicyScopedBroker.discover(query)`가 허가(allowlist∩RBAC) 후보에 **어휘 하드 필터**
  `caps = [c for c in caps if q in f"{c.name} {c.id} {c.hook}"]`를 걸었다. 이건 **"쿼리 전체가 능력
  텍스트의 부분문자열일 때만" 남긴다**(방향이 뒤집힘 — query⊆cap). 자연어 쿼리는 짧은 능력 이름의
  부분문자열이 절대 아니므로 **허가된 능력이 전부 탈락**. 조율형은 `broker.discover(state["query"])`로
  위임 대상을 찾으니, 실제 쿼리에선 항상 빈 목록 → 도구·문서·기억 전부 못 씀.
- 처방: 하드 필터 → **랭킹**(쿼리 토큰 겹침 순 정렬, 0 겹침도 유지, limit까지). 게이트는 불변.

## 배운 것 ① (본질)
**게이트 뒤 하드 필터는 "관련성 도우미"인 척하며 기능을 통째로 죽일 수 있다.** 특히 매칭 방향이
뒤집히면(입력⊆카탈로그) 자연어에선 항상 0이 된다. 작은 카탈로그의 discover는 **필터가 아니라 랭킹**이
맞다 — 허가된 걸 버리지 말고 순서만 매겨 소비자(LLM/select)가 고르게. "필터로 0을 만들 이유가 있나?"를
물어라(게이트가 이미 권한을 좁혔다면 후처리로 더 좁힐 근거가 약하다).

## 배운 것 ② (테스트가 버그를 굳힌다)
이 필터에 **의존하던 GREEN 테스트가 둘** 있었다:
- `verify_101 H2`: `discover("web_search") == []`(echo만 허가) — 버그 필터가 echo까지 떨궈 []가 됐다.
  진짜 불변식은 "미허가 web_search 부재"(echo 노출과 무관). → `WEBSEARCH_CAP not in ids`로 교정.
- `verify_100 P2`: `discover("비매칭") == []` — 필터가 허가 능력을 떨궈 []. → "비매칭 쿼리도 허가 능력
  유지"로 교정.
- 교훈: **테스트가 GREEN이어도 버그 동작을 단언하고 있을 수 있다.** 부수효과(필터가 X까지 떨굼)를
  단언하면, 버그를 고칠 때 그 테스트가 "회귀"처럼 빨개진다 — 이때 **테스트가 진짜 불변식을 단언하는지,
  아니면 버그 부수효과를 굳혔는지** 구분해 후자면 불변식으로 고쳐라(코드 되돌리지 말고). 보안 불변식
  (deny-by-default·미허가 부재)은 반드시 보존됐는지 별도 확인([[complement-attack-can-be-honest-boundary]]
  결이 다름 — 여긴 "그린이 버그를 굳힘").

## 배운 것 ③ (디버깅: 레이어 격리)
"능력이 안 나온다"를 **빈 쿼리 vs 실 쿼리**로 갈라 "후보가 비었나 vs 필터가 떨구나"를 분리했고,
**네트워크 불필요한 provider(memory)**로 MCP 연결 실패와 필터 문제를 격리했다(가짜 MCP는 연결 실패로 0이라
필터를 못 봤음). UI뿐 아니라 백엔드도 **레이어별로 켜/꺼 비교**가 근인을 못 숨기게 한다.
