# 113 — Confused deputy는 "누가 그 참조를 넣었나"로 인가한다 / 신원은 권한조회 키로 쓰기 전에 형식 검증

스펙 113(런타임 tool 배선 인가, codex 112 P0 봉합)에서 배운 것.

## 1. 자원 참조로 크레덴셜을 쓰는 경로는 "누가 그 이름을 넣었나"로 인가한다

채팅 런타임이 agent config의 `mcps`/`vectorTables` **이름**으로 MCP/컬렉션을 로드해 복호화 크레덴셜로
tool을 배선하는데 인가가 없었다(confused deputy). 올바른 주체는 **그 이름을 config에 넣은 사람**:

- 저장된 config의 자원 → **에이전트 작성자**(agent.owner_id) 권한. "에이전트는 작성자가 쓸 수 있는
  자원까지만"(작성자가 config에 박을 때 이미 권한을 가졌어야).
- 채팅 사용자로 막으면 **공유 에이전트가 깨진다**(112 갈래 재적용) — 사용자 축은 브로커 per-cap이 담당.

## 2. **호출자 입력이 작성자 권한을 빌리는** 두 번째 confused deputy에 주의

codex P0: 위를 작성자 권한으로 게이트했더니, 채팅 호출자가 `overrides.mcps`(세션 한정 덮어쓰기)에 **남의
비공개 MCP 이름을 주입**하면 게이트가 작성자 권한으로 판정해 통과 → 호출자가 작성자 권한을 빌려 남의
크레덴셜을 자기 세션에 배선. **호출자가 제어하는 입력으로 참조를 추가할 수 있으면, 그 추가분은 작성자가
아니라 호출자 권한으로 게이트**해야 한다.

봉합: override **병합 전** 저장본 자원 집합을 포착 → 저장본은 작성자 권한, **주입분은 호출자(`own`)
권한**. 원칙: **"config에 이미 있던 것"과 "이번 요청이 넣은 것"을 분리해 각각 그것을 넣은 주체로 인가.**
캘러 제어 입력(override/query param)이 저장 상태에 섞여 downstream 권한 판정에 태워지는 지점을 의심하라.

## 3. 신원 문자열을 권한조회 키로 쓰기 전에 **형식을 검증**한다

codex P2: `owner_id="admin"`(비정상 스탬프)이 casbin `enforce("admin",'*','*')`에서 기본 admin **역할
이름**과 우연히 매칭 → 특권 오판. 원인은 UUID 파싱을 casbin 판정 **뒤에** 뒀던 것. **신원을 권한 백엔드에
넘기기 전에 그게 기대한 형식(UUID)인지 먼저 검증**하라 — 안 그러면 사용자 식별자 공간과 역할/주체 이름
공간이 겹쳐 권한 상승이 샌다. 정상 경로(`owner_of`는 UUID/None만)엔 없어도 fail-closed 반례다.

## 4. 같은 RBAC 레버가 두 경로를 일관되게 게이트한다

`_rbac_check`(112 A)를 런타임 배선(113)에서 재사용 → admin이 "이 자원만 부여"하는 per-cap grant가
**브로커와 런타임 tool 배선 양쪽에 동일하게** 먹힌다. 인가 술어를 한 곳에 두면(drift 0) 새 접근 경로가
생겨도 같은 레버로 덮인다. 헬퍼(`agent_may_wire`)는 `is_privileged`/`assert_may_manage`처럼 enforcer를
지연 로드(미초기화 fail-closed)해 테스트/부팅 순서에 강건.

## 적용
- 이름/id 참조로 특권 자원을 쓰는 경로: 그 참조를 **넣은 주체**로 인가(저장본=작성자, 요청 주입분=호출자).
- 캘러 제어 입력이 저장 상태에 병합돼 downstream 권한에 태워지는 지점을 분리·재인가.
- 신원 문자열은 권한조회 전에 형식(UUID 등) 검증 — 식별자/역할 이름 공간 충돌 차단.
- 인가 술어는 단일 헬퍼로 — 새 경로가 같은 레버로 자동 커버되게.
