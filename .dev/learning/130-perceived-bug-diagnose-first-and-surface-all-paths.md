# 130 — "안 돈다" 신고는 "안 보인다"일 수 있다(진단 먼저) + 표면화는 경로 전수

## 트리거
(a) 사용자가 "기능 X가 동작 안 한다"고 신고했는데 코드상 동작해야 할 때. (b) 관측성/표면화 기능(트레이스·
인스펙터·배지)을 추가할 때. (c) 자동/위임 실행(브로커·백그라운드)이 사용자에게 보이지 않는 구조일 때.

## 사례 (스펙 130)
"조율형이 RAG 검색을 안 한다" 신고 → **진단 먼저**(층 격리 프로브 + deep-reasoner e2e 추적): 검색은
동작 중(라이브 트레이스에 broker_invoke:rag:Obsidian, 답변이 데이터 인용). 진짜 근인 둘:
- **표시 구멍**: 인스펙터 RAG 섹션이 직접형 배선만 채우고 브로커 경유 호출은 그래프 노드명뿐.
- **약한 히트**: 노트에 없는 질문엔 검색하고도 "자료에 없음" 답 → "검색 안 함"으로 오인.
처방 = 기능 수리가 아니라 **표면화**: hits/topScore 구조화 → trace.brokerCalls → 인스펙터
"rag:X · 검색 N건 · 최고 유사도"(+관련도 낮음 태그) + 메시지 칩에 rag 카운트.

## 배운 것 ① (인식된 증상 — 동작하지만 안 보이는 기능은 없는 기능)
버그 신고를 받으면 "실제로 안 도는가 vs 돌지만 안 보이는가"를 **실 트레이스/층 격리로 먼저 가른다**.
안 가르고 기능 층을 고치면 헛수리(이미 124에서 고친 버그를 또 팠을 것). 관측성 부재는 그 자체가
결함이다 — 사용자 신뢰 관점에서 "보이지 않는 성공"은 실패와 구별 불가(125 "왜 0건인지"의 형제).

## 배운 것 ② (표면화 스펙은 경로 전수 — 부분 표면화 = 새 사각지대)
메인 경로만 표면화하고 승인대기/재개 경로를 OUT으로 두면, **표면화를 믿게 된 사용자에게 그 경로들이
새 사각지대**가 된다(codex P2 ×2) — "이번엔 칩이 없네 = 검색 안 했네" 오판을 재생산. 관측성 필드는
그 트레이스를 만드는 **모든 경로에** 싣고, 투영 로직(키 화이트리스트)은 **헬퍼 하나**로(122 "모든
소비 표면 전파"의 트레이스판). 표시용 수치는 실측일 때만 렌더(없으면 생략 — topScore 부재를 0.000
"관련도 낮음"으로 오표시 금지, codex P3).

## 곁다리 (e2e 셀렉터)
"응답 도착"을 상시 존재하는 요소("인스펙터" 토글)로 폴링하면 스트리밍 중 조기 통과(오탐) — **그 상태가
만든 요소**(트레이스 칩)로 폴링해야 한다(fast-worker 자가 교정).
