# 129 — 목업 배선 = 그 API의 첫 e2e (존재≠동작) + commit 후 서버 생성 컬럼은 refresh

## 트리거
(a) 목업 UI(비배선 버튼 등)를 배선하며 "백엔드는 완성돼 있다"고 전제할 때. (b) 뮤테이션 라우트가
commit 직후 ORM 객체를 직렬화해 응답할 때 — 특히 모델에 `onupdate=func.now()` 등 **서버 생성 컬럼**이
있을 때.

## 사례 (스펙 129)
세션 상세의 "세션 종료" 목업 버튼 배선. 스펙 초안은 "백엔드 `POST /end` 완성·무변경"을 전제 —
**코드가 존재**하고 리뷰상 멀쩡해 보였다. fast-worker 브라우저 검증(시드 세션으로 실호출)이 반증:
- 첫 실호출에서 500. 근인 = `last_activity`가 `onupdate=func.now()` 서버 생성값이라 commit 후 ORM에
  만료 상태로 남고, 응답 직렬화(session_to_out)의 동기 접근이 lazy-load 시도 → MissingGreenlet
  (회고 026의 rollback 변형과 같은 부류, 이번엔 **commit 변형**).
- **커밋은 성공, 응답만 실패** → "세션은 종료됐는데 화면엔 실패 토스트" 거짓 실패 UX.
- 처방: commit 후 `await session.refresh(s)` 1줄. 같은 부류 grep으로 다른 지점(읽기 전용) 안전 확인.

## 배운 것 ① (존재≠동작 — 목업 배선은 첫 e2e다)
한 번도 호출된 적 없는 라우트는 **미검증 코드**다. 목업 UI를 배선하는 순간 그 API가 처음으로 실제
경로(HTTP→커밋→직렬화)를 탄다 — "백엔드 완성" 전제는 코드 존재가 아니라 **실행**(curl 한 번, 시드
데이터로 e2e)으로 확인하고 스펙에 적어라. 이번엔 검증 단계가 잡았지만, 초안 단계에서 두드렸으면 더
쌌다.

## 배운 것 ② (commit-후-직렬화 + 서버 생성 컬럼 = refresh 필수)
`expire_on_commit=False`여도 **서버가 생성하는 값**(onupdate)은 commit 후 해당 속성만 만료된다 —
동기 접근이 async 컨텍스트 밖 lazy-load를 유발해 MissingGreenlet. 뮤테이션 라우트가 commit 직후 그
객체를 직렬화하면 `await session.refresh(obj)`로 확정하고 응답하라. 특히 이 실패는 **커밋 성공 후**라
데이터는 바뀌고 응답만 죽는 거짓 실패가 된다(재시도 유도 시 중복 부수효과 위험까지).

## 배운 것 ③ (위임 계약이 작동한 모양)
fast-worker는 범위 밖 결함을 **고치지 않고** API 로그·모델·기존 회고(026)까지 연결해 파일:라인으로
보고했고, 메인이 수정 후 SendMessage로 같은 에이전트를 재개해(맥락 보존) 재검증했다 — "발견=보고,
수정=조율자" 분담이 낭비 없이 돌았다.

- 새 뮤테이션 라우트: commit 직후 객체 직렬화 시 서버 생성 컬럼 유무 확인 → 있으면 refresh.
