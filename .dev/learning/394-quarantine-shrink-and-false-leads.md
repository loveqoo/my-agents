# 394 — 위생 묶음: 격리는 장치로 줄이고, 내 메모도 의심하라

## 맥락

C 묶음(스펙 389): 격리 3건 판정·158 환경 독립화·옛 이름 정리·리퍼 확장·픽스처 자가검사·
리비전 중복 확인. 결과: 격리 −3(158·059·345), 오경보 2건 확정(리비전 중복=내 파싱 오류,
020 옛 이름=정당한 마이그레이션 테스트 입력), 068은 해제 실측 실패로 재격리.

## 교훈

- **"격리인데 통과" 신호의 정답은 셋으로 갈린다**: ①검증기를 환경 독립으로 재작성(158 — mock
  전제를 mock cfg 명시 조립으로) ②실행 방식을 장치로 승격(059·345 — virgin-DB 본질이면
  _throwaway_db 마커로 항상 격리 실행 → 영구 해제) ③실측 재실패면 사유만 갱신해 유지(068 —
  해제는 관찰 아닌 실측으로). 통과 신호만 보고 일괄 해제하면 flake를 그물에 들인다.
- **백로그의 내 메모도 검증 대상이다** — "verify_020 옛 이름 정리 후보"는 오판이었다(그 이름들은
  카탈로그 흡수 마이그레이션의 **입력 픽스처**). 메모를 실물 확인 없이 집행했으면 정당한 테스트를
  훼손했다. 후보 메모는 착수 시 실물 재확인([[verify-premise-before-designing]]의 자기 메모판).
- **리퍼 확장 시 상주 픽스처를 누수로 오인하기 쉽다** — suite-kb를 패턴에 넣었다가 첫 dry-run이
  적발. dry-run 기본값(스펙 384 규율)이 정확히 이런 실수를 흡수한다 — 파괴 도구의 dry-run은
  구현 검증기이기도 하다.
- **같은 파싱을 두 번 틀렸다(회고 391 이후 재발)** — 홑/쌍따옴표에 이어 타입 주석 유무로 리비전
  파싱을 또 놓쳐 "중복 4건" 유령을 만들었다. 임시 정규식 결론은 형식 변형 전수(따옴표·주석·구형식)
  를 못 덮으면 "의심"으로만 기록하고 단정 금지.
