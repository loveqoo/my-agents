# 240 — 도구 미바인딩은 크래시가 아니라 "호출한 척"으로 나타난다 (스펙 265)

## 맥락
264에서 노드형 데모를 실모델로 돌려 ALL GREEN 선언했는데, 위키 도구는 두 번 다 안 불렸고 나는
"모델 재량(강제 아님)"으로 접었다. 사용자: "위키 찾아서 계획 세워야 하는데 위키를 찾지 않았어.
제대로 테스트해줘." — 도구 발화를 필수 단언으로 올리자 진짜 버그가 나왔다.

## 무엇을 배웠나

### 1. "핵심 행동이 0회 발화한 그린"은 그린이 아니다
이 데모의 존재 이유가 위키 검색(근거 기반 답변)인데, 그 핵심 경로가 한 번도 안 돌았는데 그린을
선언했다. "모델 재량"은 편한 변명이었다 — 재량이라면 재량이 *작동하는 경우*를 한 번은 봐야 검증이다.
처방: 기능의 존재 이유에 해당하는 행동은 필수 단언으로 올리고, 발화 조건(모르는 질문·의무화 프롬프트)
을 테스트가 직접 만들어라. probe-deeper의 테스트판: 안 나왔으면 "재량"이 아니라 "왜 안 나왔지"부터.

### 2. 도구 미바인딩의 증상은 에러가 아니라 그럴듯한 환각이다
민이름('wiki_search') 저장 → 런타임 접두명('web-fetch__wiki_search')과 불일치 → by_name 매칭 0 →
도구가 **조용히** 미바인딩. 그 상태에서 프롬프트가 "반드시 wiki_search를 호출하라"고 하니 모델은
"wiki_search를 통해 검색한 결과…"라고 **호출한 척 지어냈다**. 크래시도 경고도 없이 그럴듯한 답이
나오니 표면만 보면 성공처럼 보인다. 판별은 트레이스(mcp 기록·도구 노드 발화)로만 가능 — "도구를
썼다는 주장"과 "도구 호출 기록"을 분리해서 보라.

### 3. 근인은 2단 프로브로: 배선(이름) 따로, 행위자(모델) 따로
한 프로브로 (a) 실 build_mcp_tools의 도구 이름 목록 (b) 제대로 바인딩했을 때 모델이 tool_calls를
내는지를 동시에 쟀다. (a)가 접두명을 드러내 배선 버그 확정, (b)가 모델은 정상임을 확정 — 수정 범위가
정확히 좁혀졌다(모델 프롬프트 튜닝이 아니라 이름 해석).

### 4. 이름 체계가 계층마다 다르면 접점에 미러·정규화를 명시하라
UI는 민이름(사람 친화), 런타임은 `서버__도구`(_safe_name, LLM 제약+서버 네임스페이스) — 둘 다
각자 이유가 있다. 문제는 접점(노드 tools 저장)에 변환이 없던 것. 처방: 프론트가 런타임 이름을
저장(safeToolName 미러) + 엔진에 무모호 접미 폴백(구저장분 자가치유·모호 시 정직 스킵). 145
(형태 넓히면 소비자 전수)와 같은 축 — 값의 *이름 체계*도 계약이다.

### 5. 저작 e2e와 실행 e2e는 다른 결함을 잡는다 — 실행은 "도구 있는 노드"로
저작 왕복(259)은 tools:['add'] 저장까지 봤지만 실행 e2e는 도구 없는 노드로만 돌려 미스매치가
숨었다. 실행 검증은 기능 축(도구·격리·형식)마다 그 축이 실제 발화하는 픽스처로.
