# 246 — 공용 역량 단위(기억 facet): 추출은 결합을 드러내고, 269의 정리가 컨트롤을 단순화했다 (스펙 271)

## 맥락
3부작 완결(269 어휘·270 프록시·271 공용 컨트롤). 노드=미니 에이전트라 6 facet 공유 — 그중 **기억
facet(단기+장기)**을 에이전트·노드 공용 컨트롤로 추출(안 B — facet별 쪼개기). 안 A(단일 모놀리스)는
PickerGroups 스케일과 카드 간결성 충돌 위험이라 반려.

## 발견과 교훈

### 1. 공용 추출이 잠복 결합을 드러낸다 (codex Low #2)
단기+장기를 한 "기억" 구획으로 묶고 `surfaceVisible('기억')`로 게이트했더니, **단기(historyDepth)까지
memories 소비 여부에 묶여버렸다** — memories 미소비 커스텀 impl에선 단기 편집기가 통째 사라짐. 근인:
단기는 **모델 컨텍스트 창**(항상 적용)인데 장기(mem0 소비)와 한 게이트를 공유. 처방: 단기 항상 렌더·
장기만 게이트. **규칙: 두 컨트롤을 한 구획에 묶을 때, 그들의 *게이트 조건이 같은지* 먼저 확인 —
"같이 보인다"와 "같은 조건에 보인다"는 다르다.** 묶기 전엔 각자 다른 스텝이라 안 겹쳤던 결합이,
묶으면서 생겼다(245 "한 자료구조가 두 축 겸하면"의 UI 게이트판).

### 2. 앞 스펙의 정리가 이번 컨트롤을 단순하게 만들었다 (복리)
269가 단기(세션) 죽은 선택지를 뺐더니 **장기가 단일 옵션**이 됐다 — 그래서 에이전트의 접이식
PickerGroup(카탈로그 스케일 대비)이 과투자가 됐고, 노드처럼 **간결한 multi-Select 공용 컨트롤**로
내려도 무손실. 269를 안 했으면 271의 공용화가 "접이식 vs 인라인" 밀도 충돌에 걸렸을 것. **정리
스펙(269)이 그 자체로 끝이 아니라 뒤 스펙의 설계 여지를 넓힌다 — 복리의 실례.**

### 3. 죽은 값은 유실돼도 무해 — 두 번째 같은 판정 (codex Low #1, OUT)
full-replace Select가 레거시 form.memories의 단기(세션)을 편집 시 떨굴 수 있으나, 엔진이 무시하는
죽은 값이라 효과 0 → OUT. 269 codex High(파이프라인 유도가 죽은 값 드롭)와 **동일 판정**. 같은 결함
클래스가 다른 표면(유도 필드 → full-replace Select)에서 재등장하면 같은 정직 경계로 닫는다(재판정 비용 0).

### 4. UI 구조가 바뀌면 그 구조를 검증하던 테스트가 낡는다 — 불변식은 유지
271이 직접 폼 기억을 PickerGroup collapse → 공용 컨트롤로 바꾸자 269 e2e의 collapse 헤더 단언이 깨짐
(기능 회귀 아님, 테스트 노후). 불변식(단기(세션) 미노출)은 그대로라 **테스트를 새 구조에 맞춰 갱신**
(collapse 펼치기 → 장기 Select 옵션 검사). **UI 리팩터는 형제 스펙의 테스트를 낡게 하므로, 불변식은
지키되 셀렉터/구조 단언은 같은 턴에 갱신**(안 하면 다음 회귀 실행이 거짓 빨강).
