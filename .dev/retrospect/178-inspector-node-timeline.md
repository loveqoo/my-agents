# 회고 178 — 인스펙터 개편: 자원축 → 단계(노드) 실행 타임라인 (스펙 192)

## 무엇을 했나
실사용 문의: 인스펙터가 "메모리/문서검색/MCP/브로커"를 **자원 종류별 섹션**으로 요약해, 사용자가 정작
보고 싶은 **"어느 단계에서 무엇을 어떻게 호출했고 결과가 어땠나"**가 안 보였다. 축을 뒤집어 **노드 축**
(antd Timeline 스파인)으로 완전 대체 — 시작→모델 호출→도구·문서 검색 실행→…→종료 순서로, 각 노드에
그 단계의 이벤트(회상 쿼리·검색어·히트·도구 결과)를 붙였다. RAG는 **커트라인 미달로 못 쓴 문서**까지
회색 표시. 드로워 비좁음은 탭(실행 흐름/프롬프트·설정)+전체화면 Modal(90vw)로 해소. 단위(191 확장)+
e2e 15/15+무회귀(191 e2e 12/12·tsc0).

## 배운 것

### 1. 축을 뒤집는 개편은 대개 "새 데이터"가 아니라 "이미 있는 신호의 재조립"이다
"단계별로 보여줘"라 백엔드에 노드별 이벤트 로그를 새로 심어야 할 것 같았지만, 신호는 **이미 다 있었다**:
브로커 호출은 `brokerCalls[].node`(=`broker_invoke:rag:X`)를 이고 있었고(스펙 130), 직접 경로는 합성
그래프가 `retrieve_memory→tools→model` **선형**이라 이벤트를 **타입으로** 노드에 귀속할 수 있었다(회상
→retrieve_memory, rag/mcp→tools). 프런트 순수 함수 하나(`nodeEventContent`)로 재조립 끝. **교훈:
"보여주는 축을 바꿔달라"는 요구는 먼저 "그 축의 근거가 이미 trace에 실려 있나"를 본다 — 있으면 표시
계층만 바꾸는 값싼 작업이고, 백엔드는 안 건드린다. 없을 때만 계측을 심는다.** (여기선 딱 한 곳만
백엔드가 필요했다 — 2번.)

### 2. "드롭"은 증거를 지운다 — 필터를 검색 코어에서 소비 경계로 옮겨 "안 쓴 것"을 남겨라
유일한 백엔드 변경: 커트라인 필터(`_apply_min_scores`)가 미달 히트를 **버려서** trace에 안 남아 "이 문서를
커트라인 미달로 **못 썼다**"를 보여줄 수 없었다. 고민의 핵심은 "필터 의미(에이전트는 미달 문서를 안 봄)를
지키면서 디버거에겐 다 보여주기". 답은 **필터를 검색 코어에서 소비 경계로 이동**: 코어는 `_annotate_cutoffs`
로 `belowCutoff`/`cutoff` 플래그만 **부착**(드롭 안 함), 에이전트에게 가는 결과만 `used_hits`로 통과분을
거른다. trace의 hitsDetail은 전부(플래그 포함). **교훈: "필터"를 "버리기"로 구현하면 왜 버렸는지를 못
보여준다. 판정을 데이터에 플래그로 남기고, 걸러내기는 그 데이터를 쓰는 지점(에이전트 입력)에서 하라 —
"에이전트가 보는 것"과 "디버거가 보는 것"을 분리하면 필터 의미는 그대로 두고 관측성만 는다.**

### 3. 노드 이름은 스펙 가정 말고 실 trace로 맞춰라 — 스샷이 잡았다
`call_model` 노드에 라벨을 매핑했는데, 실제 LangGraph 노드는 `model`이었다(+`agent`도 가능). e2e는
초록이었지만(내용 텍스트는 맞음) **스크린샷에 raw "model"이 라벨 없이** 떠서 알았다. 스펙 설계 문구
("call_model")를 코드 상수로 그대로 믿은 것. **교훈: 노드명·enum 같은 "실행이 정하는 값"은 설계 문서가
아니라 실 trace(스샷/로그)로 확인한다. 표시가 어긋나도 텍스트-매칭 e2e는 통과할 수 있어 — 눈으로 본
스샷만이 라벨 누락을 잡는다.** ([[verify-ui-in-browser-proactively]]·[[probe-deeper-before-concluding]] 재연)

### 4. 재구성 개편은 기존 렌더 컴포넌트를 스파인에 다시 꽂는 일 — 새로 그리지 않는다
HitCard·McpCall·MemoryRow·ScaleLegend를 자원 섹션에서 **떼어내 노드 상세로 재배치**했을 뿐, 새 렌더러는
거의 안 만들었다(HitCard에 `belowCutoff` 회색 분기 한 줄, 브로커 카드 1개 추출). 낡은 섹션·GraphPath는
삭제. **교훈: "축을 바꾸는" UI 개편은 픽셀을 새로 그리는 게 아니라 기존 조각을 새 뼈대에 재조립하는 것 —
컴포넌트를 잘게 쪼개 뒀으면(스펙 191의 HitCard 등) 개편 비용이 재배치로 떨어진다. 삭제한 옛 경로는
dead code로 남기지 말고 그 턴에 지운다(GraphPath·GraphNode import까지 tsc가 잡음).**

### 5. "이미 다른 데 있으니 생략"은 그 '다른 데'가 **나란히 보일 때만** 참이다 (후속 문의)
개편 직후 사용자가 짚었다: plan 노드는 계획 문자열이 나오는데 execute 노드는 "메시지 1건"만. 원인은
스펙 086이 `messages`만 "채팅에 이미 스트림됐으니 중복 방지"로 건수만 낸 것 — 설계 당시엔 합리적 절약
같았다. 하지만 인스펙터 타임라인과 채팅 버블은 **다른 패널**이라, 사용자가 타임라인을 볼 때 채팅 응답은
시야에 없다. 즉 "중복"이 아니라 **부재**였다. 게다가 노드 종류에 따라(plan=보임/execute=카운트) **정보
비대칭**이 생겨 "왜 얘만?"이 바로 눈에 띄었다. **교훈: "X는 이미 Y에 있으니 여기선 생략"이란 절약은
"사용자가 이걸 볼 때 Y도 같은 화면·같은 순간에 보이나?"를 확인해야 참이다. 다른 패널·다른 탭·스크롤
바깥이면 생략은 절약이 아니라 은닉이다. 특히 형제 항목 일부만 펼치면(plan은 원문·messages는 카운트)
비대칭이 사용자에게 "버그처럼" 읽힌다.** 봉합=messages도 role+프리뷰(짧은 캡·마스킹 유지), verify_086
계약 재작성(빨강≠회귀 — 4번의 dead-code 삭제와 같은 "의도된 변경이 테스트를 깬다" 재연).

## 다음에 적용
- 표시 축 변경 요구: 근거가 이미 trace에 있나 먼저(있으면 표시계층만, 백엔드 무접촉)(1).
- "다른 데 있으니 생략"은 그 다른 데가 같은 화면·순간에 보일 때만 참(다른 패널이면 은닉); 형제 일부만
  펼치면 비대칭이 버그처럼 읽힘(5).
- 필터/컷오프: 버리지 말고 플래그로 남기고 소비 경계에서 걸러라(관측성=에이전트뷰≠디버거뷰)(2).
- 실행이 정하는 값(노드명·enum): 스펙 문구 말고 실 trace/스샷으로 확정(텍스트 e2e는 라벨누락 못 잡음)(3).
- 재구성 개편: 기존 컴포넌트 재배치+dead code 즉시 삭제(4).
