# 326 — 스펙 398 회고: shared.py 소멸 — 파사드가 아니라 해체가 답인 경우

## 무엇을 했나

8회전. rag/shared.py(663줄·C급 0·MI 34.3)를 **파사드 없이 소멸** — 7개 응집 모듈로 해체하고
내부 4형제를 직접 재배선. 평면 표면(api.rag.X)은 __init__ 승격 루프가 자동 보존(구 shared dir
60심볼 누락 0 — codex 실측). 표적 verify 6종·suite 51/51, codex 적대 코드 발견 0건.

## 배운 것

1. **파사드는 계약 보존 수단이지 기본값이 아니다.** 6회전까지는 외부 소비자가 많아 파사드가
   정답이었지만, shared.py는 소비자가 패키지 내부뿐이라 "파일명만 바꾸면 잡탕 계약이 그대로
   남는다"(codex) — 같은 루프라도 소비자 지형이 처방을 가른다. 판단 기준: **외부 계약의
   두께**를 Context 단계에서 먼저 재고, 얇으면 소멸+재배선.
2. **C급 0이어도 리팩터 가치가 있다** — 이번 대상은 복잡도가 아니라 응집도(서로 다른
   상태기계의 동거)와 이름("shared"가 경계를 속임)이 문제였다. 게이트 수치는 필요조건이지
   충분조건이 아니다.
3. **승격 루프 패키지의 표면 보존은 공짜다** — __init__이 dir() 승격을 쓰는 패키지는 새 모듈을
   루프에 넣는 것만으로 평면 표면(우연 노출 포함)이 유지된다. 검증은 "구 dir ⊆ 신 dir 합집합"
   집합 비교 한 줄(codex가 실측한 방식 — 다음 소멸형 리팩터의 표준 검증).
4. **suite 실패의 판정 속도가 빨라졌다** — 실패 시그니처(historyRestore=None+창 0)에서 "1턴
   미영속→재개 접힘"을 읽고 변경 축과 무관함을 가설로 세운 뒤 재실행 판정(51/51). 시그니처
   해석→축 대조→재실행이 이제 정형 절차.
5. **적대 리뷰가 랜딩 상태까지 본다** — codex가 스테이징 상태(신규 untracked)를 P2로 경고.
   중간 리뷰 시점의 git 상태도 리뷰 대상이라는 것 — 커밋 단위가 곧 동작보존의 단위.

## 다음에 다르게

- Context 단계 체크에 "외부 계약 두께 측정"(파사드 유지 vs 소멸 판단 재료)을 명시.
- 소멸형 리팩터의 표면 검증은 dir 집합 비교로 표준화.
