# 239 — 플랜 데모 노드형 전환: 하드코딩 flow → 노코드 등가 재구성 (스펙 264)

## 맥락
사용자: "플랜 실행 데모를 노드형으로 바꾸고 동작을 테스트해보라." 코드 flow(`plan_execute` impl)로
돌던 plan-execute-demo(v5·실모델 qwen3.6-35b·web-fetch·단기기억)를 노드형(impl=pipeline) 2노드로
전환하고 실모델로 끝까지 검증(ALL GREEN).

## 무엇을 배웠나

### 1. 노코드 전환이 기능을 깎지 않고 올릴 수 있다 — 결정적 하드코딩이 모델 승격
원 plan 노드는 하드코딩 계획 문자열(모델 호출 없음). 노드형은 노드=모델 호출이라 계획 노드가 **진짜
계획을 세우게 됐다**(질문 맞춤 3단계 계획 생성, 실측 +2.4s). "노코드=열화"가 아니라 이 경우 승격.
등가 재구성 시 원 flow의 각 노드가 결정적인지 모델인지 성격부터 확인하고, 결정적 노드는 (a) 모델로
승격하거나 (b) 프롬프트에 상수로 접거나를 선택해야 한다 — 여기선 (a)가 데모 취지(계획 수립 시연)에 맞았다.

### 2. 전환 테스트 전에 인프라부터 ping — 실패의 귀속을 깨끗하게
실모델(qwen3.6-35b, :8045)이 죽어 있으면 chat 실패가 "노드형 버그"처럼 보인다. 전환 전에 모델
서버를 ping(API key required 응답 = 살아있음 확인)해 실패 귀속을 미리 갈라놨다. probe-deeper의
사전 버전: 탓하기 전에 환경부터.

### 3. 행동 차이는 그린이어도 기록한다 — 중간 노드 출력이 응답에 섞임
원 데모는 plan이 무토큰이라 사용자 응답=실행 답변뿐. 노드형은 모든 노드 출력이 스트림돼 계획(1.2.3.)
이 최종 답 앞에 그대로 보인다. 테스트는 전부 그린이지만 이건 **행동 차이**다(투명성이자 잡음).
learning 060(통합은 폐기 경로 행동을 자동 승계 안 함)의 변주: *전환은 원 구현의 행동 집합을 자동
보존하지 않는다* — 전환 후 "무엇이 달라졌나"를 행동 축으로 대조하고, 그린이어도 차이를 기록. →
"마지막 노드만 응답으로" 옵션을 백로그에.

### 4. 실모델 검증은 mock이 못 보여주는 것을 보여준다
mock으로는 계획 노드가 "canned 응답"만 내 계획 품질·페르소나 스타일 발현(한 줄 선답+인용)·노드별
실측 시간(+2.4s/+2.3s)을 볼 수 없었다. 저작·왕복·격리는 mock으로 충분했지만(259-262), **"진짜
쓸만한가"는 실모델 한 번이 갈랐다**. 143(mock이 메모리 추출을 무너뜨림)과 같은 축 — 검증 사다리에서
mock rung과 실모델 rung은 다른 결함을 잡는다.

### 5. 버전 시스템이 전환 실험을 싸게 만든다
v5(코드 flow) 보존 + v6(노드형) 활성 — 실패해도 revert 한 번. 파괴 없는 실험 통로가 이미 플랫폼에
있어(스펙 007 버전 상태머신) 전환 결정이 가벼웠다. 도그푸딩이 플랫폼 자산의 복리를 재확인.
