# 242 — 캐싱 프록시가 양자택일을 없앴다: 사용자 설계의 구현 (스펙 268)

## 맥락
노드별 RAG·메모리 요청에 내가 "1회 조회→노드 매핑 vs 노드별 키워드 조회" 양자택일로 초안을 냈고,
사용자가 **캐싱 프록시**로 통일하는 설계를 제안: "노드는 각자 조회, 같은 키워드는 프록시가 캐시".
승인 후 P1(컬렉션별 RAG 도구)+P2(프록시)를 구현, 실모델+실 mem0로 캐시 공유까지 실측(ALL GREEN).

## 무엇을 배웠나

### 1. 좋은 설계는 선택지를 잘 고르는 게 아니라 선택 자체를 없앤다
나는 두 방식의 트레이드오프(비용 vs 유연성)를 비교해 v1/v2로 나눴다. 사용자는 **메커니즘 하나**
(키워드 캐시)로 두 방식이 자연히 공존하게 했다 — 같은 키워드면 비용이 1회로 *수렴*하고, 다른
키워드면 개별 조회가 *허용*된다. 트레이드오프처럼 보이는 것이 실은 캐싱으로 해소되는 경우가 있다.
"A vs B로 갈리는가?"보다 "A와 B를 모두 담는 메커니즘이 있는가?"를 먼저 물을 것.

### 2. 주입 선례(브로커)가 새 주입을 싸게 만든다
"엔진은 주입물만 읽는다"(085) 계약에서 *호출 가능한 것*을 주입하는 선례가 브로커였다. 회상 프록시도
같은 모양(스코프 플랫폼 고정 → RBAC 보존, 엔진은 핸들만) — 설계 논의 없이 슬롯 하나로 끝났다.
아키텍처 패턴의 복리: 첫 사례를 계약으로 잘 깎아두면 둘째부터는 "같은 모양"으로 충분.

### 3. 프록시 경유는 관측을 공짜로 준다
모든 조회가 한 지점을 지나니 (노드·키워드·건수·캐시 여부) 기록이 자동 — 082(조회 행위 계측)와
266(기록+표면)을 별도 작업 없이 충족했다. 관문(choke point)을 만들면 캐싱·관측·정책이 다 그 자리에
얹힌다.

### 4. e2e 실패가 코드가 아니라 데이터 시맨틱을 가르쳐줬다
recalls=0 실패 → 게이트 프로브 → `memory_enabled(['단기(세션)'])==False`: mem0 회상은 `장기 기억
(mem0)` 블록 전용이고 단기는 회상 게이트가 아니었다(직접형과 동일 규칙 — 코드 버그 아님). 픽스처를
올바른 블록으로 바꿔 통과. 실패의 계층 판별(코드 vs 데이터 시맨틱)이 이번에도 먼저였고, 이 시맨틱을
스펙에 "주의"로 기록했다 — UI에서 단기만 고른 노드가 조용히 회상 없는 함정은 후속 개선 후보(예:
장기 미선택 시 안내).

### 5. 이번 축도 "기록+표면+실발화" 3층을 처음부터
264-266의 사흘 연타 교훈을 이번엔 선제 적용: 단위(프록시 카운터·엔진 sys 계측) → 실모델 e2e(캐시
공유 cached:true를 트레이스로 단언) → 인스펙터 귀속 카드까지 한 번에. 지적받기 전에 3층을 계획서에
넣었다(스펙 268 검증 계획) — 회고가 행동을 바꾼 사례.
