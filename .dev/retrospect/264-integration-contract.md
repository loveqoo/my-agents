# 264 — 연동 계약 정비 (스펙 289)

## 무엇을 했나

288 스위트가 드러낸 "외부 클라이언트가 연동을 포기할 전제조건" 3건을 플랫폼 계약으로 승격.
- **P1**: 히스토리 서버 재구성 — 재개 세션 + assistant 없는 body면 서버가 DB 대화를 이어붙임
  (auto 판정, 플레이그라운드=클라 모드 무회귀). LIMIT 조회(캐시 없음 — 실측 5ms/2건), trace.historyRestore.
- **P2**: 노드형 풀 서버 파생 — derive_pipeline_pool을 저장(생성·수정)+로드(오버라이드 포함) 양쪽에.
  폼 파생과 동일 규칙이라 멱등. 스위트 픽스처가 풀 미지정으로 실증.
- **P3**: 위임 상태 표면화 — 정적 마커("미서빙 — 위임 불가")는 스펙 257이 이미 보유(확인만),
  동적 사유는 plan 노드 delegationNote(후보 0=미부여/미서빙, 선택 0=발견 실패)로 타임라인에.

## 잘된 것

- **사용자의 연동자 관점 질문이 방향을 결정했다** — "그런 클라이언트는 우리밖에 없다", "잘 만든
  쓰레기가 될까 걱정". 업계 관행 두 층(원시 API=클라 재전송 vs 에이전트 플랫폼=세션+새 메시지)을
  갈라 설명하니 결정이 빨랐다. 캐시 질문도 실측 근거(턴 5~30s vs 조회 5ms, 다중 프로세스 무효화
  위험)로 "안 넣는다"에 합의 — 결정을 스펙에 근거와 함께 박제.
- **어제 만든 스위트가 즉시 회귀망으로 작동** — P1 구현 5분 만에 프로브로 실증, 시나리오 5개 추가
  (서버/클라 모드·노드형 승계·타 유저 적대·DB 재구성), P2는 픽스처에서 풀을 지우는 것 자체가 증명.
- **재개 경로의 선례 재사용** — _load_session_conversation이 이미 있어 P1의 새 코드는 판정 블록
  하나+LIMIT 파라미터 수준.

## codex 적대 라운드 (Med 5 · High 0 · 보안 No Finding 3)

- **판정 규칙은 "부재 조건"이 아니라 "계약 형태 그 자체"로** — 1차안 "assistant 부재"는 빈 배열
  (재구성분만으로 직전 턴 재실행)·user-only 누적(이중 카운트)·assistant 위조(모드 오판) 세 방향에서
  뚫렸다. "정확히 user 1개"(=계약이 말하는 '새 메시지' 형태)로 조이니 셋 다 소멸 — 휴리스틱을
  고를 때 "무엇이 없으면"보다 "계약이 정의한 형태와 일치하면"이 강하다.
- 민이름 매칭 전역 유일 조건(#4 수용), _safe_name 절단 충돌(#5)은 전역 네이밍 이슈로 백로그.
- 보안 축(타인 세션 유출·A2A 파급·delegationNote 누출)은 No Finding — 재구성을 세션 해석(소유권
  fold) **뒤에** 둔 구조 덕분(설계 단계에서 경계를 상속받는 위치 선택이 방어의 대부분).

## 배운 것

- **실측 발견도 오귀인될 수 있다 — 원인 축을 하나씩 갈라 재검증하라.** 288 때 "위임엔 이름 토큰
  필요(lexical)"라 적었지만, 진짜 원인은 미서빙 게이트였고 lexical 탈락은 ranked 전략에만 존재
  (FirstMatch는 첫 후보 무조건 위임). P3 시나리오를 만들다 재검증에서 걸렸다 — 발견 기록에도
  "어느 게이트가 접었나"를 분리 실측해야 한다.
- **UI의 의도된 숨김(타인 private, 스펙 147)과 검증 픽스처의 소유자가 충돌한다** — suite 픽스처
  (suite principal 소유)는 관리자 UI 목록에 안 뜬다. 브라우저 검증은 관리자 소유 임시 픽스처로.
- **in-process 러너의 lifespan 부채는 누적된다** — 체크포인터(288)에 이어 authz(289 적대 시나리오).
  새 부팅 초기화가 생기면 스위트 러너에도 추가하는 것까지가 한 단위.
