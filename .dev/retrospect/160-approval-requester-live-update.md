# 160 — 승인 후 요청자 채팅 자동 갱신(멈춤 버그)

**스펙**: docs/spec/179 P3 · **관련**: 회고 159(mock 트리거), 스펙 041/177(승인)

## 무엇을 했나
2브라우저 실사용 제보로 드러난 버그: 브1 삭제요청→브2 승인→**브1이 "승인 대기"에 멈춤**. 백엔드는
승인 시 재개·결과 영속하나 대기 중 요청자 채팅엔 라이브 push가 없었다(§7 빚). `onApproval` 콜백 +
승인 상태 폴링 + 세션 재로드로 요청자 채팅이 승인 후 자동 갱신되게 했다.

## 무엇이 잘못됐고 무엇을 배웠나

### 1. 트리거하는 쪽만 검증하고 결과를 경험하는 쪽을 안 봤다 (핵심)
스펙 179 e2e에서 나는 "채팅→승인대기→**승인 페이지 큐 비워짐**"까지만 확인하고 통과 선언했다. 정작
사용자가 겪는 **요청자 채팅의 재개**는 안 봤다 — 그래서 "멈춰 있다"는 실제 버그를 못 잡았다. 승인은
두 주체(요청자·승인자)가 있는데 나는 승인자 관점만 초록으로 만들었다.

- **처방**: 상호작용 검증은 **결과를 경험하는 주체의 최종 상태**까지 본다. 승인이면 승인자 큐가 아니라
  **요청자가 완료를 보는가**가 완료조건. "동작을 일으키는 쪽"과 "결과를 받는 쪽"이 다르면 후자를
  단언하라. (사용자에게 "됩니다"라고 두 번 확언했다가 두 번 정정 — 검증 대상을 잘못 골랐다.)

### 2. status 플래그가 아니라 실제 데이터 변화에 게이트하라 (TOCTOU)
첫 수정은 `listApprovals`의 `status != pending`을 보고 즉시 세션을 재로드했다 → **빈 세션**이 떴다.
원인: `resolve`가 status를 **먼저** approved로 커밋한 뒤 서버사이드로 재개·persist를 한다. status만
보면 persist 완료 전(레이스 창)에 재로드해 0건을 그린다. DB엔 결국 2건 영속되지만 타이밍이 어긋났다.

- **처방**: "완료됐나"를 **부수 플래그**로 판정하면 그 플래그와 실제 부수효과 사이 창에 걸린다.
  **결과 자체의 관측 가능한 변화**(세션 메시지 수 baseline 대비 증가)에 게이트해 persist 완료 시점에만
  반영. [[gate-on-intent-value-not-mutable-baseline]]와 같은 결(가변 플래그 대신 진짜 상태로 판정).

### 3. 어서션이 성공 상태 고유 문자열을 겨냥해야 (false green 재발)
레이스 수정 전, e2e가 `/mock-llm/`로 성공 판정해 **빈 세션인데도 통과**했다 — "mock-llm"이 헤더 모델
배지라 항상 존재. 성공 상태에만 있는 문구(응답 본문 "결정적 mock 응답")로 바꾸고, 실패 상태(승인 대기·
"불러올 메시지가 없")를 명시적으로 배제하니 그제야 레이스를 잡았다. 어서션은 **성공에만 참인 신호**로.
(회고 159의 "테스트 더블이 라이브와 달라 false green"과 형제 — 이번엔 어서션이 헤더 노이즈를 짚음.)
