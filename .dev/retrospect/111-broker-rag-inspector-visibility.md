# 111 — 회고: 조율형 RAG 검색 표면화 (스펙 130)

## 무엇을 / 왜
사용자: "조율형이 RAG 검색을 안 한다." **진단 먼저**(deep-reasoner e2e) — 검색은 실제로 동작(라이브
트레이스에 broker_invoke:rag:Obsidian + 답변이 데이터 인용), 진짜 문제는 (1) 인스펙터가 브로커 경유
RAG를 안 보여주는 **표시 구멍**, (2) 약한 히트로 "자료에 없음" 답이 "검색 안 함"으로 오인. 처방:
RagProvider raw에 hits/topScore 구조화 → 브로커 이력 통과 → trace.brokerCalls → 인스펙터 RAG 섹션에
"rag:X · 검색 N건 · 최고 유사도 0.NNN"(+관련도 낮음/0건/실패 태그).

## 잘된 것
- **고치기 전에 진단으로 증상을 갈랐다**: "안 돈다"는 신고를 브로커 층 프로브(내가)+e2e 추적
  (deep-reasoner)으로 반증하고, 인식된 증상의 근인(표시 구멍)을 특정 — 기능 층을 헛수리하지 않음.
  진단이 곧 스펙이 됐다(관측성 처방, 125와 같은 결).
- **codex가 "부분 표면화" 구멍을 잡음**: 스펙이 승인대기/재개 경로를 OUT으로 뒀는데, 표면화가 목적인
  스펙에서 일부 경로만 보이면 **새 사각지대**가 된다(P2 ×2) — 셋 다 주입하고 투영 화이트리스트를 헬퍼
  하나로 통일(122 "모든 소비 표면 전파"의 트레이스판). + topScore 부재 시 0.000 오표시(P3)도 수정.
- **e2e가 사용자 시나리오 그대로**: fast-worker가 실제 옵시디언 매니저에 실제 질문 → 인스펙터 확인
  (프로브와 같은 4건·0.850). 첫 실행의 셀렉터 오탐(상시 존재하는 "인스펙터" 토글에 매칭 → 스트리밍
  중 조기 통과)을 트레이스 칩 폴링으로 스스로 교정.

## 아쉬운 것 / 리스크
- 스펙 초안이 pending/재개를 OUT으로 선언한 판단 — "표면화 스펙의 부분 적용은 목적 훼손"을 codex가
  지적하기 전엔 못 봄. 표면화/관측성 스펙은 **경로 전수**가 기본이어야.
- e2e가 스로어웨이 세션 2건 생성(저비용, 미정리 수용). 조율형 응답이 예상(60~120s)보다 훨씬 빨랐음
  (2.7s) — 로컬 모델 성능 추정이 보수적이었다.
- 관련도 낮음 임계 0.5는 RetrievalTestPanel green 임계 차용 — 실사용 보정은 후속.

## 다음 작업 Context에서 상기할 것
- **사용자 버그 신고 = 인식된 증상일 수 있다** — "안 돈다 vs 안 보인다"를 진단(층 격리+실 트레이스)으로
  먼저 가른다. 동작하지만 보이지 않는 기능은 사용자에겐 없는 기능.
- **표면화/관측성 스펙은 경로 전수**(메인/승인대기/재개) — 일부만 보이면 새 사각지대. 투영 로직은
  단일 헬퍼로.
- 표시용 수치는 **실측일 때만 렌더**(없으면 생략 — 0.000 오표시 금지).
- 참고: learning 130, 회고 106(125 관측성), learning 122(모든 표면 전파).
