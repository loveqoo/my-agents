# 308 — 검색 히트→즉시 편집 진입 (스펙 333)

## 무엇을 했나

사용자 제안("검색 테스트 결과에서 버튼으로 즉시 수정") 구현 — 수만 줄 논의에서 나온 정밀 진입.
검색 코어 히트에 document_id 동반(additive) + 공용 패널에 hitAction 주입점 + 에디터 locate
(히트 텍스트 선택+스크롤). "검색해 보니 이상함 → 그 자리에서 교정 → 재검색 확인" 동선 완성.
331(편집)·332(엔티티)에 이은 3연작 — 각 층이 앞 층의 시임을 그대로 탔다.

## 핵심 배운 것

### 1) 공용 컴포넌트 확장은 "주입점 하나"가 정답이다
RetrievalTestPanel은 컬렉션·메모리 두 도메인이 공유 — 편집 버튼을 패널에 직접 넣으면 메모리
경로가 오염된다. `hitAction?: (hit) => ReactNode` 옵션 주입점 하나로 컬렉션 어댑터만 버튼을
공급하고 메모리는 미전달=무변경. 어댑터 패턴(126)의 결이 확장에서도 유지됨.

### 2) 내부 id를 표면에 실을 땐 "어느 표면까지"를 핀으로 고정
document_id를 SearchHit에 실으면서 확인한 것: 시험 엔드포인트(관리 도구)에는 싣고, 인-챗
trace/브로커 표면(_hits_detail)은 화이트리스트라 안 샌다 — 하지만 그건 "지금 우연히"일 수 있어
**비노출을 테스트로 핀**(H5, codex P3). 권한도 사슬로 확인: 검색=공용(172)이어도 id로 할 수
있는 건 content GET/PUT뿐이고 거긴 may_manage 404-fold(비소유는 id를 알아도 존재 비노출).

### 3) 텍스트 정밀 진입은 "저장 표현의 변주"를 후보군으로
히트 텍스트(디코딩된 유니코드)로 원본 JSONL에서 위치를 찾을 때, 원본이 ensure_ascii 계열이면
비ASCII가 \\uXXXX로 저장돼 indexOf가 실패(codex P2). 후보 3(원문/JSON 내부형/ASCII 전량
이스케이프)+못 찾으면 우아한 강등(그냥 열림). 텍스트 매칭은 "같은 내용의 다른 직렬화"를 항상
의심 — 완벽 매핑(파싱 후 행 매핑)은 과투자라 후보군+강등이 균형점.

### 4) e2e에서 "선택된 채 열림"은 getSelection 실측으로
스크린샷으로는 선택/스크롤이 검증 안 됨 — `window.getSelection().toString()`이 히트 텍스트를
포함하는지 단언. 선택 상태가 곧 UX(insertText가 그 행을 교체)라 기능 단언과 일치.
