# 회고 202 — 별명 폐지: 이름 단독 표시 + alias→description 개명 (스펙 210)

## 무엇을 했나
사용자 UI 정책 10건 배치의 1·7번. 4엔티티(alias 컬럼 rename ×3 + Collection 병합 drop) DB 마이그레이션,
백엔드 44건·프론트 64건 rename(fast-worker 2기 병렬), displayName=name 단일출처 전환, 리스트 툴팁화.
검증=DB 컬럼/병합 실측+API 스모크+브라우저 6단언+구계약 verify 3개 갱신(148 40/40·149 31/31·157 9/9).

## 배운 것

### 1. 표시 데이터의 "박제 사본"은 정책 전환 시 별도 데이터 수선이 필요하다
화면 별명의 마지막 잔존은 코드가 아니라 **세션 행에 박제된 agent_name**(시드가 "Research Assistant"를
심음)이었다. 코드 rename을 아무리 전수해도 비정규화 사본은 안 바뀐다. **교훈: 이름/표시 정책을 바꿀 때는
"참조(FK)로 유도되는 표시"와 "박제된 표시 사본"을 구분해 후자는 데이터 수선(UPDATE+시드 수정)을 체크리스트에
넣는다.** grep 대상은 코드만이 아니라 시드 데이터 문자열도.

### 2. SPA 검증 스크립트의 내비게이션 실패는 가짜 PASS/FAIL 둘 다 만든다
page.goto('/sessions')가 라우팅되지 않아(메뉴 클릭형 SPA) 화면이 안 바뀐 채 단언이 돌았다 — 부정 단언
("별명 없음")은 이전 화면 잔상(툴팁)으로 **가짜 FAIL**, 긍정 단언은 이전 화면의 우연 일치(rag:docs-kb 태그)로
**가짜 PASS**가 났다. 스크린샷 육안 확인이 이를 잡았다(sessions.png가 에이전트 화면이었음). **교훈: 브라우저
단언 전에 "지금 그 화면인가"를 확정하라(헤더 타이틀 단언 또는 기존 하네스의 nav 패턴 재사용). 부정 단언은
특히 화면 오염에 취약하다. 기존 ui-audit의 data-menu-id 클릭 패턴을 처음부터 재사용했으면 안 헤맸다.**

### 3. 계약 변경은 과거 검증 자산의 계약도 갱신 대상으로 센다
표시 계약이 148(별명 우선)→210(이름 단독)으로 뒤집히며 구계약을 단언하던 스크립트 10개가 일괄 stale이 됐다.
파이썬 3개는 갱신(전량 PASS), 브라우저 샷 7개는 시점 검증이라 stale 기록만. 부수로 verify_113이 남긴 DB 오염
(mine_* 잔재 컬렉션)도 발견·청소해 148을 40/40으로. **교훈: 스펙이 기존 계약을 뒤집으면 "그 계약을 검증하던
자산 목록"을 완료 기준에 포함하라 — 안 하면 다음 실행 때 원인 불명 red가 미래의 나를 헤매게 한다.**

## 다음에 적용
- 표시 정책 변경 체크리스트: 코드 rename + 비정규화 박제 사본(시드·기존 행) + 구계약 검증 자산.
- 새 브라우저 검증 스크립트는 기존 하네스(ui-audit)의 nav·로그인 패턴을 복사해 시작(자작 goto 금지).
- 서브에이전트 판단 보류 항목(컬렉션 상시 설명 줄)은 메인이 정책 원칙으로 즉결 — 보류를 백로그로 미루지 않기.
