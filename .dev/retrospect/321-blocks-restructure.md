# 321 — 스펙 393 회고: blocks 해체 — "같은 방식"의 두 번째 회전이 확인한 것

## 무엇을 했나

392와 같은 루프(codex 자문+패턴 리서치→승인→실행→적대 리뷰)로 blocks.py(995줄·MI 21.6·C급 5)를
8개 형제 모듈+92줄 파사드로 해체. 라우트 표면 (method,path,status,name) 24개 diff 0 기계 증명,
suite 51/51, 저장소 C급 61→56.

## 배운 것

1. **방법이 자산이 됐다.** 392에서 만든 루프(자문→습득→계획→적대)를 그대로 재적용하니 2번째
   회전은 마찰이 거의 없었다 — 특히 "동작보존 함정 목록을 계획에 박고 시작"이 이번에도 되돌림 0을
   만들었다. 리팩터 스펙의 템플릿이 사실상 확립됨(진단→구조판단→위험 오름차순→함정→수치 기준).
2. **표면 박제는 도구 버전에 취약하다.** FastAPI 신버전의 지연 include(_IncludedRouter) 때문에
   `router.routes`가 APIRoute를 직접 안 담아 박제 스크립트가 0을 읽었다 — 프레임워크 내부 구조에
   기대는 검증 스크립트는 실측으로 형태부터 확인(original_router 재귀로 해결).
3. **"의미 보존 리팩터"에서 관용구 교체가 의미를 바꾼다.** any-in → set 교집합으로 "더 깔끔하게"
   바꾼 한 줄이 오염 config에서 500을 만들 뻔했다(codex P2 — unhashable). 순수 이동이 아닌
   *개선*이 섞이는 지점이 적대 리뷰의 정확한 타격 지점이었다 — 이동과 개선을 커밋 안에서라도
   구분 의식할 것.
4. **파사드의 재수출 범위는 "공개 표면"이지 "네임스페이스 전체"가 아니다.** 옛 모듈의 잡동사니
   임포트(select 등)까지 재수출하면 파사드가 다시 쓰레기장이 된다 — 소비자 전수 실측(0건)으로
   경계를 정직화하고 주석으로 박제(complement-attack-can-be-honest-boundary의 파사드판).
5. **테스트가 파일 경로/소스 텍스트를 검사하면 분할의 소비자다**(verify_054의 blocks.py 소스
   grep). monkeypatch뿐 아니라 소스-텍스트 단언도 리팩터 시 같은 턴에 갱신 대상.

## 다음에 다르게

- 리팩터 중 "이동+개선"이 한 함수에 섞이면 개선분을 자문 결과와 대조해 별도 확인 항목으로.
- 프레임워크 업그레이드 후 첫 구조 작업에서는 검증 스크립트의 전제(내부 타입)를 먼저 1줄 실측.
