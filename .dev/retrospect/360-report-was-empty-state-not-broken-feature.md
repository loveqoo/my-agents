# 360 — 스펙 437 회고: "안 된다" 보고의 실체는 고장이 아니라 빈 상태의 조용함

## 무엇을 했나

"단순형에 문서·MCP가 안 된다" 보고 → 전수 조사(설정 감사→실모델 재현 매트릭스) → 기능 전 유형
정상 확인 → 실체=빈 데모 컬렉션의 조용한 무히트 → A(정직 메시지+픽커 경고)+B(시드 샘플) 수리.

## 배운 것(전이 가능)

1. **"안 된다" 보고는 고장·설정·빈 데이터 세 갈래로 분해** — 전수 조사 순서가 유효했다: ①설정
   감사(읽기 전용, 빈 tools가 "전체 노출" 설계임을 확인) ②실모델 재현(도구 호출·RAG 배선 실측)
   ③데이터 상태(컬렉션 0건 발견). 기능 검증만 했으면 "이상 없음"으로 닫고 보고와 어긋났을 것 —
   [[probe-deeper-before-concluding]]에 "데이터 상태 축"을 추가.
2. **빈 상태는 기능 고장처럼 읽힌다 — 조용히 두지 말 것** — 검색이 정상으로 돌아도 "찾지 못함"만
   반환하면 사용자는 배선 고장으로 해석한다. 수리=원인을 아는 쪽(런타임)이 정직하게 말하기
   ("컬렉션이 비어 있습니다 — 업로드하세요"). 무히트일 때만 판정해 비용 0.
3. **시드 설명 화석이 오진을 유발** — "샘플 적재됨"이라 쓰고 빈 껍데기만 만들던 시드. 설명과 실물이
   어긋나면 조사 비용이 배가된다(적재 주체가 수동 스크립트였다는 걸 파야 했음). 문구는 코드가 실제로
   하는 일만 말하게.
4. **FE 패치는 브라우저가 판정** — "(비어 있음)" 라벨을 픽커 2곳에 붙였는데 브라우저 검증이 FAIL —
   실제 직접형 픽커는 제3의 컴포넌트(청크 수 부제 렌더)였다. [[ui-verification-must-be-functional]]의
   재확인: tsc 초록≠올바른 표면. 같은 개념의 렌더가 여러 컴포넌트에 흩어져 있으면 grep으로 전 표면
   열거 후 브라우저로 실물 확인.
