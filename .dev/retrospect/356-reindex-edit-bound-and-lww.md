# 356 — 스펙 433 회고: 재인덱싱·편집 유계화 + 삭제 조건이 품고 있던 계약

## 무엇을 했나

432가 인제스트만 고치고 OUT으로 남긴 두 경로(재인덱싱·문서편집)에 같은 패턴(배치 flush+expunge)을
이식 — 재인덱싱 피크 12.5배↓(Δ+2204→+176MB), 편집 5.9배↓(+779→+133MB), 청크 수 동일.
codex가 내가 만든 P1(동시 편집 LWW 파괴)을 잡아 봉합.

## 배운 것(전이 가능)

### 1. `DELETE WHERE <조건>`의 조건 자체가 동시성 계약을 품고 있다

메모리 최적화를 위해 삭제를 `WHERE document_id`(문서 전체) → `WHERE id IN old_ids`(내 스냅샷)로
바꿨다. 기능 테스트는 전부 초록이었지만, **바뀐 건 삭제 범위가 아니라 last-write-wins 계약**이었다:
문서 단위 삭제는 "잠금을 얻은 쪽이 상대가 넣은 것까지 치운다"는 성질로 LWW를 *구현*하고 있었고,
id 지정으로 좁히자 동시 편집 A+B 청크가 공존했다. **범위를 좁히는 리팩터는 "무엇을 덜 지우나"가
아니라 "덜 지움이 어떤 보장을 깨나"로 검토할 것.**

### 2. 미커밋 삭제 + 별도 읽기 세션 = 옛 값과 새 값을 동시에 쓰는 법

"삭제를 먼저 해야 LWW가 보존되는데, 삭제하면 옛 벡터를 못 읽는다"는 딜레마의 해법: 우리 DELETE는
**미커밋**이라 **다른 세션 스냅샷엔 옛 행이 그대로 보인다**. 배치마다 별도 읽기 세션으로 옛 벡터를
끌어오면 두 요구가 동시에 만족된다(대가: 연결 1개 추가 사용). MVCC를 설계 도구로 쓰는 예.

### 3. 같은 부류 후속은 패턴이 손에 있을 때 바로 — 대신 경로별 판단은 다시

432 패턴 이식은 빨랐지만 **경로마다 다른 판단**이 필요했다: 인제스트는 F1 가드를 말미로 옮겨 잠금
시간을 줄인 반면, 편집은 문서 1개라 잠금이 짧아 **선행 유지**(안전 시맨틱 무변경)를 택했다. "같은
패턴"이 "같은 결정"은 아니다 — 각 경로의 규모·잠금 비용을 따로 재야 한다.

### 4. 테스트 픽스처가 불변식을 깨면 red는 코드 탓이 아니다

G4h 첫 실행의 "집계 0 vs 실측 1" red는 내 팬텀 삽입이 collection.chunk_count를 안 올려 **시작부터
불일치**였기 때문. 동시성 시뮬레이션은 "상대가 커밋한 상태"를 충실히(집계까지) 재현해야 한다.

## 흠집

3연속 스펙(430·432·433)에서 codex가 매번 P0/P1을 잡았다 — 공통점은 전부 **동시성/경합 부류**(회로
상태 3상, 재인덱싱 완주 창, 삭제 조건의 LWW). 내 자체 검증은 단일 흐름을 보고, 경합은 상상 밖에
있다. 경합이 얽힌 변경엔 codex를 **설계 단계에** 한 번 더 넣는 걸 고려.
