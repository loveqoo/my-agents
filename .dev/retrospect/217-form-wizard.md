# 회고 217 — 폼 개편은 구조 논의부터: 위저드 4단계와 "요약은 payload를 축소하면 안 된다" (스펙 239)

## 무엇을 했나
사용자 "지금도 어렵다 — 명확하고 간편하게, 계획 논의 열심히" → AskUserQuestion 3라운드로 구조 합의
(위저드 4단계·생성/수정 통합·요약까지 가야 생성/저장·760px 모달) → 순수 표현 개편(데이터 모델 무변경)
으로 구현. e2e 13/13·scenario-audit 7/7. codex가 요약 축소 2건+**위저드 이전부터 있던 실 버그**(조율형
ragMinScores 저장 유실)를 적발 → 수정.

## 배운 것

### 1. "어렵다"는 피드백엔 부분 개선이 아니라 구조 논의가 답이다 — 선택지를 그려서 물어라
238에서 부분 개선(1급 승격·disabled·rich select)을 다 했는데도 "지금도 어렵다"가 왔다. 필드 단위
수선으로는 "결이 다른 결정이 한 화면에" 있는 구조 문제를 못 고친다. AskUserQuestion에 **ASCII
프리뷰로 구조안 자체를 그려서** 비교시키니 논의가 3라운드 만에 수렴(위저드/드로어/점진공개 →
4단계/생성규칙 → 수정저장/그릇). 구조 결정은 사용자가 고르게 하고, 필드 배치는 내가 정한다.

### 2. 요약(확인) 화면은 저장 payload의 부분집합이면 거짓이다 — "확인"의 계약은 전체성
요약 카드를 "현재 종류의 표면"만 보여주게 짰더니 codex가 짚음: 종류를 바꿔도 이전 종류의 연결
(도구·문서·기억)이 **저장은 되는데 요약엔 안 보인다**. 데이터 보존 정책(206)은 옳지만, "이대로
만들어집니다"라는 화면이 실제 저장분을 숨기면 거짓 확인. 처방=숨은 표면도 "보존된 연결(사용 안 함)"
로 표기. **요약·확인 UI를 만들 땐 표시 필드 목록을 저장 필드 전체와 대조하는 체크를 반드시.**

### 3. UI 개편 검증이 그 표면의 잠복 버그를 캐낸다 — 조율형 ragMinScores 유실
위저드와 무관하게, 저장 로직이 vectorTables만 돌아 조율형(capabilities `rag:*`)의 최소 유사도
슬라이더 값이 **UI엔 보이는데 저장서 조용히 유실**되고 있었다(스펙 191 v2 이래). 슬라이더 표시
조건(두 표면)과 저장 순회(한 표면)의 비대칭 — **같은 데이터의 "표시 조건"과 "저장 조건"이 다르면
그 차집합이 조용한 유실 축**. codex에 "표시-저장 대조"를 물은 게 적중.

### 4. 상시 게이트 자산(scenario-audit)은 UI 구조 변경과 같은 턴에 갱신한다
위저드로 바꾸면 "폼 채우고 바로 생성 버튼" 여정이 깨진다 — J1/J2를 같은 턴에 갱신해 7/7 유지.
일회성 shot-* 스크립트(과거 스펙 검증 산출물)는 갱신 대상이 아님을 구분(상시 게이트만 유지 비용을
진다). 갱신 후 실제로 돌려 blocked 0 확인까지가 한 단위.
