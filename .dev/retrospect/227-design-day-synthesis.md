# 회고 227 — 디자인의 날 종합: "보여줄 만한 화면"은 어떻게 만들어졌나 (2026-07-08~09)

## 하루 수준에서만 보이는 것 (개별 회고 224~226이 못 담는 것)

### 1. 품질은 왕복의 밀도에서 나왔다 — 큰 설계 몇 번이 아니라 작은 교정 수십 번
후속 수정 31회+α. 리듬: 사용자 스샷/스케치 → 구현 → **실측**(boundingBox·scrollTop·elementFromPoint)
→ 스샷 회신 → 다음 교정. 왕복당 몇 분. "보여줄 만한 화면"은 이 리듬의 누적이지 어느 한 방이
아니다. 사용자 실기기가 헤드리스 게이트를 이긴 게 3회(vh 가림·비침·닫기 가림) — **왕복 자체가
검증 사다리의 한 런**이다.

### 2. 문법이 축적되자 후반 결정이 즉답이 됐다
오전: 원리 수업이 필요했다(집중→가림→배치, 상태 노출, 요약≠컴포넌트). 오후: "A2A 토글 어디에?"
→ 2줄 칩 문법 적용으로 즉답, "좌측 메뉴 어색" → 탭 규칙 적용으로 즉답. **디자인 시스템이 문서가
아니라 교정 대화 속에서 자랐고, 자란 만큼 논의 비용이 떨어졌다.** 문법 목록: 3층 위계 / 값 있는
컨트롤=인라인·값 없는 도구=한 입구 / canonical 하나(상태·기능) / 2줄 칩(성격별 정렬) / 관심사
전환=상단 Tabs / 은유 먼저(서랍) / 자동 선택은 노출.

### 3. 역할 분업이 명확해질수록 빨라졌다
사용자 = 원리 교사(오전) → 아트 디렉터(스케치·은유) → QA(실기기). AI = 구현·실측·게이트 신설·
회고. 특히 사용자가 **결정**(요약 생략, 계측 상시, 좌측 정렬)을 빠르게 내려줄 때 왕복이 짧았고,
내가 추측으로 메꾸려 할 때(선택지 남발, ASCII 과밀 프리뷰) 왕복이 길어졌다. 모호하면 스케치를
요청하고, 결정거리는 평이한 말로 하나씩.

### 4. 오늘의 실패 패턴도 하나로 수렴한다 — "그 자리만 보고 화면을 안 봄"
중복 5건, 정렬 어긋남, 흰 조각, 무동작 호버 — 전부 컴포넌트를 고립적으로 만들고 화면 단위
확인을 건너뛴 것. 처방은 이미 메모리에(추가 전 grep·전이 후 상태 캡처·이동 실측) — **다음
디자인 작업에선 이 회고와 224~226을 Context에서 먼저 상기할 것.**
