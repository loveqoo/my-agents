# 314 — 사내 CA 지원(OS 신뢰 저장소+파일 방식) (스펙 339·340)

## 무엇을 했나

회사망(TLS 검사) 디바이스에서 위키 검색 등 아웃바운드 HTTPS가 인증서 검증 실패 — 아웃바운드
httpx 11곳을 지점별로 고치는 대신 **truststore.inject_into_ssl() 전역 주입**(pip 방식,
SYSTEM_TRUSTSTORE=1 옵트인 — 기본값은 사용자 결정으로 꺼짐).

## 핵심 배운 것

### 1) 횡단 관심사는 지점 수를 세는 순간 전역 처방을 찾아라
"위키 검색이 안 됨"의 표면 수정은 _wiki_get에 verify= 넣기지만, 같은 문제가 모델 provider·MCP
어댑터·A2A까지 11곳 — CA 신뢰는 프로세스 속성이지 호출 지점 속성이 아니다. ssl 전역 주입이
지점 열거보다 정확하고, 새 아웃바운드가 생겨도 자동 커버.

### 2) 주입은 "컨텍스트 생성 전"이 계약 — 모듈 최상단
inject_into_ssl은 ssl.SSLContext 클래스를 교체하므로 이미 만들어진 컨텍스트는 못 바꾼다.
main.py의 다른 api 모듈 import보다 앞(최상단)에 게이트+주입 — import 순서가 곧 적용 범위.

### 3) 재현 불가 환경은 "계약 검증+무회귀+사용자 실측 대기"로 정직하게 쪼갠다
사내 MITM은 이 맥에서 재현 불가 — 검증을 (a) 주입 성사(V2: SSLContext 클래스 실측),
(b) 무회귀(V3: truststore로 표준 CA 사이트 TLS 실동작), (c) 사내 CA 신뢰=라이브러리 계약,
(d) 최종 실증=사용자 디바이스 대기로 분해해 각각 명시. 125(관측성으로 옮김)와 같은 결.

### 4) stdout/stderr 합치면 "마지막 줄" 파싱이 로그에 밀린다(재발 계열)
V3의 WIKI-OK가 stdout, httpx 로그가 stderr — 합친 문자열의 마지막 줄은 로그였다. 311·312의
"출력 형식 실측" 교훈의 변주: 신호 파싱은 위치(마지막 줄)가 아니라 토큰 포함으로.

## 검증
- VERIFY339_OK 3/3(기본 꺼짐·주입 성사·위키 TLS 무회귀) · lint/mypy 클린 · README/.env.example 안내.
- 사용자 실측 대기: 회사 디바이스 SYSTEM_TRUSTSTORE=1 → 위키 검색.

관련: [[company-integration-context]](회사 층 경계 — 이건 앱 층에서 정당) · 스펙 064(SSRF
allowlist — 신뢰는 CA, 도달은 allowlist로 각자 축)

## 추기 — 스펙 340(EXTRA_CA_FILE, 같은 날)

- 사용자 후속: "인증서 경로 방식 필요" + **정정 두 번**("서버를 https로 띄우는 게 아니라 http
  그대로, 아웃바운드만") — 내 검증 설계(자가서명 HTTPS 대역)가 서버 TLS 전환으로 **오독될 수
  있는 서술**이었다. 재현 장치를 설명할 땐 "이건 외부 사이트 대역이고 우리 서버는 무변경"을
  먼저 말하라(장치와 대상의 혼동은 설명자의 책임).
- 파일 방식은 재현 가능: 자가서명 CA 대역으로 증상(CERTIFICATE_VERIFY_FAILED)→처방(성공)을
  로컬 실증 — 339(OS 저장소)에서 불가하던 검증 축이 파일 방식에선 열린다. **추가 vs 교체**가
  핵심 설계(교체형 SSL_CERT_FILE은 표준 사이트를 깨뜨림 — V5가 핀).
- 439 위키 403은 TLS 성공의 증거(UA 정책·앱 계층) — 상태코드가 아니라 "응답을 받았는가"가
  TLS 검증의 신호.
