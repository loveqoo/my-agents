# 회고 214 — 조용한 무발동을 진단으로: 관찰 불가가 버그를 "미스터리"로 만든다 (스펙 236)

## 무엇을 했나
실사용 사건(다른 기기서 위키 도구가 조용히 무발동 — 사용자가 한 세션 내내 엉뚱한 층 추적) 후속.
(P1) trace.toolDiag(bound/called)로 무발동 턴을 인스펙터에 표면화, (P2) 폼에 mock+도구 사전 경고
(provider_kind 레지스트리 감지), (P3) mock 일반 트리거(문장에 도구 이름 언급→발동)로 임의 도구 실습
가능화. codex 5건 중 3건 수정(단어 경계·비-string required·브로커 턴 억제)·2건 문서화 경계.

## 배운 것

### 1. "왜 안 되는지" 신호가 0인 기능은 고장이 아니라 미스터리가 된다 — 진단은 기능의 일부
게이트(공개·허용호스트·배선)를 다 통과해도 마지막 층(모델)이 조용히 안 부르면, 사용자는 신호가 있는
층만 뒤진다(신호 없는 층은 존재 자체가 안 보임). 회상 진단(158)·검색 진단(125)·이번 도구 진단까지
같은 처방 세 번째: **실패·무동작을 "정상처럼 조용"하게 두지 말고 그 자리에서 "왜 후보"를 표면화**.
새 기능을 낼 때 "안 될 때 사용자가 뭘 보게 되나"를 완료 조건에 넣어야 한다.

### 2. 진단 신호 자체도 오진 축이 있다 — 부착 조건을 소비 선언과 정렬
toolDiag를 모든 턴에 붙이면 route(도구를 설계상 안 읽음)·조율형(브로커 경유)이 "무발동"으로 오진된다.
impl.describe().consumes로 게이트(234의 메모리 게이트와 동형)하고, UI는 brokerCalls 있으면 억제.
**진단은 "사실(숫자)"과 "해석(문구)"을 분리** — called=0은 사실이고, "모델이 안 불렀다"는 해석은
다른 경로(브로커)가 없을 때만.

### 3. 데모(mock)의 능력 한계는 숨기지 말고 (a)선언하고 (b)좁혀라
mock이 임의 도구를 못 부르는 건 설계지만, 그걸 아는 건 코드를 읽은 사람뿐이었다. 처방 둘 다:
(a) 폼에서 사전 경고(레지스트리 provider_kind — 모델명 하드코딩 아님, learning 026), (b) 일반 트리거로
한계 자체를 좁힘(이름 언급→발동, 실습 가능). **한계 공지와 한계 축소는 배타가 아니라 병행.**

### 4. "문자열 in 문자열" 트리거는 단어 경계가 없으면 오발동 폭이 크다
codex가 search⊂research·echo⊂echolocation을 짚음. 길이 컷(4자)만으론 부족 — **단어 경계 정규식**
(`(?<![a-z0-9_])base(?![a-z0-9_])`)으로. 그리고 채울 수 없는 필수 인자(비-string required)가 있으면
잘못된 호출을 만드느니 **트리거를 포기**(invalid args tool_call은 새 미스터리를 만든다 — 진단 스펙이
새 무진단 실패를 낳으면 자기모순).

## 다음에 적용

- 진단 신호 추가 시: 부착 게이트(consumes류)+대안 경로 억제(브로커류)로 오진 축을 먼저 닫기.
- 키워드/이름 매칭 트리거는 단어 경계+채움 불가 시 포기(길이 컷만으론 부족).
