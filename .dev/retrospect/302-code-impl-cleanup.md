# 302 — 하드코딩 에이전트 정리: 코드 정의 impl은 SDK 부류로 (스펙 327)

## 무엇을 했나

사용자 관찰 "`_bootstrap_builtins`의 에이전트들 다 어디 갔죠?" → impl(엔진) vs 에이전트(인스턴스)
두 층을 측정으로 설명 → "범용형이 있으니 하드코딩은 커스텀(SDK) 말고 불필요" → 재설계 합의:
**코드로 정의된 에이전트(SDK 수기·스킬 코드젠)는 한 부류 — UI는 구성을 소유하지 않고(편집 봉인),
플레이그라운드에서 테스트만.** 실행: artifact 데모 2종+targeting-catalog MCP 제거, 시드 plan-execute
데모를 노드형(research-pipeline-demo)으로 교체, 범용 5종 밖 impl의 UI 편집 봉인.

## 핵심 배운 것

### 1) 사용자의 "다 어디 갔죠?"는 분류 부재의 신호였다
등록된 impl 8종에 아무 분류가 없어 SDK 레퍼런스(plan_execute)·코드젠 템플릿(route)·전략 변형
(orchestrate_ranked)·죽은 데모(artifact 2종)가 한 목록에 섞여 있었다. 질문에 답하려 만든 표(impl별
폼 노출·사용처)가 그대로 재설계의 재료가 됐다 — **"어디 갔죠?"에 측정으로 답하면 다음 설계가 공짜로
따라온다.** 기존 원격 code 에이전트의 "읽기 전용, 구성은 코드가 소유" 원칙을 인프로세스에 확장한
것뿐이라 새 개념 0.

### 2) 편집 봉인은 "밀어 넣기" 방어 장치까지 함께 걷지만 — 변형은 남는다
UI 편집을 안 열면 AgentForm의 exotic impl 옵션 폴백(323~327 대화에서 사용자가 물었던 그 세 줄)도
불필요해진다. 그런데 **전부 걷으면 안 됐다** — `orchestrate_ranked`는 범용(편집 가능)이면서
AGENT_TYPES 밖이라 폴백이 지탱하고 있었다. "이 방어 장치는 이제 죽었다"고 걷기 전에 **그 장치가
지탱하는 사례를 열거**해야 한다(조율 변형만 남기고 exotic 분기만 제거).

### 3) 목록이 안 보이는 세 이유를 순서대로 소거 — 스크롤/필터/가시성/staleness
UI 검증에서 probe 에이전트가 목록에 안 떠 3번 실패: ①suite 에이전트는 타인 소유라 기본 숨김(스펙
147 — 검색해도 0/14) ②새로 만든 에이전트도 안 뜸 — **목록이 앱 마운트 시 1회 로드라 stale**(리로드
필요) ③상세→목록 복귀는 메뉴 재클릭이 안 먹어 리로드로. 브라우저 검증 스크립트는 "데이터가 화면에
왜 없는가"의 원인 사다리(권한 가시성→로드 시점→네비 상태)를 알고 있어야 헛짚지 않는다.

### 4) 전환 잔재는 전환 스크립트의 사각 — 노드 도구명 반쪽 접두사
dev DB의 plan-execute-demo(수동 전환분)는 노드1은 `web-fetch__wiki_search`(정상), 노드2는
`wiki_search`(민이름 — 도구 필터에 안 걸려 **바인딩 0인 잠재 결함**)였다. 시드 교체 김에 둘 다
런타임명으로 통일하고 virgin DB 검증(S1d)에 "전부 런타임명" 단언을 박았다. 수동/스크립트 전환은
같은 필드를 두 곳에서 만들면 반쪽 드리프트가 남는다 — 전환 후 형식 불변식을 측정하라.

### 5) codex 3발견 — 봉인·정리·테스트의 여집합
① **"편집 봉인"을 canManage 하나에 합치면 과봉인**: 코드 정의 게이트를 canManage에 얹었더니 삭제·
공개 전환·활성화·운영까지 숨어 목록(삭제 보임)과 비일관 — 구성 편집(canEdit)과 인스턴스 관리
(canManage=소유권)는 **다른 축**이라 분리. ② **reconcile은 추가·동기화만 알고 제거를 몰랐다**:
_DEFS에서 정의를 지워도 기존 설치의 custom 행은 고아로 잔존(served_url 404 → 조용한 도구 0) →
reconcile에 "레지스트리 밖 custom 행 삭제(단, 배선 중이면 보존)" 추가 + throwaway 검증(S5a/S5b).
정의 카탈로그의 생애주기는 add/sync/**remove** 세 동사가 한 벌. ③ **기능 제거=그 verifier까지**:
154/155(시드 이름)·188(제거된 데모가 검증 수단)·233(impl 목록)이 낡음 — 188은 뼈대 커버리지를
**테스트 전용 서브클래스로 이전**해 프로덕션 데모 없이 유지(기능은 지워도 뼈대 계약 테스트는 산다).

### 6) 내부 키는 폴백 경로로 샌다
typeLabel의 폴백이 `impl || '직접 응답'`이라 미지 impl은 내부 키(`route`)가 태그로 그대로 노출됐다
(스펙 108 위반 — 정상 경로는 다 감쌌는데 **폴백이 누출 경로**). '코드 정의'로 접었다. 사용자 언어
정책은 happy-path 매핑만이 아니라 폴백·에러 경로까지 검사해야 완성.
