# 회고 189 — 플랜 에이전트 도구-인지 (스펙 202, 사용자 아키텍처 문제 제기)

## 무엇을 했나
사용자 지적("공통 클래스 구현이면 도구 연결이 동작해야") → 조사: 계약(ctx.tools)은 이미 도구를
주입하고 있었고 PlanExecuteAgent 예제가 버리고 있었음. 처방: plan은 결정적 유지+계획에 도구 반영,
execute는 bind_tools+ToolNode 표준 루프(필요할 때만 호출 — 사용자 결정), 적합성(089)에 "도구
가용성" rung(T1/T2). 사용자 재현 경로에서 plan 노드가 도구를 계획에 올리고 wiki_search 실호출 확인.

## 배운 것

### 1. Protocol 계약은 "주입받는다"까지만 강제한다 — "소비"는 적합성 검사로 별도 강제해야
계약 설계는 옳았다(플랫폼이 ctx.tools 주입). 그런데 Protocol은 시그니처만 검사하므로 **구현이 주입을
통째로 버려도 조용히 합격**한다 — 노코드 계약("설정=동작")은 인터페이스만으로 성립하지 않는다.
**교훈: "플랫폼이 X를 준다"를 계약이라 부르려면 "구현이 X를 배선한다(또는 안 씀을 선언한다)"를
적합성 rung으로 검사해야 한다 — 인터페이스는 형태를, 적합성 검사가 의미를 지킨다.** (산출물형처럼
조상이 골격을 소유하면 이 문제가 구조적으로 사라진다 — 후속 방향.)

### 2. 사용자 뉘앙스("무조건 말고 필요하면")를 검증 가능한 형태로 번역한다
"도구를 쓴다"를 행동으로 검증하면 모델 의존(비결정적)이라 취약하다. 사용자의 "필요하면 쓸 수 있어야"
는 정확히 **가용성**(그래프에 tools 노드 배선)으로 번역되고, 이건 구조 검사라 결정적이다.
**교훈: 계약 문장을 검증으로 옮길 땐 "행동(호출했다)"이 아니라 "능력(호출할 수 있다)"으로 번역할 수
있는지 먼저 본다 — 후자가 결정적이면 후자가 계약이다.**

### 3. 기존 검증이 설계 가드레일이 된다 — "더 똑똑한 plan" 유혹을 086이 막았다
plan을 모델 기반 동적 계획으로 승격하고 싶었지만, 086이 "plan은 결정적(plan<execute 실측)"을 계약으로
검증하고 있었다 — 덕분에 결정적 유지+도구 반영이라는 절충을 골랐고 기존 검증 전부 무회귀.
**교훈: 개선 충동이 기존 검증과 충돌하면 그 검증이 지키는 계약부터 읽는다 — 검증은 회귀 감지기이자
설계 결정의 기록이다(우회 말고 절충 또는 별도 스펙).**

## 다음에 적용
- 주입 계약엔 소비(또는 미사용 선언) 적합성 rung을 짝으로(1).
- 계약 문구는 "능력" 형태로 번역해 결정적 검증으로(2).
- 기존 검증과 충돌하는 개선은 그 검증의 계약을 먼저 읽고 절충/별도 스펙(3).
