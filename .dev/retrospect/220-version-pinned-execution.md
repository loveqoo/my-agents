# 회고 220 — "버전별 서빙"은 배포가 아니라 config 소스 전환이었다 (스펙 242)

## 무엇을 했나
사용자 방향("내부는 버전별 서빙, 외부는 활성 하나, 플그 버전 선택, 버전별 테스트")을 검토 —
AgentVersion이 이미 버전별 config 스냅샷을 보유하므로 "버전별 서빙"=_load_context의 config 소스
전환 한 층으로 구현. 채팅 version 파라미터+trace 버전 기록+버전 지정 평가(배포 전 게이트 성립).
codex 5건 중 3건(재개 drift·초안 권한·trace 누락) 수정.

## 배운 것

### 1. "N개 서빙"처럼 크게 들리는 요구도 기존 구조에 대면 한 층일 수 있다 — 스냅샷이 이미 있었다
버전별 서빙을 배포·라우팅 문제로 접근하면 큰 공사지만, 우리 구조에선 "실행 시 어느 config를 읽나"
문제였다. 요구를 받았을 때 "이걸 위해 무엇이 이미 있나"(버전 스냅샷·오버라이드 화이트리스트 선례)
부터 대조하면 규모가 한 자릿수 줄어든다. 241의 정직 경계("배포 전 게이트 불가")도 이 한 층으로 해소.

### 2. 상태 재개(체크포인트)가 있는 시스템에서 실행 컨텍스트 축을 추가하면, 재개 경로마다 그 축의 승계를 물어야 한다
version 축을 추가하자 승인 재개(게이트로 차단)·ask/form 재개(codex 적발 — pending에 버전 저장해
서버측 승계)가 각각 drift 축이 됐다. 235 ephemeral 때도 재개 경로가 마지막 구멍이었다(3번째 반복).
**새 실행 축 체크리스트: 신규 턴 / 승인 재개 / ask·form 재개 / (플그) 클라이언트 재전송 — 네 경로
전부에 축이 관통되는가.**

### 3. 실행 컨텍스트의 권한은 "무엇을 실행하나"가 아니라 "무엇이 보이나"로 정한다
초안은 미공개 작업본 — 사용 권한(may_use)만으로 버전 지정 실행을 허용하면 작성 중인 프롬프트가
누출된다(codex #2). 실행 파라미터가 접근 범위를 넓히면(활성→모든 버전) 권한도 그에 맞춰 승격
(may_manage). "같은 에이전트인데 왜 권한이 다르냐"가 아니라 "다른 자원(초안)에 접근하는 것"이 정답.

## 다음에 적용
- 새 실행 축(버전·모드류) 추가 시: 재개 4경로 승계 체크 + 접근 범위 확장 여부로 권한 재산정.
- 큰 요구는 기존 스냅샷/선례 자산 대조부터(배포 문제 → 데이터 문제로 축소되는지).
