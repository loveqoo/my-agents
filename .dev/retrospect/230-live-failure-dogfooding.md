# 회고 230 — 장애가 드러낸 것들: 실데이터 도그푸딩과 단일 경로의 배당 (스펙 253~255)

## 무엇을 했나
사용자가 라이브 모델 장애 중 도그푸딩하며 연속 발견 → 칩 시맨틱(실패 시도가 "1 rag"), 헤더 밀림,
엔티티 히트 카드(빈 라벨 나열), meta JsonTree, 인스펙터 관통. 3~4왕복에 전부 수정.

## 배운 것

### 1. 장애·실데이터는 mock 시드가 못 만드는 상태다 — 도그푸딩의 고유 커버리지
mock 환경은 rag 실패를 만들 수 없고(임베드 무장애·삭제 차단), 60자 파일명도 시드에 없다.
사용자의 라이브 장애 + 실제 엔티티 컬렉션(sql_filter_key)이 검증 그물 밖 상태를 공짜로 재현해줬다.
회고 229의 상태 트리에 축 하나 추가: **장애 상태도, 실데이터 형상도 상태다**. e2e로 강제 불가능한
것(실패 칩)은 "사용자 실기기 확인 요청"을 정식 검증 런으로 스펙에 명기했다.

### 2. 단일 공유 경로의 배당이 실증됐다 — 수정 1회 = 두 경로 적용
직접형·조율형 RAG가 같은 빌더(rt._hits_detail)+같은 렌더러(HitCard)를 쓰는 구조 덕에, 개행 보존·
meta 관통·구조화·JsonTree를 한 번 고치자 두 경로가 함께 고쳐졌다. "두 벌=드리프트"의 역방향 증명 —
**검증도 "공유 구조 확인"으로 압축**된다(코드 그물 추적이 e2e 두 벌보다 쌌다).

### 3. 뷰어를 넣으려면 데이터부터 — UI 작업이 API 계약 작업이 되는 패턴
인스펙터 구조화는 백엔드 프리뷰의 개행 유지에, JsonTree는 meta 관통에 막혀 있었다. 표시 계층
개선의 절반은 "그 데이터가 프론트까지 오는가" — 프론트만 보고 끝났다고 하면 안 된다.

### 4. 카운트 시맨틱 원칙: 집계=성공, 실패=승격
"N rag"의 N에 실패를 섞으면 거짓 신호, 실패를 지우면 더 중요한 신호 소실 — 성공만 세고 실패는
빨간 별도 칩으로 승격. 다른 집계(도구 미발동 진단·평가 통과율)와 같은 계열의 정직성 원칙.

관련: 스펙 253·254·255 · 회고 229(상태 트리)·224~228
