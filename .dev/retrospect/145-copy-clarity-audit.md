# 145 — 문구·평이함 감사 (검증 축3) (스펙 167)

축2·축1 골격을 축3에 적용: UI 문구가 일반인도 이해할 수준인지. 루브릭(합격선 박제) + 적대적
리뷰어("IT 모르는 일반인" 연기, deep-reasoner) + 메인 트리아지·수정.

## 결과
deep-reasoner가 사용자 노출 문자열 전수 채점. **오탈자·맞춤법은 사실상 0**(카피는 깨끗 — 관대함이 아닌
실측). 진짜 문제는 **개발 내부 산출물이 사용자 문구로 누출**: 오류창의 `(스펙 089)`·`impl`·`신뢰
레지스트리`, 버튼 라벨 `GET /models`(HTTP 메서드!), `2차 스펙`(로드맵 용어), `(kind=embedding)`(코드
필드), `ready` enum, `Fernet`(라이브러리명). 12건 수정(막힘 8 + 거슬림 4).

## 배운 것
- **가장 위험한 카피 문제는 오탈자가 아니라 "내부 산출물 누출"**. 스펙 번호·HTTP 메서드·코드 enum·
  라이브러리명·로드맵 용어가 사용자 문구에 그대로. **자가검증이 절대 못 잡는 종류** — 내가 "스펙 089"를
  오류창에 쓰고도 못 봤다(나는 그게 뭔지 아니까 안 걸린다). 적대적 리뷰어 + "내부 누출"을 유형으로
  명시한 루브릭이라야 잡힌다. 관대함의 핵심 사례.
- **도메인 필수어는 없애지 말고 설명을 붙인다**(루브릭 규율). `임베딩`은 유지하되 `(kind=embedding)`
  코드값만 제거, `A2A/MCP`는 글로스 있는 곳 통과. 용어를 다 지우면 정확도 손실 — 누출된 *코드 부스러기*만.
- **적대적 리뷰어가 스스로 관대함 가설을 기각**. deep-reasoner가 "오탈자 많을 것"을 다회 스캔으로 반증,
  "A2A 무조건 막힘"을 글로스 확인으로 부분 기각. 근거 대며 flag/통과를 가른 게 신뢰를 줌(무한 나열 아님).
- **감사끼리 상호 검증**: 카피 수정 후 **축2 하네스(ui-audit) 재실행**으로 텍스트 길이 변화가 오버플로/
  렌더를 깨지 않음을 확인(0 FAIL). 축1·2·3이 서로의 회귀 검증 도구가 된다 — 자산의 복리.
- **범위 규율**: 막힘·오탈자 우선 수정, 거슬림 선별, 취향 보류(rubric). mem0(백엔드 시드 용어, 프론트
  mock이라 효과 없음)·차원 글로스·배치 admin jargon(슈퍼유저 전용, 등급 하향)은 백로그로 — 전면
  갈아엎기 아님.
