# 회고 182 — 문제집 목록 최근순 정렬 + 검색 + 페이징 (스펙 196)

## 무엇을 했나
문제집 목록이 이름순·검색 없음·전량 렌더라는 실사용 요청. → 백엔드 `list_datasets`를 페이징화
(`created_at DESC`, `q` name·설명 ilike+이스케이프, limit/offset, `DatasetPageOut{items,total,
any_generating}`) + `get_dataset` 단건 추가. 프론트 목록을 공용 `PagedListShell`(스펙 128)로 교체 —
디바운스 서버검색·페이지네이션을 셸이 담당. 196 e2e 14/14(정렬·검색·페이징 경계·이스케이프·404·UI
필터)·195/194 무회귀·tsc0·스샷.

## 배운 것

### 1. 부모가 쥔 목록 상태를 컴포넌트로 이관하면, 그 상태의 **파생 소비처를 전부 재배선**해야 한다
`datasets` 배열을 PagedListShell로 넘기면 부모엔 그 배열이 없어진다. 그런데 `datasets`는 목록 렌더
말고도 **세 곳**에서 더 쓰이고 있었다: (a) generating 폴링 조건(`datasets.some(generating)`), (b) 열린
드로어 rebind(`datasets.find(id)`), (c) runFilter 옵션(`datasets.map`). 각각 페이지-독립 소스로 이전했다
— (a)→응답 `any_generating` 신호, (b)→`getEvalDataset` 단건 폴링, (c)→`runs`에서 유도. **교훈: 상태를
셸/자식으로 이관할 땐 "이 상태를 **읽는 곳**"을 전수하고(렌더 외 폴링·동기화·파생목록), 각각 대체 소스를
정한 뒤 옮긴다 — 렌더만 갈아끼우면 나머지 독자가 빈 배열을 읽는다.** (회고 181 #1 "필드 제거는 소비처
전수"의 **상태 이관판** — 같은 규율이 필드/상태/마커에 반복 적용된다: [[remove-field-follow-consumers]])

### 2. 페이징을 도입하면 "전체 목록을 훑던" 소비처가 조용히 깨진다
runFilter는 **모든** 문제집을 드롭다운 옵션으로 깔았다. 목록을 페이징하면 부모엔 현재 페이지(20개)만
남아, 21번째 문제집으로는 필터를 못 건다 — 컴파일도 e2e happy-path도 통과하지만 대량에서 깨진다. 실행
이력 탭이라 `runs`(이미 전량 로드)에서 dataset를 유도하는 게 옳았다. **교훈: 페이징 도입 시 "전체를
가정하던" 코드(전량 map·find·some)를 찾아 페이지-독립 소스로 바꾼다 — 페이징은 목록 렌더만 바꾸는 게
아니라, 그 목록을 전체라고 믿던 모든 곳의 가정을 깬다.**

### 3. 정렬·검색·페이징은 API 왕복으로 결정적으로 검증한다
UI 클릭보다, 순차 생성(시차)→최근순 `items[0]` 확인, `limit/offset` 경계(2+1), `q="%_\\"` 이스케이프
(주입 없음), 단건 404를 **API로** 못박고 UI는 검색 필터 스모크만. 결정적이고 빠르다. **교훈: 순서·경계·
필터 같은 계약은 API 레벨에서 확인(브라우저는 렌더 스모크) — 정렬 뒤집힘·오프바이원·이스케이프 누락은
클릭 테스트보다 API 왕복이 정확히 잡는다.**

## 다음에 적용
- 상태를 셸/자식으로 이관 = 그 상태의 독자(렌더·폴링·동기화·파생목록) 전수 후 대체 소스 배선(1).

- 정렬·경계·이스케이프는 API 왕복으로 결정적 검증, UI는 스모크(3).
