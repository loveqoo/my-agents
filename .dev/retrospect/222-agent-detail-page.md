# 회고 222 — 누적된 화면은 "관심사 재배치"가 답, 그리고 복잡도는 측정하면 순위가 나온다 (스펙 245)

## 무엇을 했나
"기능이 쌓여 서비스가 어렵다"(사용자) → 에이전트 상세 인벤토리(640px 드로어에 4관심사 12블록)
→ 구조 합의(AskUserQuestion: 풀페이지+전수 진단 병행) → 5섹션 페이지(개요/구성/버전·배포/공개·연동/
운영)+좌측 네비로 승격. 병행으로 전 화면 복잡도 하네스(블록·컨트롤·세로배수 실측) → 승인 화면이
압도적 1위(117블록·22화면 분량)로 다음 후보 확정.

## 배운 것

### 1. 화면 비대는 기능들의 죄가 아니라 "배치 재설계 부재"의 죄 — 주기적 재배치가 필요하다
12블록 각각은 정당하게 들어왔다(154 공개·209 수확·240~244 운영…). 문제는 **더할 때마다 넣을 자리만
찾고 전체를 다시 그린 적이 없다**는 것. 239 폼, 245 상세 — 같은 병이 두 번. 기능 N개가 쌓이면
관심사 축(이 화면에서 사용자가 하려는 일의 종류)으로 재배치하는 스펙을 주기적으로 잡아야 한다.

### 2. "어렵다"는 느낌도 측정하면 순위가 나온다 — 그리고 순위는 직감과 달랐다
복잡도 하네스(블록 수·컨트롤 수·세로 배수)를 돌리니 직감(에이전트·평가가 복잡할 것)과 달리 **승인
화면이 22배 화면 분량**으로 압도적 — 페이지네이션 없이 데이터에 비례해 자라는 화면이었다.
[[numeric-verification-unlocks-autonomy]]의 UX판: 느낌을 수치로 바꾸면 우선순위 논쟁이 사라진다.
단, 측정 한계를 정직하게: 최상위 표면만 재므로 드로어/모달 속 복잡도는 별도 축.

### 3. 컴포넌트를 "부모가 골라주니까"로 방어를 빼면 오재사용 축이 남는다
페이지가 ui 전용이라 mem0/ops 조건에서 source 체크를 뺐더니 codex가 지적 — 부모 계약에 기댄 방어
제거는 컴포넌트가 재사용되는 순간 구멍. 조건부 렌더의 가드는 컴포넌트 안에 자족적으로.
그리고 분기 기준은 소비처와 동일 규칙으로(목록 `|| 'ui'` vs 상세 `=== 'ui'` — 레거시 행이 샜다).

## 다음에 적용
- 기능 추가가 잦은 화면은 N스펙마다 "관심사 재배치" 점검(블록 수 임계 감시 — 복잡도 하네스 재실행).
- UX 우선순위 논의 전에 complexity-audit부터(느낌→수치).
- 컴포넌트 가드는 자족적으로, 분기 술어는 소비처와 단일 규칙.
