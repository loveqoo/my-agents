리팩터 캠페인의 최종·최고위험 파일 chat.py(1,147줄, 메인 /chat SSE)를 파사드 391줄+3형제

codex 적대 발견 0건(2연속), suite 51/51, 실채팅 SSE 프레임 순서 실측 정확.
**캠페인 총결산: 5파일(chat_stream·blocks·chat_context·batch/jobs·chat) 4,805줄 해체,
저장소 C급 61→47, MI 문턱 근접 전부 해소.**

## 배운 것

1. **가장 위험한 파일을 마지막에 — 순서가 안전장치였다.** 5회전 동안 함정 목록·표면 박제·
   monkeypatch 선그렙·이동/개선 구분이 누적된 뒤에야 메인 경로를 건드렸고, 그 결과 최고 위험
   파일에서 적대 발견 0. 위험 오름차순은 단계 안에서만이 아니라 **캠페인 단위에서도** 유효.
2. **"명시 개선"은 스펙에 선언하면 안전하게 섞을 수 있다.** dict→dataclass는 이동에 섞인
   개선이지만, 계획 단계에서 1:1 필드·소비자 전수(chat_trace 15곳)를 선언하고 적대 축으로
   명시하니 잠입 개선(321의 P2)과 달리 사고 없이 통과. 규율은 "개선 금지"가 아니라 "개선의
   선언·전수 검증".
3. **실측 가능한 계약은 실측한다** — SSE 프레임 순서를 문서 신뢰 대신 라이브 서버 스트림
   파싱으로 검증(session→text→message_id→trace→done→memory). 프론트 파서가 전제하는 순서라
   테스트 그물 밖 계약이었는데, 한 스크립트로 닫혔다 — 이런 "그물 밖 계약 실측"을 리팩터
   완료 조건에 상시 포함할 것.
4. **mypy가 dataclass 전환의 잔존을 즉시 잡았다**(turn.get 1곳) — 382가 ChatContext로 보여준
   "타입 전환=정적 검사 배당"의 재확인. dict 표면을 타입으로 바꾸는 리팩터에선 mypy가 소비자
   전수 검사기 역할.
5. **스펙의 검증 목록도 실측 대상**: 계획에 넣은 verify_242가 기격리(KNOWN_DRIFT)였다 —
   착수 시 표적 verify 목록을 격리 대장과 대조하는 1줄이 스펙 템플릿에 필요.
