# 311 — 게이트 드리프트 3건 정비 (스펙 336)

## 무엇을 했나

331~335 기능 몰이 뒤의 정비 차례. ①suite flaky(발화 정렬, 0/5→8/8) ②복잡도 D 2곳 분해
③verify_312 검증기 2중 버그 수정. 수치 게이트 전판 초록 복귀.

## 핵심 배운 것

### 1) 모델의 지시 가중치: 유저 발화 ≫ 노드 시스템 프롬프트 — 실측이 갈랐다
"반드시 echo 호출" 노드 프롬프트를 아무리 강화해도 0/6(qwen3.6이 "내용 이미 있음=완료"로 판단).
**같은 요구를 사용자 발화로 옮기자 결정적으로 호출**(8/8). 시나리오 단언이 도구 호출을 기대하면
발화가 그 도구를 요구해야 한다 — 노드 프롬프트만의 도구 강제는 모델 로터리. 단, 발화 정렬이
커버리지 축소가 되지 않게 **사실 토큰 관통 단언을 함께**(codex P2 — 도구명 카운트만으론 "아무거나
echo"도 통과).

### 2) 패턴 grep이 게이트 위반을 숨겼다 — 두 번째 rank D의 발굴
`make complexity` 출력에 `grep "rag|D \("` 필터를 걸어 보다가 blocks.py의 D를 며칠간 못 봤다.
**게이트 출력은 전문을 보거나 exit code로 판정** — 사람이 만든 필터가 게이트를 우회시킨다.

### 3) 라우트 함수 위에 헬퍼를 삽입하면 데코레이터가 헬퍼를 감싼다 — 같은 사고 2회
`async def route(` 를 anchor로 old_string 치환하면 그 위의 `@router.post`는 앵커 밖이라 헬퍼가
데코레이터와 함수 사이에 낀다. blocks는 즉시 의심해 잡았지만 rag는 dev 서버 부팅 실패
(FastAPIError)로야 발현 — 그 사이 verify가 **침묵 크래시**(grep 결과 0을 통과로 오독할 뻔).
라우트 근처 삽입은 데코레이터를 old_string에 포함시켜라. + grep 무출력 ≠ 통과(exit code 확인).

### 4) 검증기도 "즉시 완료" 전제의 소비자였다 — 여파 스윕은 grep으로 닫아라
334 때 verify 4종을 갱신했지만 312를 누락("312 무회귀" 주장은 334 이전 실행 기준 — 정직 정정).
전환성 변경의 소비자 스윕은 기억이 아니라 **전수 grep**(ingest_document 호출자)으로.
+검증기의 조건부 다리(스킵)는 기대치도 함께 조건부여야(고정 2건 기대가 mock-only 환경서 거짓 빨강).

### 5) suite 통과 표기는 "ok"다 — 단언 문자열도 실측하고 써라
5회 측정 루프가 "PASS" grep으로 전부 무출력 — 통과를 실패로 오독할 뻔(반대 방향의 거짓 신호).
파서·grep을 짜기 전에 실제 출력 형식 한 번 확인.
