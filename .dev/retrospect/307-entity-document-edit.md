# 307 — 엔티티 문서 편집 개방 (스펙 332)

## 무엇을 했나

331이 제외했던 엔티티 컬렉션을 편집에 개방 — 사용자 질문("엔티티도 수정할 수 있나?")에 검토
먼저(방안 A 행 UI vs B 에디터 개방), B 채택. 백엔드 분기 2곳+게이트 개방으로 끝(331 기계 전부
재사용). 1행=1청크라 부분 재임베딩이 정확히 행 단위: meta만 바꾼 행은 재임베딩 0으로 meta 갱신.

## 핵심 배운 것

### 1) 확장 스펙의 적대 리뷰가 원 스펙의 기존 구멍을 표면화한다
codex P2 = JSONL의 `NaN`/`Infinity`가 파서를 통과해 JSONB insert 500 — 이건 332가 만든 게 아니라
**149(엔티티 인제스트)부터 있던 구멍**인데, 편집 입구가 열리며 공격 표면으로 재조명됐다.
`parse_constant` 거부 훅 하나로 업로드·편집 두 입구 공통 봉인(행 번호 400 계약 유지). 기능을
새 입구로 확장할 때의 리뷰는 "새 코드"만이 아니라 **그 입구가 다시 여는 기존 경로 전체**를 본다.

### 2) 이분법 판정을 한쪽 완화하면 화이트리스트로 바꿔라
331의 `kind != "document" → 제외`를 `kind == "document"일 때만 PDF 검사`로 완화하니, 미지/레거시
kind(DB는 String(20) — check 제약 없음)가 **문서형 청킹 경로로 조용히 흘러드는** 제3의 길이 생겼다
(codex P3). "A 아니면 B" 가정의 완화는 명시 화이트리스트+기타 fail-closed로.

### 3) "검증 fail-closed 승계"라는 문구도 검증 대상이다
스펙에 "entity_schema 검증 fail-closed 승계"라 썼는데 schema는 컬렉션 생성 시 **선택**이라,
스키마 없는 컬렉션은 기본 행 계약만 검증된다 — codex가 문구와 실동작의 갭을 짚음. 계약 서술은
"항상인 것"과 "있으면인 것"을 분리해 적는다(모호한 승계 문구가 후속 독자를 속인다).

### 4) UI 목록에 "맥락 탭"이 있으면 e2e 내비게이션도 그 탭을 탄다
엔티티 컬렉션이 목록에 안 보여 e2e가 죽음 — 컬렉션 뷰는 스펙 212 규칙대로 문서/엔티티 탭 분리.
331 e2e(문서형=기본 탭)를 복제하면서 탭 전환을 빠뜨렸다. 데이터 kind축 탭이 있는 화면의 e2e는
시드한 데이터가 어느 탭에 사는지부터.
