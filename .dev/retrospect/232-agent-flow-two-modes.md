# 232 — agent-flow 두 모드: 사용자 지시가 구조 충돌일 때 (스펙 258)

## 상황
사용자: "agent-flow가 정상 동작 안 함 — source=ui가 아니라 code로, doc-translator처럼 만들어야."
지시를 그대로 따르면 **기능이 깨진다**: agent-flow는 인프로세스 LangGraph flow(source=ui+impl)를
만드는데, source=code는 원격 A2A 서비스(endpoint 필수, `_a2a_stream` 릴레이)라 `resolve_agent_runtime`이
그래프를 실행조차 안 하고 원격으로 빠진다.

## 무엇을 했나 (핵심 판단)
지시를 **맹종하지도(깨짐) 기각하지도(사용자가 옳을 수 있음) 않고**, 구조를 코드로 확증한 뒤 충돌을
**정직하게 표면화**하고 사용자에게 의도를 물었다(AskUserQuestion). 답=  "두 모드 다 지원, 유저에게 물어
분기." → 결과적으로 사용자 지시(code 지원)와 기존 설계(ui 인프로세스)를 **둘 다 살리는** 답으로 수렴.

## 배운 것
1. **사용자 지시가 구조와 충돌하면, 맹종/기각 이분법이 아니라 "충돌을 증거와 함께 표면화→의도 질문"이
   답이다.** 사용자는 "code로"라는 *수단*을 말했지만 진짜 의도는 "code 에이전트도 만들고 싶다"였다.
   수단을 그대로 실행(깨짐)하거나 "안 됩니다"(기각)로 끝냈으면 둘 다 틀렸다. 구조를 읽어 수단↔의도
   간극을 찾고, 의도를 되물어 상위 답(두 모드)으로 올라갔다. [[probe-deeper-before-concluding]]의 확장 —
   내 측정(구조)과 사용자 보고가 어긋날 때, 내 측정을 버리지도 사용자를 무시하지도 말고 *간극 자체를 대화*.
2. **"정상 동작 안 함" 보고는 종종 복합**: 여기선 (a) 개념 충돌(ui vs code 기대) + (b) 진짜 문서 버그
   (스킬이 존재하지 않는 `classify_conformance`를 검증 게이트로 참조 — 따라 하면 그 지점 실패). 사용자
   진단(source)만 좇았으면 (b)를 못 잡았다. 보고를 단일 원인으로 좁히지 말 것.
3. **스킬(문서)도 코드처럼 드리프트한다**: 함수명이 바뀌거나 애초 틀리면 스킬이 유령을 참조. 스킬 개정
   시 참조한 함수/라우트/필드를 **코드에 grep해 실존 확인**(deep-reasoner 문서-코드 대조가 유령참조 0 확증).

## 처방
- 스킬/문서가 코드 심볼(함수·라우트·필드·파일)을 참조하면, 개정 시 그 심볼을 grep해 실존·시그니처 확인.
  비자명하면 deep-reasoner에 "문서-코드 일치" 적대 검토(유령참조·틀린분기·오도 표현).
- 사용자 지시가 코드 구조와 모순될 때: (1) 구조를 코드로 확증 (2) 수단↔의도 간극을 짚어 표면화
  (3) AskUserQuestion으로 의도 확인 (4) 둘 다 살리는 상위 답을 탐색. 맹종도 기각도 아니다.
