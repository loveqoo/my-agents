# 171 — 커스텀 Desc를 antd Descriptions/Form으로 (스펙 187 Phase 3)

**스펙**: docs/spec/187 · **관련**: 169(Drawer)·170(Table)

## 무엇을 했나
`shared.Desc`(28줄) 호출부 50곳을 전환하고 정의 삭제. 스펙 187 3단계 완주 — shared.tsx 575→384줄,
from-scratch 재구현이 전부 antd로.

## 무엇이 잘못됐고 무엇을 배웠나

### 1. 같은 컴포넌트라도 **용도별로 옳은 대체물이 다르다** — 전환 전 용도 분류
"Desc → Descriptions"로 1:1 기계 치환했으면 틀렸다. 50곳을 전수 조사하니 42곳은 표시(라벨:값)지만
**8곳은 폼 행**(라벨+Input) — 설명 컴포넌트에 입력을 넣는 건 antd 의미론 위반. 표시→`Descriptions`,
폼→`Form`(레이아웃 전용)으로 갈랐다. 183의 "같은 리터럴, 다른 축"과 동형 — 같은 표면(컴포넌트 이름),
다른 용도.

- **처방**: 컴포넌트 통일 전에 호출부를 **용도로 분류**하라(표시/입력/기타). grep 카운트가 아니라 각
  사이트의 children이 무엇인지(값이냐 컨트롤이냐) 봐야 한다. [[same-literal-may-be-different-axis]]의 UI판.

### 2. antd Form을 "레이아웃 전용"으로 쓰는 법 — 상태 재배선 없이 채택
Form 채택이 곧 Form 상태관리(name·onFinish) 도입은 아니다. `component="div"`·name 미지정으로 **라벨
정렬·여백만 antd에 맡기고** 입력 상태는 기존 controlled 그대로 두면, 로직 무변경으로 antd 폼 룩을
얻는다. 전면 Form 상태 이관은 별개 결정(지금 불필요).

- **처방**: 라이브러리 채택 시 "스타일/레이아웃 층"과 "상태관리 층"을 분리해 필요한 층만 채택하라.
  한꺼번에 다 받으면 리팩터가 로직 수술로 번져 위험이 커진다.

### 3. 그룹 경계는 "비-Desc 요소가 낀 지점"이 정한다
연속 `<Desc>`를 하나의 Descriptions로 합치되, 중간에 PersonaStaleNote·도구 카드 같은 비-Desc 요소가
끼면 거기서 분할해야 한다(안 그러면 요소 순서가 바뀜). 조건부 행은 items 스프레드로 자연 매핑.
`width={84}` 커스텀은 Descriptions가 표 기반이라 라벨 정렬이 자동이 되어 그냥 삭제 — 커스텀 prop이
라이브러리 채택으로 **불필요해지는** 사례.
