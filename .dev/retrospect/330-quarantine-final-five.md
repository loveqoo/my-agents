# 330 — 격리 잔여 5건 근본 해결(스펙 402): 대장 0, 그리고 실구멍 하나

## 대장 사유는 노화한다

400이 남긴 "환경/인프라 5건"을 실측하니 **4건은 사유가 이미 낡아** 있었다 — 114는 가시성
계약(147) 노후, 143은 시드가 아니라 제품 게이트 자체, 057은 370 노후 3겹(이벤트루프는 부수),
054rt는 캐시-관문 어긋남의 픽스처 충돌. 격리 사유도 자산이다 — 쓰는 순간의 진단이지 영구
판정이 아니므로, 대장이 오래 살면 사유 재실측부터.

## "환경 전제"의 두 갈래 처방

- **게이트가 제품 계약이면 단언으로 승격**(143): "실모델일 때만 도우미"는 스킵 사유가 아니라
  검증 대상 — mock이면 거절+사유 문자열을 핀하고, 실모델 전체 경로는 opt-in(env)으로 분리하면
  virgin·라이브 양무대에서 그물에 산다.
- **하네스가 유발자면 하네스를 고친다**(068): SSE 첫 프레임만 읽고 끊는 early-abort가 서버 턴
  취소→풀 poison→후속 요청 비결정 500을 만들었다. 검증 대상(재개/소유권)은 무죄 — 드레인으로
  5/5 그린. "비결정 실패는 단발 판정 금물, 반복 실행으로"(deep-reasoner 규율).

## 테스트가 우연히 캔 프로덕션 실구멍

068의 풀 오염은 실사용(탭 닫기·모바일 이탈)에서도 재현 조건(codex 확인) — pool_pre_ping 부재
+체크포인터 psycopg 풀+release_thread 취소 레이스. **테스트 하네스의 "버그"가 앱의 잠복 부채를
가리키는 경우가 있다** — 하네스만 고치고 끝내면 절반, 실구멍은 백로그로 승계(별도 스펙 후보).
반대쪽 054rt 캐시-관문 의심은 codex가 **비실재**로 닫음(편집=항상 version 범프) — 의심 2건을
같은 리뷰에 실어 실구멍/비실재를 한 번에 갈랐다.

## 부수 교훈

- 057 하네스: 예외 후 별도 `asyncio.run(_cleanup())`은 첫 루프의 engine/Task를 새 루프에서
  만진다("Task attached to a different loop") — 정리는 같은 루프의 finally에서.
- endpoint류 기대값은 하드코딩 말고 **카드가 광고한 값을 실측**해 비교(모의 카드 상수는 포트가
  다를 수 있다) — "불변식(endpoint==카드 url)"을 단언하는 게 목적이지 특정 주소가 아니다.
- 배터리-한정 플레이크(137runner·140·141)는 이번에 실물을 못 잡음 — 그물에 실패 전문 보존
  계측을 상시 장착해 덫을 놓고 종료(재발 시 /tmp/run_suite_fails/). 한 줄 요약만 남기는 그물은
  비결정 실패를 영영 못 잡는다(instrument-first).
