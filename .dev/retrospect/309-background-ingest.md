# 309 — 인제스트 배경 잡화 + 캡 재승인 (스펙 334)

## 무엇을 했나

미승인 수치 지적("저는 이 수치를 승인한 적 없습니다")에서 출발 — 캡 재결정을 물었더니 사용자가
배경 잡화(정공법)를 선택. 업로드=접수(형식 검증까지 동기·400 계약 보존), 임베딩+적재=배경,
행 캡 50,000(이번엔 **승인 수치**)+env, 임베딩 배치화(128/호출), CPU 구간 to_thread(이벤트 루프
스파이크 해소 — 사용자의 "블락되나요?" 질문에 대한 구조적 답), 부팅 좀비 스윕, 전역 processing
신호 폴링.

## 핵심 배운 것

### 1) 동기→배경 전환은 "그 상태를 전제하던 모든 소비자"를 깨운다
verify_149/331/332/333이 전부 "업로드 반환=ready" 전제라 연쇄 수정. 심지어 문서 상태 축
(parsing→embedding→ready)은 **처음부터 배경화를 위해 있던 상태 기계**였는데 동기 구현이 그 위를
덮고 있었다 — 전환 자체는 상태 축이 이미 있어 쌌고, 비용은 전부 "즉시 완료" 전제의 소비자들.

### 2) 상태 겹침 경합은 "누가 어떤 상태를 못 보는가"로 뚫린다 — codex P1
재인덱싱 사전 검사는 parsing만 보고, 배경 잡은 embedding으로 옮겨 임베딩한다 — 그 창에서
재인덱싱이 완주하면 늦은 적재가 옛 모델 벡터를 스왑 밖에 커밋. 상태 기계에 상태를 **추가**하면
기존의 상태 집합 검사들(in_ 목록)을 전수 재감사해야 한다. +B7 교훈: 경합 테스트가 **잘못된
이유의 400**(변경 없음)으로 초록이었다 — 거절 테스트는 거절 사유까지 단언.

### 3) 폴링 신호는 "보이는 것"이 아니라 "전역 상태"에서
처리 중 판단을 현재 페이지 행에서 도출하면 새 문서가 뒷 페이지에 있을 때 폴링이 안 선다(codex
P2). 서버가 페이지와 무관한 전역 카운트를 응답에 실어야 한다. 이 과정에서 내가 만든 onData
주입점이 즉시 죽은 표면이 됨 → 기존 extra 채널로 회수(새 주입점보다 기존 채널 먼저).

### 4) fire-and-forget의 예외는 어디에도 없다
spawn된 잡이 자체 try 밖에서 죽으면 로그조차 없이 증발(문서는 parsing 영구 잔류). ①잡 외곽
try+best-effort 박제 ②spawn 자체에 done-callback 예외 로깅(모든 배경 잡 공통 수혜) ③부팅 스윕
— 세 겹이 각각 다른 실패 지점을 덮는다.

### 5) 만료된 ORM 인스턴스는 async에서 접근 즉시 폭발
테스트에서 배경 잡이 다른 세션으로 갱신한 상태를 보려고 expire_all() 했더니, 그 뒤 기존 인스턴스
속성 접근(col.id)이 동기 lazy-load → MissingGreenlet. **expire 전에 필요한 스칼라를 전부 박제**.
