## 무엇을 했나

392·393과 같은 루프의 3회전. chat_context.py(812줄·MI 23.85·C급 5)를 타입 허브+9형제 모듈로

DTO 전환이 이미 문제를 풀었음). suite 51/51·캐시 지문(371)·소비자 9곳 무변경.

## 배운 것

1. **백로그 항목도 재검증 대상이다.** 374 T2의 "typed builder"는 당시엔 맞는 처방이었지만 382가
   dict→DTO를 이미 해결해 낡은 처방이 됐다 — 백로그를 집행하기 전에 "이 처방의 전제가 아직
   유효한가"를 자문으로 물었더니 기각이 답이었다(verify-premise-before-designing의 백로그판).
2. **적대 리뷰의 수확 체감이 곧 방법의 성숙 신호.** 1회전 P2 2건(계약 구멍) → 2회전 P2 1건
   (관용구 교체) → 3회전 P1/P2 0건. 함정 목록을 계획에 선제 반영하는 정확도가 회전마다 올라갔고,
   3회전은 "이동에 섞인 개선"을 자체 검열해 코덱스가 잡을 것을 남기지 않았다.
3. **"기존에 통과했었다"는 전제도 실측**: verify_122 실패를 회귀로 단정하기 전에 HEAD 워크트리
   재현으로 기존 드리프트임을 판정(probe-deeper의 리팩터판 — git worktree가 5분 만에 종결).
   실측 결과는 격리 사유 정밀화로 환원(드리프트 목록이 조사 노트가 됨).
4. **순환은 타입을 최하위로 내려 끊는다**(2번째 적용 — 392 chat_graph_build, 394
   chat_context_types). "파사드가 로더를 재수출하고 로더가 타입을 쓴다"는 구조에선 타입 하강이
   정석 — 이제 이 코드베이스의 관례로 봐도 된다.
5. **or-체인도 CC 예산이다.** 분기 없는 "값 선택" 함수도 `or` 폴백이 누적되면 C급 —
   pin/head처럼 원천별로 함수를 가르면 자연스럽게 B 이하.
