# 회고 207 — 입력 규칙을 좁힐 땐 검증부만 아니라 *생산자 전수*를 감사 (스펙 217)

## 무엇을 했나
식별 이름 규칙에서 한글·마침표를 제거(영소문자·숫자·대시만, 사용자 지시). 규칙은 전 리소스 공용
NAME_RE 하나. 기존 데이터 0건 위반(V6). 그런데 규칙만 좁히면 새는 곳이 둘 있었다 — slugify **폴백
기본값**이 한글("이름-미상")이었고, 에이전트 **복제 접미**가 한글("-복사본")이었다. 둘 다 새 규칙을
*생산*하는 쪽. 검증 42/42.

## 배운 것

### 1. 입력 규칙을 좁히면 검증 호출부가 아니라 그 값을 *만들어내는 모든 생산자*가 회귀 위험
규칙(NAME_RE)만 좁히고 `validate_resource_name` 호출부(create/update 라우트)만 보면 초록이다. 하지만
그 이름을 *자동 생성*하는 경로 — slugify(원격 유래 변환)·slugify **fallback**·복제 접미("-복사본")·기본값
— 는 여전히 옛 문자셋으로 값을 뱉는다. 복제는 `-복사본`을 붙여 "research-assistant-복사본"을 만들어
새 규칙을 즉시 위반했다(검증을 안 타는 직접 insert라 조용히 통과했을 것). **교훈: 입력 규칙을 조이면
"누가 이 값을 검사하나"(validator)뿐 아니라 "누가 이 값을 만드나"(producer: 자동 생성·slug·복제 접미·
fallback 상수)를 전수 감사하라. 생산자가 이제-불법인 값을 뱉으면 검증부는 초록인데 런타임이 깨진다.
[[move-breaks-references-both-directions]]의 입력판 — 규칙은 소비·생산 양방향으로 검사.**

### 2. fallback/기본값 상수도 규칙의 적용 대상 — "예외 통로"가 아니다
slugify가 전탈락 시 쓰는 fallback이 한글("이름-미상")이었다. 정상 경로는 규칙을 지켜도 *예외 경로의
상수*가 규칙을 어기면, 드물게(전탈락 입력) 불법 이름이 생산된다. **교훈: 규칙을 바꾸면 그 규칙이 만드는
값의 상수·기본값·플레이스홀더도 같이 바꾼다(fallback "unnamed"). 예외 통로는 규칙의 여집합이 아니라
규칙을 가장 조용히 위반하는 곳.**

### 3. 공용 규칙은 파급을 데이터 실측으로 먼저 재라 — "안 깨진다"를 측정으로
전 리소스 공용 NAME_RE라 겁날 수 있었지만, DB 실측(4테이블 한글/마침표 0건)으로 회귀 0을 먼저 확인한
뒤 진행했다. V6(전량 준수 재검)이 이를 게이트로 고정. **자가 "아마 괜찮아" 대신 SELECT로 셌다.**

## 다음에 적용
- 입력/식별자 규칙 변경 = validator 호출부 + **producer(자동생성·slug·복제·fallback 상수) 전수** 감사.
- 규칙이 만드는 값의 기본값·플레이스홀더·fallback도 새 규칙 준수로 동반 수정.
- 공용 규칙 조이기 전 기존 데이터 위반 수를 SELECT로 측정(0이면 무해, >0이면 grandfather·마이그 계획).
