# 096 — 위임 결과 attribution 견고화 (스펙 115)

## 무엇을

102 codex 설계한계 봉합: 다중 위임 fold의 `## 능력:` 라벨 스푸핑 가능성을 요청별 랜덤 nonce 펜스로
위조 불가화. 사용자 "1~4 루프"의 3번.

## 어떻게

- 각 결과를 `⟦BEGIN {nonce}⟧…⟦END {nonce}⟧`로 감싸고 라벨은 펜스 밖. nonce는 delegate 노드가
  `secrets.token_hex(8)` 요청별 생성·위임 능력에 미노출. `fold_results`는 순수(fence 인자).

## 잘된 것

- **위조 불가 경계의 핵심을 정확히 짚음**: 정적 구분자가 아니라 **요청별 랜덤·비노출 nonce**라야 untrusted
  콘텐츠가 흉내 못 냄(learning 115 ①). 순수성은 nonce를 노드가 주입해 유지(④).
- **codex가 경계의 약한 고리 2개를 잡음**: [P1] 라벨이 펜스 밖(신뢰)인데 `cap.name`이 자원명(소유자
  제어)이라 라벨 자체 위조 가능 → `_label_safe` 정규화(경계는 신뢰 구성요소까지 정규화해야, 115 ②).
  [P2] 단일 raw + 지침 불일치로 가짜 펜스 오인 → 단일도 펜스 + 지침 조건화(방어 설명은 데이터 형식과
  일치, 115 ③). 자가검증이면 "펜스 넣었으니 됐다"고 넘어갔을 것.
- **조작적 검증**: `_segments(out, nonce)`가 진짜 nonce로만 파싱 = "위조 불가"의 조작적 정의. 주입
  콘텐츠(가짜 라벨·틀린 nonce END·개행 name)가 진짜 경계를 못 만듦을 단언. verify_102 무회귀.

## 배운 것 / 함정

- **위조 불가 구분자 = 비밀성+요청별 유일성**(115 ①), 정적 구분자는 무의미.
- **경계는 가장 약한 구성 부분만큼만 강함**(115 ②) — 데이터를 가둬도 신뢰 측 라벨이 attacker-영향이면 뚫림.
- **방어 지침은 실제 데이터 형식과 일치**(115 ③) — 어긋나면 그 틈이 공격면.
- **랜덤은 순수 함수 밖에서 주입**(115 ④) — 함수 결정성 유지, 테스트는 고정 nonce.

## 검증 생략 / OUT

- 완전 구조화(JSON) fold — 결국 LLM 프롬프트로 평탄화되므로 nonce 펜스가 직접적. LLM의 펜스 완벽
  준수 보장은 모델 품질(별개). fence='' 레거시 폴백 예외 강제(노드는 항상 주입).
