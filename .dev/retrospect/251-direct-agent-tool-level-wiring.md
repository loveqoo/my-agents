# 251 — 직접형 도구 단위 배선: 사용자의 "근본 질문"이 설계 결함을 드러냈고, 적대 리뷰가 조용한 회귀를 잡았다 (스펙 276)

## 맥락
승인 오버라이드 화면을 보던 사용자가 "도구 1개가 3기능일 때 각각 고르면 그것만 호출되나?" →
노드형=예(도구 단위 bind+ToolNode), 직접형=아니오(서버 단위)임을 코드로 확인. 이어 "로컬 MCP도
그러냐, 원격이라 어쩔 수 없는 것 아니냐" → **원격도 클라이언트가 tools/list 노출을 고르는 구조라
서버 단위는 설정 모델의 선택이지 기술 제약이 아님**을 밝힘(enabled_tools·노드형이 증거). 직접형도
도구 단위로 정렬(config.tools 신설, mcps=서버 합집합 파생).

## 발견과 교훈

### 1. "근본을 묻는" 질문은 감사 트리거다 — 도메인 오해를 먼저 교정하라
사용자가 "원격이니까 하위 도구가 딸려올 수밖에 없다"는 **틀린 전제**를 갖고 있었다. 여기서 "네
맞습니다"로 넘어갔으면 서버 단위 제약을 기정사실로 굳혔을 것. 코드를 읽어 **전제 자체를 반증**
(build_mcp_tools가 이미 enabled_tools로 도구별 필터·노드형이 도구 단위)하니 "직접형도 가능하다"는
개선 여지가 열렸다. **사용자의 '왜 이렇게 되어 있냐'는 종종 설계 결함의 신호** — 답하기 전에 그게
제약인지 선택인지 코드로 가른다([[probe-deeper-before-concluding]]의 반대 방향: 사용자가 단정할 때 내가 반증).

### 2. mcps는 진실원으로 두고 tools를 그 위 필터로 = 파급 최소 무회귀
`mcps`(서버 목록)를 tools로 대체하지 않고 **서버 합집합 파생으로 유지**했다. 이유: 서버 로드
(name.in_)·삭제 가드(093)·조율형·A2A·eval이 전부 mcps를 소비 — 시맨틱을 바꾸면 파급이 크다.
`selected_for_server`가 "이 서버 항목 있으면 그것만·없으면 전체"라는 **서버별 폴백** 하나로 세 무회귀
(구저장 빈 목록·오버라이드 서버 추가·카탈로그 미열거 서버)를 담당. **기존 진실원 위에 얇은 필터 층을
얹으면 소비처 전수를 안 건드린다**(268 P1 "서버 풀은 노드 합집합 파생"의 직접형판).

### 3. 적대 리뷰가 '안 만든 경로'의 조용한 회귀를 잡았다 (245 재현)
codex가 4건 중 유일한 코드 결함으로 **pipeline+config.tools 조합**을 지목: UI는 pipeline에서 tools:[]로
저장하지만 **curl 직접 저작**은 agent-level tools가 노드 도구 풀을 좁혀 노드가 조용히 미바인딩. 내
e2e는 직접형만 봤기에 못 잡았다(245 "안 만든 경로는 내 초록에 안 걸린다" 재현). 처방: 백엔드에서
**impl 게이트**(pipeline/조율형은 tool_names=[]=전체) — UI finalize 규칙을 백엔드서도 강제
([[gate-on-intent-value-not-mutable-baseline]]: 클라이언트 신뢰 말고 의도 값으로). e2e ④b로 봉합 실증.

### 4. 적대 High가 '기존 모델의 성질'이면 정직 경계 — 새로 연 구멍과 구분하라
codex High(overrides.tools=[]로 저장 필터 제거)는 실재하나, **오버라이드는 세션 한정 자기 덮어쓰기**
(스펙 025)이고 mcps 오버라이드로 서버 확대가 **원래 가능**했다 — 276이 연 구멍이 아니다. 승인 게이트도
유지. **적대 발견이 유효해 보여도 "이 변경이 만든 것"과 "원래 있던 성질"을 가른다** — 후자면 봉합 대상이
아니라 정직 경계([[complement-attack-can-be-honest-boundary]]). Medium(_safe_name 충돌)도 265부터의
클래스라 같은 판정. **네 발견 중 하나만 내 변경의 결함**이었고 그것만 고쳤다(과잉 수정 방지).
