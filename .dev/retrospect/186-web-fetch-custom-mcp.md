# 회고 186 — web-fetch 커스텀 MCP + 능력 부여 도그푸딩 (스펙 201)

## 무엇을 했나
사용자 설계("주소를 조립해 패치")대로 위키피디아 공식 API 기반 wiki_search/wiki_page를 커스텀 MCP
(스펙 156 레지스트리)로 추가 — 재기동 reconcile 자동 등록 → 공개 → **새 능력 부여 UI로 member에
실부여(유지)** → 플레이그라운드에서 research-assistant(qwen 실모델)가 wiki_page를 277ms에 호출해
라이브 위키 데이터(2026-04 인구 통계)로 답변까지 전 루프 실증. 단위 15/15·e2e 7/7·스샷.

## 배운 것

### 1. 오염 행 하나 + 이중 best-effort catch = 가짜 초록의 합작
/mcp-servers가 500이었다 — 원인은 적대 테스트가 **DB에 직접 삽입**한 잔재 행(source='user', 스키마
Literal 밖)이 목록 직렬화 전체를 죽인 것. 그런데 UI(listMcpServers().catch(()=>[]))와 어제 200 e2e의
측정(api().catch(()=>[]))이 **둘 다 500을 삼켜 "mcp=0"으로 일치** — "옵션 수=자원 수" 검증이 0=0
공허 통과했다. **교훈: (a) 측정 기준을 피측정물과 같은 소스에서 뽑으면 소스가 죽었을 때 공허하게
일치한다 — 기준은 raw status까지 본다(이번 e2e에 500 회귀 감시 1a 추가), (b) best-effort catch는
진단을 삼킨다 — 목록 0건이 의외면 catch를 벗기고 status부터, (c) DB 직접 삽입 잔재는 API 검증
밖이라 목록형 endpoint의 독이 된다(행 단위 직렬화 실패=전체 500은 경계로 기록).**

### 2. 설정 드로어는 "체크 ≠ 적용" — 커밋 경로를 코드에서 역산하고 자동화한다
오버라이드 드로어에서 web-fetch를 체크하고 닫았는데 3회 연속 위키 도구가 안 불렸다 — OverridePanel은
**'적용(새 대화)' 버튼이 커밋 단계**고 체크만으론 미적용. onApply 경로를 코드에서 역산하고서야 잡았다.
**교훈: UI 자동화로 설정을 바꿀 땐 "그 설정이 실제 페이로드에 실리는 경로(커밋 단계 유무)"를 코드에서
먼저 확인 — 폼형(즉시 반영)과 드래프트형(적용 버튼) 드로어는 겉이 같다.**

### 3. 이름 비슷한 도구가 있으면 모델 라우팅이 경합한다 — 실검증은 경합 제거로 결정화
web-fetch를 붙여도 모델이 기존 local-tools의 **mock web_search**를 골랐다(이름·설명이 더 "검색"스러움).
local-tools를 오버라이드에서 빼자 wiki_page를 정확히 호출. **교훈: 도구 실검증은 이름/역할이 겹치는
도구를 치우고 돌려야 결정적이다 — 그리고 실서비스에서도 도구 이름·설명이 곧 모델 라우팅이므로 겹치는
네이밍은 그 자체가 품질 문제다.**

## 다음에 적용
- 목록 API 검증은 raw status 포함(catch 삼킴 감시), 기준-피측정 동일 소스 공허 일치 경계(1).
- 드로어 자동화 전 커밋 단계 유무를 코드에서 확인(2).
- 도구 실검증은 경합 도구 제거 후, 네이밍 겹침은 품질 이슈로 취급(3).
