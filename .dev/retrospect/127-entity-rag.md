# 127 — 스펙 149: 엔티티 RAG 회고

## 무엇을 했나
컬렉션에 kind=document|entity 축. 엔티티형=JSONL({metadata, data}) 업로드 → 1행=1청크(분할
없음), data 임베딩·metadata JSONB 저장, 검색 hit에 meta 동반(시험 엔드포인트+인-챗 도구).
선택적 JSON Schema로 행 전수 검증(fail-closed, 행 번호 400). verify 31/31·e2e 7/7·codex
High1/Med4/Low3 중 5건 수정.

## 요구가 "고정 스키마 봉투"로 이미 정제되어 왔다
사용자가 JDBC 직결의 복잡함을 스스로 겪고(테이블 6개+ 조인) SELECT→JSONL+JSON Schema라는
**경계가 명확한 인터페이스**를 준비해 왔다. v1 설계가 "SQL은 사용자가, 적재는 우리가"로 단순해진
건 이 정제 덕 — 데이터 소스 통합을 우리가 다 짊어지는 대신, 사용자의 기존 파이프라인 출구를
계약(봉투+스키마)으로 받는 쪽이 양쪽 모두 싸다. 자동화(DB 직결)는 v2로 명시.

## "필요할까요?"라는 질문이 기능이 됐다
JSON Schema 등록은 사용자의 한 줄 질문("혹시 업로드할 때 JSON Schema 필요할까요?")에서 나왔다.
봉투 검사만으론 SQL 변경으로 인한 내용물 드리프트(id 컬럼 누락)를 못 잡는다는 답이 곧 기능 명세가
됐다 — 147의 라벨 질문, 148의 축 분리와 같은 패턴: **사용자의 짧은 질문은 설계 신호**.

## codex가 잡은 것 — 검증기 자체가 공격 표면
- **스키마 ReDoS(High)**: 사용자 등록 JSON Schema의 `pattern`에 병적 정규식 + 8,000자 행 →
  행 전수 검증 CPU 폭주. "검증을 추가하면 검증기가 새 공격 표면"이라는 역설 — v1은 정규식
  키워드 자체를 400으로 거부(기능 제한을 정직하게 안내). 완화 아닌 차단이 더 단순·확실했다.
- **null=미변경 관례가 해제 경로를 삼켰다**: alias에서 쓴 "None=미변경" 관례를 entity_schema에
  그대로 쓰면 오등록 스키마를 영영 못 지운다(ReDoS와 결합하면 업로드 영구 잠김). Pydantic
  `model_fields_set`으로 "미포함=미변경 / 명시적 null=제거"를 구분 — **선택 필드의 3상태(유지/
  변경/제거)는 2상태 관례로 접으면 안 되는 경우가 있다**.
- 캡의 위치(5001번째 행을 처리한 뒤 거부 → 선검사)·metadata 무캡·server_default 불일치 등
  "캡을 달았다"와 "캡이 비용 경계로 동작한다"의 차이를 반복해서 짚음(cap-the-raw-source 계열).

## e2e에서 배운 것
fast-worker가 antd 6의 접근성 이름 함정 2개(아이콘+텍스트 버튼의 합성 이름, Tooltip title이
접근성 이름에 안 실리고 아이콘 aria-label이 실림)를 스스로 실측·교정하고 스크립트에 주석으로
남김 — 148의 "실측 먼저" 원칙이 서브에이전트 산출물에 누적되고 있다.

## 다음에 적용
1. 사용자 입력으로 실행되는 검증기(정규식·스키마·표현식)는 그 자체를 공격 표면으로 취급 —
   비용 경계(크기·키워드·시간)를 함께 설계.
2. 선택 필드 갱신 API는 3상태(유지/변경/제거)가 필요한지 먼저 묻는다 — "None=미변경" 관례를
   무심코 복사하지 않기.
3. 외부 데이터 통합은 "우리가 소스에 붙기" 전에 "사용자 파이프라인의 출구를 계약으로 받기"를
   먼저 검토(경계가 명확하면 v1이 작아진다).
