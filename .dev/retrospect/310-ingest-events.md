# 310 — 배경 잡 이벤트(SSE) + 전역 알림 (스펙 335)

## 무엇을 했나

사용자 제안("성공/실패는 이벤트로 알려줘야") — 334의 폴링(드로어 한정)을 넘어 SSE 전역 채널.
in-process pub/sub(`events.publish`) + GET /events(인증·heartbeat·finally 해제) + AdminShell 전역
구독 → 어느 메뉴에 있어도 "임베딩 완료/실패" notification. 버스는 범용(재인덱싱·평가 런이 후속
한 줄로 합류 가능).

## 핵심 배운 것

### 1) 장수명 연결은 graceful shutdown의 암살자 — 이번 스펙 최대 발견
SSE를 붙이는 순간 dev 서버가 reload마다 **"연결 종료 대기"에 영원히 갇혀 죽은 척**했다(열린
EventSource는 안 닫히니까). 검증 프로브가 "임베딩이 매달린다"로 발굴 — 원인은 내 기능이 서버
수명주기를 바꾼 것. `timeout_graceful_shutdown=5`로 봉합(run()+재기동 레시피 메모리 갱신).
**스트리밍/장수명 표면을 추가하면 종료·재시작 경로를 반드시 재점검**하라. e2e의 networkidle
대기도 같은 이유로 불성립(요소 기준 대기로) — 상시 연결은 "네트워크 조용함" 가정 전부를 깬다.

### 2) 항상 켜진 연결 하나가 도구 체인을 연쇄로 무너뜨렸다
멈춘 8000을 `lsof -ti :8000 | xargs kill -9`로 정리했더니 **vite(프록시로 8000에 연결 중)까지
딸려 죽었다** — lsof는 LISTEN만이 아니라 ESTABLISHED 상대편도 나열한다. 포트 청소는 대상
프로세스를 확인하고 죽일 것(레시피에 경고 추가).

### 3) 이벤트는 알림이지 진실이 아니다 — 의미론을 처음부터 계약으로
구독 전/연결 끊김 동안 발생분은 유실(영속 알림함 아님), 상태의 진실은 문서 status+폴링. 이
구분을 스펙·주석·프론트 코드에 명시해 두면 "알림 놓쳤는데 상태가 왜 이래요"류 혼란이 예방된다.
같은 결: 알림 거부(429 상한)도 기능 무손실이라 부담 없이 걸 수 있었다.

### 4) 브로드캐스트 UX는 "건수 = 알림 수"가 기본값이면 폭주한다 — codex P2
대량 업로드 N건=영구 실패 알림 N개. antd notification의 key 병합(컬렉션+상태)로 최신 것만 유지
— 푸시 알림 설계는 항상 "폭주 시나리오"를 기본 검토 항목으로.

### 5) 테스트 플러드가 자기 큐를 오염 — 격리 실패의 자충수
E2(느린 구독자)를 publish 플러드로 만들었더니 검증용 건강한 큐까지 가득 차 E3이 연쇄 실패.
특정 구독자의 상태를 시험할 땐 **그 구독자만 직접 조작**(slow.put_nowait), 전역 발행은 모든
관찰자를 오염시킨다.
