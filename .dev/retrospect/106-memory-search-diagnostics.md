# 106 — 회고: 메모리 검색이 "왜 0건인지" 안 보이던 문제 (스펙 125)

## 무엇을 / 왜
사용자: "메모리 UI 불편 + **다른 노트북 배포에서 유사도 검색이 안 됨** + 왜 결과가 안 나오는지 알 방법이
없음." 근인은 관측성 부재였다 — `recall_probe`가 미가용 3사유(미설정·모델누락·초기화 실패)를 `None`
하나로 뭉개고, 검색 중 예외(임베더 호출 실패)는 500으로 던져 UI엔 사라지는 토스트만. 사용자 선택:
**진단/디버깅 먼저**. 처방: `recall_diag`(예외 안 던지고 4모드 구조화) + `MemorySearchOut.diag` +
프론트 **지속 진단 패널**(백엔드 상태·임베딩 모델·스코프·회상수·오류). "다른 노트북 설정을 고치기"는
비목표 — **왜 안 되는지 보이게** 해서 그 배포서 "임베딩 미설정/초기화 실패"를 스스로 보게 한다.

## 잘된 것
- **관측성으로 환경 버그를 옮김**: 로컬 재현 불가(다른 노트북=별도 도커)라 코드로 그 환경을 못 고친다.
  대신 진단이 근인을 *그 화면에* 띄우게 만들어 사용자가 자가진단. 로컬 검증 스샷이 "정상·백엔드 준비됨·
  임베딩 모델 표시·회상 0건"을 보여 **0건이 진짜 없음임을 증명**(백엔드는 정상) — 다른 노트북선 여기가
  다른 상태로 뜬다.
- **단일 권위 계약 유지**: 처음엔 `configured`로 조기 반환했다가 verify_084가 4개 red — 테스트가
  `resolve_backend`를 패치해 백엔드를 주입하는데 내가 그 위에서 우회했다. `resolve_backend`를 **가용성
  단일 권위**로 되돌리고 `configured`는 error *문구 선택*에만 씀 → 084 무회귀 + 125 유지. (recall_probe와
  같은 경로 = drift 0.)
- **적대 검증(codex)이 실제 결함 2건 포착**: 오늘 codex 응답. H1=마스킹 정규식이 `api_key: <값>` 공백형·
  hex 토큰 놓침 / M2=검색 예외가 enabled=True·results=[]라 "0건" 오인. 둘 다 수정.

## 아쉬운 것 / 리스크
- **비밀 마스킹은 정규식 추측이 태생적으로 불완전**(codex H1). 근본 처방으로 전환 — **mem_cfg의 실제
  api_key 값을 정확 치환**(형태 무관 1차 방어) + 정규식은 백스톱. verify_125에 hex·라벨공백형·정확치환
  케이스 추가. 그래도 "설정된 키 외" 우발 노출(예: 다른 서비스 키가 예외에 섞임)은 백스톱 정규식 의존.
- **실패≠0건 구분을 UI에서 두 곳 손봐야 했다**(M2): 토스트 억제 + emptyMessage 억제. 진단 패널만 믿고
  기존 "회상 없음" 경로를 안 막으면 실패가 정상으로 위장된다 — 상태 분기 추가 시 *기존 표시 경로 전부*
  점검. [[installed-guard-isnt-covering-guard]] 결.
- 로컬 embedder가 구성돼 있어 "미설정/초기화 실패" 상태를 브라우저로 실제로 못 띄웠다(단위테스트로만).
  다른 노트북 스샷은 사용자 몫.

## 다음 작업 Context에서 상기할 것
- 관측성 부재 버그는 **재현 불가 환경도 "왜"를 그 화면에 띄우게** 만들어 옮긴다(고치는 대신 보이게).
- 진단/시험 도구가 실패를 **삼켜 구조화**할 땐 반드시 "실패≠0건"을 UI 상태로 구분(0건 위장 금지, 084 P2a 결).
- 비밀 노출 정제는 **실제 비밀값 정확 치환 우선**, 정규식은 백스톱(추측 마스킹 단독은 샌다).
