# 165 — useAsyncData/runWithToast 공용 훅

**스펙**: docs/spec/184 · **관련**: 182(리뷰서 발견)·HoC 질문 답

## 무엇을 했나
프론트 복붙(단발 페치+로딩+에러+alive 가드 / mutation try-catch-토스트)을 훅 2개로 흡수.
소비자 3곳 변환으로 추상 무누수 증명. 사용자 "HoC 필요한 곳?" 질문엔 **불필요** 결론을 코드로 실증.

## 무엇이 잘못됐고 무엇을 배웠나

### 1. 훅이 모든 페치에 맞지는 않는다 — "폼 시드" 패턴은 별개
두 번째 소비자로 SettingsView를 노렸다가 부적합 발견: SettingsView는 페치값을 **편집 가능한 폼 필드**
(`orgName`)에 시드하는 패턴이라, useAsyncData(data)를 받아 다시 useEffect로 폼에 복사해야 → 오히려
코드 증가. useAsyncData는 "페치→표시/목록"에 맞고 "페치→가변 폼 시드"엔 안 맞는다. 대신 순수 표시
뷰(MemoryView)를 골라 깨끗이 변환.

- **처방**: 훅을 적용할 때 소비자의 데이터 **수명**을 보라 — 불변 표시 데이터냐(훅 맞음), 가변 폼의
  초기값이냐(훅 부적합, 별 패턴). 억지로 끼우면 boilerplate가 되레 는다. [[probe-deeper-before-concluding]].

### 2. 내 검증 하네스가 과엄격하면, 고칠 건 코드가 아니라 하네스
브라우저 검증서 "콘솔 에러 0" 단언이 실패했으나, 정체는 배경 401·antd6 Alert deprecated 경고—훅과
무관한 사전 노이즈였다. 기능 체크(렌더·로드·reload·no-error-토스트)는 전부 초록. fetcher가 A2/M1서
에러 토스트 0 = 200 성공이므로 401은 다른 배경 호출임을 논리로 확정. 코드가 아니라 **하네스 필터를
정직하게 보정**(사전 노이즈 명시 제외).

- **처방**: 자가작성 검증이 붉으면 "내 변경이 원인인가"를 먼저 격리하라(163의 stash 대조와 같은 규율,
  여기선 "fetcher 성공=토스트0" 논증). 사전 노이즈를 회귀로 오인해 멀쩡한 코드를 건드리지 말 것.
  단, 노이즈를 **끄는 게 아니라 명시 제외**(주석으로 왜 무관한지)—침묵 억제는 진짜 회귀도 삼킨다.

### 3. "HoC 필요한가"의 답은 "공유되는 게 트리냐 로직이냐"
사용자 질문에 리뷰가 **불필요**로 답한 근거를 코드로 실증: 여기서 공유되는 건 렌더 래핑이 아니라
state+effect 로직 → 훅. HoC 니치(조건부 렌더·권한 게이트)는 이미 AuthGate(render-prop)·PagedListShell
(제네릭)·인라인 `<IfCan>`이 덮음. HoC를 억지로 넣으면 에러 표면·권한 분기 다양성을 획일화→과설계.

## 복리 포인트
- useAsyncData가 AgentsView 분해의 `useAgents()` 훅 토대 → 다음 대형 리팩터의 첫 소비자.
- "훅 vs HoC vs 폼시드" 판정 기준 확립: **공유 대상(트리/로직)**·**데이터 수명(불변/폼초기값)**.
