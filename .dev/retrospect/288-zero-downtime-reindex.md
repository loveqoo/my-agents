# 288 — 무중단 재인덱싱 (스펙 313)

## 무엇을 했나
스펙 312가 재인덱싱 중 컬렉션을 **배타 잠금**으로 검색까지 409로 막던 걸, **검색 무중단**으로 진화시켰다.
핵심은 새 코드가 아니라 **이미 존재하던 성질의 발견**이었다.

- **백엔드**: `search_collections`에서 재인덱싱 잠금 검사 **제거**(검색은 커밋된 것을 읽음) · 검색
  엔드포인트의 `locked`→409 매핑 제거 · 모델교체 경로를 "텍스트 읽기→commit→HTTP→짧은 쓰기 txn"으로
  다듬어 트랜잭션 보유 단축 · 원자 스왑이 MVCC 전환점임을 주석 명시. **쓰기(인제스트·재인덱싱)는 여전히
  직렬화, 검색만 예외.**
- **프론트**: ReindexModal 카피를 "재인덱싱 중 접근 잠금"에서 **"검색은 무중단(진행 중 이전 결과 →
  완료 순간 새 결과), 업로드·편집만 잠깐 대기"**로 교정(긍정문).
- **스키마 변경 0** — 세대(generation) 컬럼 불필요.

## 배운 것 / 복리 포인트

- **무중단은 만드는 게 아니라 이미 있던 걸 "막지 않기"였다 — MVCC가 공짜로 준다**. 처음엔 세대 컬럼
  (`Chunk.generation`+`Collection.active_generation`)으로 "옛 세대 서비스하며 새 세대 짓고 플립"을
  구현하려 했다(스키마 2컬럼+마이그레이션+청크 읽는 모든 경로에 세대 필터). 그런데 `_do_reindex`가
  이미 **"새 벡터 전량 계산 → 한 트랜잭션 원자 스왑"**이었다 → Postgres MVCC상 동시 검색은 커밋 전엔
  옛 청크·커밋 후엔 새 청크를 보고 **반쪽은 스냅샷 격리로 원천 불가**. 즉 무중단은 **구조적으로 이미
  성립**해 있었고, 스펙 312가 검색을 막은 건 (당시 명시 요구 +) 내가 "부분결과 위험"을 과대평가한
  탓이었다. **DB가 이미 주는 보장을 앱 레벨 잠금으로 덧씌우면, 그 잠금을 걷어내는 게 곧 기능이다.**
  → [[structure-first-boundary-is-spec]] [[whole-fix-over-minimal-patch]]

- **"세대 컬럼"은 과설계였다 — 격리 수준을 먼저 물었어야**. 세대 기반(갈래 A)은 초대형 컬렉션에서
  단일 트랜잭션 부담을 쪼개는 데는 필요하지만, 개인 도구 규모에선 MVCC 단일 txn 스왑으로 충분하다.
  "무중단=버전 관리"라는 반사적 설계로 뛰기 전에 **"DB가 이 동시성을 이미 어떻게 다루나"**(MVCC/격리
  수준)를 물었으면 스키마 변경을 통째로 아꼈다. YAGNI는 구조가 잡히기 전까지 — 여기선 구조(원자 스왑)가
  이미 있었다. → [[core-is-model-config-and-memory]]

- **무중단 주장은 "실동시성"으로만 증명된다 — happy-path 재현 불가**. 검증을 `not reindex.done()`인
  동안 검색 버스트로 짰다: reindex를 `create_task`로 발사하고 완료 전까지 검색을 반복하면 **그 검색들은
  정의상 재인덱싱 중**이다. 11회 전부 200·hit≥1(409·빈결과 0), 마지막 1회는 hit=2(스왑 커밋 직후·엔드포인트
  반환 직전 창 — 옛→새 전환을 in-flight로 포착). "잠금 제거했다"를 단언하는 단위 테스트만으로는 "검색이
  실제로 안 막힌다"를 못 잡는다 — ASGI in-process + asyncio.gather로 실 동시성을 태워야 잡힌다.
  → [[verification-ladder-three-rungs]] [[ui-verification-must-be-functional]]

- **불변식을 완화하면 그걸 검증하던 테스트가 거짓이 된다 — 같은 턴에 승계**. 스펙 312의 verify_312가
  "잠금 중 검색 → 409"를 단언했는데, 스펙 313이 그 행동을 뒤집으니 그 줄이 곧 회귀 실패로 뜬다. 새
  스펙 테스트만 짜고 옛 테스트를 놔두면 "옛 계약을 지킨다는 초록 거짓말"이 남는다. 313 테스트 신설 +
  312의 그 줄을 200으로 교정(같은 턴). 카피(UI)도 같은 원리로 승계. → [[context-control-propagates-to-affordances]]

- **codex 여집합이 P0 아닌 정직 경계 2개를 짚었다 — 고치지 말고 명시**. (1)다중 컬렉션 검색은 READ
  COMMITTED 문장별 스냅샷이라 한 호출에서 A=옛·B=새 세대 가능(단일 컬렉션 내 혼출·409·빈결과는 아님 —
  각 컬렉션은 원자 전환). (2)관리 CRUD TOCTOU는 스펙 312 F4 기존 경계. 둘 다 안전 위반 아님 → 스펙
  OUT에 근거와 함께 기록(전역 스냅샷 원하면 REPEATABLE READ, 빚). 내 "쓰기끼리 완전 직렬화" 표현이
  과장이라 완화. → [[complement-attack-can-be-honest-boundary]] [[use-codex-for-adversarial-verification]]
