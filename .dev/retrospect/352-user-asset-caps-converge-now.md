# 352 — 스펙 429 회고: 유저 자산 상한 + "지금 수렴하라"

## 무엇을 했나

회수 캠페인(346~352)이 **일부러 안 지운** 축 — 살아있는 유저 기억·메시지 — 에 상한(1000/유저·180일,
구남님 승인). 기억=`memory.add()` 관문서 유저당 초과분 오래된 것부터 축출, 메시지=기존 session-cleanup
(last_activity<cutoff, 활성 보존)의 보존일수 기본 None→180 ON.

## 배운 것(전이 가능)

### 1. "다음 호출이 마저 수렴한다"는 미검증 지연 가정 — 지금 완전히 수렴하라

첫 구현의 축출은 **첫 페이지 100개만** 지웠다. "초과분이 100 넘으면 다음 add가 수렴"이라 주석 달았는데,
codex가 **한 add에 200개 넣는** 시나리오로 깼다: add당 신규 N개, 축출 100개 → total이 +N-100씩 **영원히
증가**(N>100이면). "다음번에 정리됨"은 신규 유입<축출량이라는 **미검증 가정**이었다. 고침=이 호출 안에서
`while total>CAP: 오래된 100 삭제`로 **완전 수렴**(bounded backstop). 상한/회수 로직은 "지금 이 호출이
불변식을 회복"해야지 미래 호출에 미루면 유입이 빠를 때 계약이 깨진다. [[cap-the-raw-source-not-the-buffer]]의
친척 — 경계를 관문에서 **완결**.

### 2. 되돌릴 수 없는 데이터 마이그레이션 downgrade는 정직한 no-op

처음 downgrade는 "값이 정확히 기본값(180·cron)이면 NULL로" 되돌렸다. codex: 사용자가 **우연히 같은 값을
커스텀**했으면 downgrade가 그걸 파괴한다 — 값만으론 "migration이 켠 것"과 "user가 고른 것"을 **구분 불가**.
주석은 "코인시던스 방지"라면서 SQL은 정반대였다. 고침=downgrade **no-op**(정직). 데이터 활성화는 값
되돌림이 아니라 관리자가 설정에서 끈다. 되돌릴 수 없으면 **되돌리는 척하지 말 것**.

### 3. 회수 캠페인이 "안 지운" 축을 상한으로 마감 — 축 분리

346~352는 유령·만료만 지우고 산 유저 자산은 보존(토대). 그 결과 "상한 없음=무한 증가"가 열린 채였다
(스코어보드 0은 분류 정직이지 유계 아님, [[compounding-vs-latent-axis]]). 마감=**축 분리**: 기억은 개수
상한(add 관문, 유저별), 메시지는 나이 상한(세션 배치, last_activity). 한 메커니즘에 욱여넣지 않음
([[find-invariant-before-mechanism]] — 각 축의 자연스러운 관문).

### 4. codex가 또 내 verify(초록)가 놓친 실결함을 잡음 — 반복 패턴

verify가 1001→1000은 확인했지만 **대량 add 수렴**은 내가 상상 못 한 케이스였다(retrospect 351과 동일 —
happy-path 초록). 파괴·비가역 경로엔 codex 적대 검토가 그 자리 관문. 발견은 즉시 테스트로 고정(verify_429
A2 대량 수렴). [[use-codex-for-adversarial-verification]][[verification-ladder-three-rungs]].

## 흠집

"초과분이 크면 다음에 정리"라고 적을 때, "그럼 유입이 축출보다 빠르면?"을 스스로 물었어야 했다.
회수/상한 로직엔 항상 **최악 유입률**을 대입해 수렴을 증명할 것 — 평균이 아니라.
