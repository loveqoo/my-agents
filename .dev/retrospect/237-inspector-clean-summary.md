# 237 — 인스펙터 remove 다듬기: 증상의 계층부터 가른 소크라테스 대화 (스펙 262)

## 맥락
플레이그라운드 인스펙터에서 clean 노드가 "remove / remove / user: «...»"로 떴다. 사용자가 연속으로
물었다: "remove가 실제 프롬프트에 있나?" → "왜 2개 이상?" → "디버깅할 때 알아야 하나?" → "다듬자".
각 질문이 다음 결정을 정확히 좁혔다.

## 무엇을 배웠나

### 1. "거슬리는 표시"를 만나면, 고치기 전에 *계층*부터 갈라라(동작 vs 표시)
사용자의 첫 질문("실제 프롬프트에 있나?")이 정확한 첫 질문이었다. `remove`가 **모델 프롬프트에 있으면**
동작 버그(모델 오염)고, **인스펙터 표시에만 있으면** 겉치레다 — 처방이 완전히 다르다. 코드로 갈랐다:
`ainvoke` 인자는 `[sys, human]`뿐이고 `RemoveMessage`는 *반환 델타*에만(pipeline.py). 표시 아티팩트로
확정. **증상을 보고 바로 고치지 말고, 그게 어느 계층에서 나오는지부터 측정**(learning 043 code-vs-data,
036 측정 먼저의 결). 표시 계층이면 동작은 안 건드린다.

### 2. "왜 N개?"는 메커니즘을 드러낸다 — 개수는 우연이 아니라 신호
"remove / remove"가 2개인 건 그 시점 상태에 이전 메시지가 2개(사용자 입력 + 앞 노드 결과)였기 때문.
개수 = 걷어낸 맥락 수. 대화가 길수록 늘어난다. 이 "왜"를 답하면서 개수가 *디버깅 신호*(격리 경계가
어디였나)임이 드러났다 — 그래서 완전히 숨기면 안 되고 접어야 한다는 결론으로 이어졌다.

### 3. 정밀 디버그 통로에선 신호는 남기고 용어만 사람 말로
플레이그라운드 = 정밀 디버그 통로(메모리). 그래서 "완전히 숨기기"(신호 상실)도 "날것 remove"(잡음)도
아닌 중간 — **"이전 맥락 N개 정리 (격리)"**. 격리가 일어났다는 사실 + 개수(디버깅 신호)는 보존하고,
`RemoveMessage`라는 LangGraph 내부어는 감춘다. 디버깅할 때 알아야 할 건 "이 노드가 앞 맥락을 걷어내고
앞 결과만 받았다"는 *사실*이지 그걸 구현하는 *수단*(상태 삭제)이 아니다.

### 4. 사용자의 연쇄 질문이 스펙을 정확히 깎았다
내가 처음 "다듬을까요?"라고 뭉뚱그려 물었을 때, 사용자는 바로 승낙하지 않고 계층(프롬프트?)→원리
(왜 2개?)→가치(디버깅에 필요?)를 되물어 *무엇을 어떻게* 다듬을지를 스스로 정의하게 했다. 성급히
"숨기기"로 갔으면 디버깅 신호를 날렸을 것. 되묻기가 설계를 깎는다(retrospect 234 결).
