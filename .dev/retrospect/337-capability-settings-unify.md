# 337 — 능력→설정 파생 단일화(스펙 409, 408 재구조화)

## 발단 — 구남님의 정당한 질책

408을 "완료" 커밋한 직후, 구남님이 UI를 열어보고 4가지를 지적했다:
① 모델 폼에 스트리밍·thinking이 **두 번씩** 나온다(헷갈림) ② 새 메타 설정마다 또 구현할 거냐
③ 플레이그라운드 오버라이드가 안 된다 ④ 노드형은 어떻게 할 거냐. 그리고 결정타:
**"그동안 배운 걸 취하지 않고, 복리를 위해 노력하지 않고 바로 작업을 진행한 것 같다."**

전부 사실이었다. 근거를 코드로 확인했다: CapsEditor가 능력+사용을 두 줄로 겹쳐 표시,
`MODEL_PARAM_OVERRIDE_KEYS` 하드코딩(설정 하나=5곳 수술), `OverridePanel.Overrides`에 modelParams
부재(API 세션 층이 UI 없는 허구), 노드형 미설계(codex 급수정만).

## 뿌리 — 복리를 놓친 지점(가장 중요한 학습)

**이 저장소엔 이미 잘 된 설정 캐스케이드가 있었다** — temperature(스펙 077)가 모델→세션을
`OverridePanel`이라는 **범용 오버라이드 장치**로 처리한다. 408의 나는 이걸 **확장하지 않고 옆에
좁은 하드코딩 통로를 하나 더 팠다.** 그래서 중복·불균일·UI 누락이 전부 생겼다. 회고 261의 "사본이면
드리프트"를 설정 축에서 그대로 반복한 것. **교훈: 새 축을 추가할 땐 "이미 이걸 하는 범용 장치가
있나"를 먼저 묻는다. 있으면 확장, 없을 때만 신설.** 바로 코드로 뛰면 이 질문을 건너뛴다.

## 무엇을 했나 — 능력이 설정을 파생시킨다

- **서술자 단일 정본**(`agent/capabilities.py: CAPABILITY_SETTINGS`) 한 목록이 백엔드
  화이트리스트(SETTING_KEYS)·유효값 계산(resolve_effective)·노드 정규화·admin 4화면
  (GET /models/capabilities/descriptors)을 **전부 구동**. 설정 추가 = 목록에 **한 줄**.
- **모델 폼 중복 제거**: 능력당 한 블록(능력 토글 + 능력 ON이면 요청 기본값 하나). 겹친 두 줄 소멸.
- **단일 `CapabilitySettings` 컴포넌트**: 에이전트 폼·플그 오버라이드·노드 편집기가 **공유**(사본 금지).
- **플그 세션 오버라이드 실통로**: `Overrides.modelParams` 추가·전송 → 408의 UI 없던 3층이 실제로.
- **노드별 오버라이드**: 노드 dict `modelParams` + 캐스케이드 노드 층(모델→에이전트→노드→세션).

## 배운 것 (복리 후크)

- **범용 장치 확장 > 옆에 좁은 통로 신설**(위 뿌리). 하드코딩 화이트리스트는 "설정마다 재구현"의
  씨앗 — 정본 목록에서 파생시키면 추가가 한 줄이 된다. FE/BE 드리프트는 엔드포인트로 서빙(사본 0).

- **"유효값=능력 AND 설정"은 모든 축에 균일 적용** — thinking도 능력 게이트에 넣었다(408은 미게이트).
  streaming만 게이트하고 thinking은 안 하면 "부분집합 불가침"이 반쪽. 대칭이 원칙의 증거.
  **이관 주의**: 기존 모델은 thinking 능력 기본 false라 thinking이 꺼진 채 시작 — MLX처럼 thinking
  있는 모델은 관리자가 "Thinking 모드 지원"을 켜야(능력=선언 사실). e2e 스크린샷이 이 동작을 실증.

- **`bool("false")==True` 함정**(codex P1②) — 능력/설정 값을 `bool()`로 해석하면 문자열 "false"가
  게이트를 켠다. **진짜 bool만 인정**(`_as_bool`·`isinstance(v, bool)`)해야 봉인. 검증은 **실행 관문
  (covering guard)에 두는 게 핵심** — 인제스션 정리(clean_*)는 저장을 깨끗이 하지만, ORM/SQL 직접
  우회가 있어도 실행부 `resolve_effective`가 최종 게이트라 안전(installed-guard-isnt-covering-guard의
  올바른 형태: 관문이 부수효과 발생 지점을 덮음).

- **층 순서는 순서대로 적용해야 성립**(codex P1①) — 세션이 노드를 이겨야 하는데, `_apply_overrides`가
  세션을 cfg에 **미리 병합**해 노드가 나중에 세션을 되덮었다. "세션이 최상위"를 코드로 보장하려면
  세션 층을 **노드 뒤에 재적용**해야 한다. 병합 시점이 곧 우선순위 — 미리 섞으면 순서가 무너진다.
