# 회고 184 — 청크 정책 수정 기능 제거 (스펙 198, 재청킹 폐기)

## 무엇을 했나
"재청킹·재임베딩 만들어줘"로 시작 → 코드에서 **원본 미저장**(Document에 원본 텍스트/바이트 컬럼 없음,
Chunk.text만)을 발견 → 사용자와 방향 재합의: 재청킹은 만들지 않고 **혼란의 원인인 청크 정책 수정 기능을
제거**(청크 정책=생성 후 불변, 모델·차원과 동일 취급). 프론트 EditModal 청크 필드 제거 + 백엔드
`CollectionUpdate` 스키마에서 chunk 필드 제거(API 우회 차단). e2e 10/10(API 왕복 무시 + UI 부재)·tsc0·스샷.

## 배운 것

### 1. 기능 요청의 "숨은 전제"를 코드에서 먼저 검증한다 — 착수 전에
"재청킹 만들어줘"는 **원본이 저장돼 있다**를 암묵 전제한다. 그 전제를 코드로 확인하니(`Document` 모델에
raw 컬럼 없음) 원본이 없었다 — 청크는 겹침이 있어 이어붙여도 원본 복원이 불가. 만약 전제 확인 없이
착수했으면 스키마 컬럼·마이그레이션·배경 재처리 잡·진행 UI를 다 만든 **뒤에** "기존 문서는 재청킹 불가"에
부딪혔을 것이다. **교훈: 기능 요청을 받으면 그 기능이 성립하기 위해 **이미 있어야 할 데이터/상태**를
코드에서 먼저 확인한다 — 없으면 그 사실이 설계의 첫 입력이다([[probe-deeper-before-concluding]]의 착수
전 버전; "만들 수 있나"를 "무엇이 이미 있어야 하나"로 되묻기).**

### 2. "만들어줘"를 곧이곧대로 만들기 전에 근본(혼란원)을 짚으면 더 작은 답이 나온다
사용자가 재청킹을 원한 진짜 이유는 "청크 크기를 바꿨는데 기존 문서가 안 바뀐다"는 혼란이었다. 재청킹은
그 혼란을 **비싸게**(원본 저장+재처리) 푸는 길이고, **청크 수정 기능 제거**는 혼란의 원인 자체를 없애는
싼 길이다. 원본 미저장을 알리자 사용자가 후자를 골랐다. **교훈: 기능 요청의 배후 불편을 먼저 말로 옮기면,
요청한 기능보다 근본을 없애는 더 작은 해가 보인다(추가 < 제거).**

### 3. 프론트 필드만 지우면 샌다 — 불변은 백엔드 스키마로 계약한다
청크 수정 제거를 EditModal 필드 제거로만 끝내면 구 클라이언트/직접 API 호출이 `chunk_size`를 그대로
보내 값을 바꿀 수 있다. `schemas.py`의 `CollectionUpdate`에서 필드를 **제거**하면 Pydantic이 그 키를
무시해 불변이 스키마 계약이 된다. e2e에서 **구 클라이언트를 재현**(PUT에 chunk_size+1234 전송)해 값
불변을 확인했다 — UI 부재만 봤으면 이 우회를 놓쳤다. **교훈: "수정 못 하게"는 입력 UI 제거가 아니라
**쓰기 입구(스키마/라우트)에서 필드를 없애는 것**이고, 검증은 "UI에 없다"가 아니라 "구 클라이언트가
보내도 무시된다"로 한다([[installed-guard-isnt-covering-guard]]·[[gate-on-intent-value-not-mutable-baseline]]와
같은 결 — 방어는 부수효과 발생 지점에서).**
