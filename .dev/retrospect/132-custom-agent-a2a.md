# 132 — 스펙 154: 커스텀 에이전트 A2A 공개 회고 (자율 루프 5건차)

## 무엇을 했나
실사용 #3(+백로그 ③ 흡수): private↔public 전환(승격/강등) 신설, code(제1자 SDK 배포) 에이전트의
A2A 1홉 중계 공개, external 재공개 봉인 유지. verify 12/12·e2e 16/16·codex High 0(Low 1 수정,
판정 3건 경계 기록).

## 보고된 증상과 실제 원인이 달랐다 — 게이트 조합이 만든 착시
"커스텀은 A2A 공개가 안 된다"의 실체는 source 게이트가 아니라 **private 게이트(147)**였다 —
사용자가 만드는 모든 에이전트가 소유자 스탬프(=private)를 받으므로 A2A가 항상 거부됐고, 서빙
파이프라인은 공통 인터페이스(impl)를 처음부터 해석하고 있었다. 147을 설계할 때 OUT시킨 승격
기능이 사실상 A2A 공개의 선행 조건이었던 것 — **한 스펙의 OUT이 다른 기능의 차단기가 될 수
있다. 기능이 "안 된다" 보고를 받으면 게이트를 하나씩 벗겨 어느 게이트인지 특정부터.**

## 중계 설계에서 배운 것
- 순환 방지의 v1 답은 "표식 헤더 + 1홉 한정" — 완전한 사이클 방지(서명 홉 토큰)는 등록자 신뢰
  경계 밖의 위협이라 OUT으로 정직 기록. **가드의 목적(실수 방지 vs 악의 차단)을 나눠 적으면
  v1 범위가 명확해진다.**
- 중계 인증의 두 축을 분리: 우리 노출 입구 인증(current_principal)과 원격 호출 자격(등록 시
  저장한 토큰) — "public으로 켜면 등록자 토큰으로 대리 실행"을 경계에 명시.

## 검증에서 배운 것
- e2e가 시드 에이전트를 조작할 때 "사전/사후 curl 실측 + 예외 안전망 강제 원복"이 실제로
  발동해 상태 훼손 0 — 150에서 세운 "전역 상태 e2e는 원복이 검증 항목" 원칙이 예외 경로에서도
  동작함을 확인.
- ASGI 루프백으로 A2A 카드→message/send까지 실행하는 통합 검증이 impl 해석·중계 응답을 한
  번에 실측 — mock A2A(/_remote)가 실서버에 떠 있는 구조 덕분(dogfood 인프라의 복리).

## 다음에 적용
1. "안 된다" 보고 → 어느 게이트에서 거부되는지 특정(에러 메시지/코드 경로)부터 — 게이트가
   여러 겹이면 사용자는 가장 바깥 것만 본다.
2. 스펙에서 기능을 OUT할 때 "이 OUT이 차단하는 다른 시나리오"를 한 줄 적기.
3. 가드는 목적(실수/악의)별로 나눠 명시 — v1 범위 결정이 빨라진다.
