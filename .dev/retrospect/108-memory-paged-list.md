# 108 — 회고: 메모리 서버 페이지네이션 + 일치/유사도 통합 (스펙 127)

## 무엇을 / 왜
사용자: 메모리 UI가 여전히 불편 — 계속 증가하는 데이터에 전량 렌더는 무겁고, 일치+유사도 둘 다,
디버깅 정보도, 그리고 "다른 메뉴의 모범"이 될 조합을 조사 후 논의. **첫 오케스트레이션 실전**:
deep-reasoner(조사)→사용자 결정(안 B)→메인(스펙·보안 코드)→fast-worker(브라우저 검증)→codex(적대).
결과: `MemoryBackend.list_page` 추상 계약(사용자 확정: 페이징을 추상 레이어에) + mem0 raw SQL 구현 +
inmemory 구현 + 페이지 라우트 2개 + `PagedMemoryList`(Segmented 일치/유사도, SessionsView 패턴 이식).

## 잘된 것
- **조사가 진짜 버그를 캤다**: deep-reasoner가 "무겁다" 이전에 **20건 잘림**(mem0 get_all 기본 top_k=20,
  21번째부터 불가시 + user_owns 오거부 가능)을 증거(파일:라인)로 발견. UI 개선 요청이 정합성 버그
  수정을 동반하게 됨. 실측(psql로 payload 키·created_at 확인)으로 "추정"을 착수 전에 소거.
- **협업 분담이 컨텍스트를 아꼈다**: 조사 96k·브라우저 66k 토큰이 서브에이전트에서 소화되고 메인은
  결정·보안 코드·종합만. fast-worker는 지시서의 틀린 가정(드롭다운 출처가 mem0가 아니라
  sessions.user_id distinct)을 스스로 발견·해결하고 차이를 보고 — 위임 보고 형식(건드리지 않은 것/
  이상 징후)이 작동.
- **검증 수렴**: 내가 선제 발견한 stale-응답 경합(reqSeq)을 codex도 MEDIUM으로 독립 지적(이미 수정됨).
  codex 잔여 2건(offset 무제한 DoS·created_at 텍스트 정렬 취약)도 즉시 수정 + 회귀 핀(C11).
- **사용자와 트레이드오프 재설명**: 첫 A/B 질문에 "몰라서 선택 불가" 답 → 일상어·비유(도서관)·판단 기준
  하나("얼마나 쌓일 것 같나")로 재설명 후 결정. 스펙 전 재확인 질문(mem0 페이징 되나? 추상 레이어에?)이
  설계를 더 명확하게 만듦.

## 아쉬운 것 / 리스크
- **계약 테스트의 가짜가 실제 API와 어긋나 있었다**: verify_040 fake get_all이 top_k 인자를 안 받아
  (a) 기본 20 잘림 버그를 계약 테스트가 못 잡았고 (b) 수정이 오히려 red가 됨. 가짜를 실제 시그니처
  (top_k=20 기본+슬라이스)로 미러링해 교정 — GREEN이 버그를 굳히는 124 부류의 "가짜 드리프트" 변형.
- offset 페이지네이션은 수십만 건 규모에서 느려짐 — keyset(커서) 전환은 후속(OUT 명시).
- created_at 정렬은 payload 텍스트 기반(가드 캐스트로 방어) — mem0 스키마 결합은 mem0_backend에 격리했으나
  업그레이드 시 점검 필요.
- 브라우저 최종 스샷이 유사도 모드 상태라 일치 모드 페이지네이션은 프로그램 체크로만 확인(8/8이라 수용).
