# 353 — 스펙 430 회고: 외부호출 정책 관문 + "판정 불가 종료"

## 무엇을 했나

kpas 비교 7항목 중 유일한 실측 빈틈(#2)을 채택 — 흩어진 타임아웃 하드코딩 9곳을 `net_policy.py`
대장 한 곳으로, 모델 본선의 암묵 SDK 기본(600s·재시도2)을 명시 정책(180s·0)으로, 서킷브레이커
(3연속→30s 열림→half-open)로 행 반복 방어. codex P1 5건 전부 실결함 봉합.

## 배운 것(전이 가능)

### 1. 외부 비교 분석은 "전부 흡수"가 아니라 "걸러서 하나" — 전제 실측이 필터

kpas 7항목을 그대로 받으면 회사 층 과투자·금칠이 섞인다. 각 항목을 "실측된 우리 빈틈인가 + 회사
층인가 + 핵심인가"로 걸러 #2 하나만 채택 — 채택 근거도 grep 전수 실측(모델 본선 무정책)이었다.
[[verify-premise-before-designing]]의 비교분석 판. 나머지는 발단 절에 기각 사유를 남겨 재론 비용 0.

### 2. 내 기각 논리를 사용자가 뒤집을 때 — 축이 다르면 결론이 다르다

브레이커를 "대량 트래픽 연쇄장애 장치 → 개인 도구 과설계"로 기각했는데, 구남님이 교정: 개인 사용의
고통은 **행 반복**(죽은 의존성에 매 요청 타임아웃 풀 대기)이다. 같은 장치도 판정 축(볼륨 보호 vs
대기시간 UX)에 따라 결론이 뒤집힌다 — [[cpu-axis-not-latency]]와 같은 부류의 축 오류. 기각 전에
"이 장치가 이 사용자의 어떤 고통을 없애나"를 먼저 물을 것.

### 3. 스트림/제너레이터 관문의 제3상태: "판정 불가 종료"를 설계에 넣어라 (codex P1의 뿌리)

성공/실패 2상으로 설계한 회로 기록이 **GeneratorExit(소비자 이탈)·비일시 오류** 경로에서 깨졌다 —
어느 쪽도 기록 안 되면 half-open trial이 영영 남아 회로 고착, 반대로 초기값 True(A2A)면 이탈이
성공으로 오염. 수리=3상(완주=성공·전송층 죽음=실패·**그 외=release**(trial만 해제)). 스트림을 감싸는
모든 상태 기계는 "완주 못 한 채 끝나는 길"을 별도 상태로 가져야 한다 — try/except/else의 else는
제너레이터에선 소비자가 끝까지 읽어야만 도달한다는 함정 포함.

### 4. transient 판정은 개별 타입 열거가 아니라 계열 루트로

ConnectError만 보면 mid-stream RST(ReadError)·EOF(RemoteProtocolError)를 놓친다 — "연결이 죽는 모양"
은 여러 타입이라 **httpx.TransportError(계열 루트)**로 잡아야 한다. HTTPStatusError는 그 계열 밖이라
"서버가 살아 응답"이 자연 제외되는 부수 이득. 예외 분류는 열거보다 계층.

### 5. grep 전수의 그물도 패턴이 좁으면 샌다

`httpx.AsyncClient(` grep으로 "전수"했는데 `asyncio.timeout(15)`(discovery)이 그물 밖이었다 — codex가
적중. 열거 grep은 **한 패턴이 아니라 부류의 모든 표현형**(httpx·asyncio.timeout·wait_for·SDK 인자)
으로. [[learning 149]]의 확장: 전수 grep도 패턴 다양성이 없으면 자가선언과 같다.

### 6. timeout 수치를 옮길 때 의미(per-phase vs wall-clock)도 함께 옮겨 적어라

대장에 "전체 deadline"이라 적었는데 httpx/SDK 배선은 per-phase(행 감지)다 — 수치는 맞고 **의미가
부정직**했다. 정책 대장은 값만이 아니라 배선 의미까지 명시해야(같은 180이 asyncio.timeout이면 총
벽시계, httpx면 청크 간 침묵 한도). 스트리밍 총 시간 무한은 의도임을 OUT에 정직화.
