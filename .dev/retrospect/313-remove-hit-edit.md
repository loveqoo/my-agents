# 313 — 검색 히트 편집 진입 제거 (스펙 338)

## 무엇을 했나

사용자 결정("검색 기능에 수정을 넣지 말고 일반 임베딩처럼 리스트에서")으로 333(히트→편집)·
337(ordinal 좌표)을 롤백 — UI·주입점·에디터 locate 기제·소비자 잃은 백엔드 배관(document_id/
ordinal)·전용 테스트까지 닫힌 제거. 편집 진입은 문서 목록 한 곳(331/332).

## 핵심 배운 것

### 1) 기능 제안이 통과했어도 실사용 첫 접촉이 최종 심사다
333은 사용자 아이디어("검색 결과에서 버튼으로 즉시 수정")에서 출발했고 e2e까지 통과했지만,
실사용 첫 접촉(337 버그)에서 "검색=관찰, 편집=목록"이라는 더 단순한 멘털 모델이 이겼다.
아이디어 채택 ≠ UX 확정 — 만들었어도 실사용 피드백에 가볍게 되물릴 수 있게 층을 얇게
(주입점 하나·additive 필드)유지한 것이 롤백 비용을 반나절이 아닌 20분으로 만들었다.

### 2) 롤백도 "닫힌 제거"다 — 329 규율 재적용
UI만 걷으면 백엔드 배관(document_id·ordinal)·주입점(hitAction)·locate 기제가 소비자 0의 죽은
표면으로 남는다. 제거 전 소비자 grep → 유일 소비자 확인 → 배관까지 동반 제거 → 제거 심볼
grep 0 확인. 전용 verify/e2e도 대상 기능과 함께 삭제(가치가 남은 단언은 없었음 — H5 비노출
핀은 대상 필드 자체가 소멸).

### 3) 롤백된 스펙 문서에는 그 자리에서 이정표를
333·337 문서 머리에 "338에서 롤백" 주석 — 미래의 Context 단계가 스펙만 읽고 산 기능으로
오독하지 않게(324 감사의 '폐기 잔재' 축을 문서에 선제 적용).

  제거 심볼 grep 0 · lint/mypy/tsc/build 클린.
