# 243 — codex 적대 리뷰(262-268): 예약 접미와 재개 경로의 세 번째 반복 (codex 후속)

## 맥락
262~268(인스펙터 귀속·데모 전환·도구 이름 해석·문구·컬렉션별 RAG·회상 프록시)을 codex에 8개 각도로
넘김. P1 0건 — 프록시 스코프 격리·도구 풀 경계·컬렉션 스코프·suffix 악용은 **안전 확인**(by-design
기록). P2 2건 + P3 3건 전부 확증 후 수정.

## 발견과 교훈

### 1. 파생 id를 만들면 그 이름공간은 예약해야 한다 (P2 — `A__tools` 충돌)
엔진이 도구 노드 id를 `<노드>__tools`로 *파생*하는데, 사용자 노드 이름이 그 이름공간을 침범할 수
있었다(노드 "A"+도구, 노드 "A__tools" → 그래프 빌드 크래시 + 인스펙터 오귀속). `_unique_node_ids`가
사용자 이름끼리만 dedupe하고 파생 id는 안 셌던 것. 처방: 예약 접미로 끝나는 이름에 '_' 덧붙여 회피.
**규칙: 사용자 입력에서 id를 만들고 + 거기서 또 파생 id를 만들면, 파생 규칙의 상(image)을 예약**하라
— 265(이름 체계 접점)의 형제: 이름공간이 겹치는 지점은 전부 계약이다.

### 2. 재개 경로는 세 번째 반복이다 — "원 턴 컨텍스트 축" 체크리스트가 필요했다
approval 재개가 recall_scope의 user 축을 None으로 뒀다(원 요청자 approval.user_id가 있는데도) —
브로커 RBAC는 이미 그 값을 쓰면서 회상만 빠뜨림. **231(재개가 principal/chain 유실)·이번(user 축
유실)·트레이스 미방출까지, "재개는 원 턴의 컨텍스트 축을 전수 재구성해야 한다"가 세 번째 반복**이다.
새 축(이번엔 recall_scope·memoryRecalls)을 메인 경로에 더할 때마다 재개 경로가 자동 승계하지 않음 —
메인에 축을 더하면 재개·A2A에 같은 축을 갖다 댈 것(learning 149 grep 규율에 "재개 미러" 축 추가).

### 3. 새 트레이스 표면은 기존 표면의 마스킹 규약을 상속하지 않는다 (P3 — query 원문)
memoryRecalls.query를 원문(120캡)으로 실었는데, input 모드 키워드는 앞 노드 출력이라 비밀이 섞일 수
있다. 다른 트레이스 표면은 전부 _sanitize/_redact를 거치는데 새 표면만 맨몸 — 089(값 allowlist)의
변주: **표면을 새로 만들면 형제 표면의 정화 규약부터 이식**하라.

### 4. "조용한 무동작 선택지"는 만들 때 잡는 게 싸다 (P3 — 단기만 선택)
단기(세션)만 고른 노드는 회상이 조용히 안 돈다 — 사용자 질문("단기가 뭐냐")에서 이미 드러났고 백로그에
넣었던 것을 codex도 P3로 확인. RECALL_BLOCK 미러 상수 + 경고 한 줄로 봉합(선택은 보존 — 금지 아닌
안내). 086(dead-state)의 UI판.

### 5. 안전 확인도 수확이다
프록시 캐시의 교차 사용자 격리(턴당 생성+스코프 복사)·도구 풀 경계(_resolve_tool은 ctx.tools만)·
컬렉션 스코프(서버측 rag_collections에서만 빌드)가 by-design으로 확인됨 — 268 설계의 핵심 보증
3개가 적대 검토를 통과했다는 기록 자체가 다음 리뷰의 비용을 줄인다.

## 조치

trace.memoryRecalls 방출 + NodeListEditor 회상 안내. verify_268 22/22(+2 케이스) + 전 무회귀 +
tsc 0 + 실모델 e2e 재확인 ALL GREEN.
