# 회고 212 — 능력×타입 조합 전수 매트릭스: 자가 초록 밑의 false-green을 codex가 3건 적발 (스펙 233)

## 무엇을 했나
사용자 지시: 에이전트의 도구·기능·타입 경우의 수를 계산하고 **모든 조합을 실제 발동까지** 테스트하라
(계기: 스펙 201 후속2 — 위키 도구가 능력 부여됐고 단위테스트 초록인데 실제 대화선 발동 안 함=배선 부재).
축을 코드 정본에서 열거(impl 8 × 기능 6 = 48칸), verify_110 패턴(실 저장 config→채팅 관통→trace 단언,
오버라이드 금지)으로 하네스 작성. 서브에이전트가 "48칸 전부 초록·결함 0" 보고. **믿지 않고** 직접 재현 +
codex 2라운드 적대 검증 → false-green 3건 적발·봉합 후 정직 초록(PASS 30 + IGNORE-OK 26).

## 배운 것

### 1. "테스트 초록"의 3가지 위장 통과 — 신호가 발동을 *증명*하나를 캐라
서브에이전트도 나도 첫 초록을 냈지만 codex가 셋을 짚었다:
- **노드 존재 ≠ 성공**: `broker_invoke:{kind}` 노드는 provider가 error여도 남는다. "위임 노드 있음"을
  "능력 동작함"으로 읽으면 A2A·RAG·memory 실패가 초록. → 성공 필드(error 없음·hits·resultPreview)까지 봐야.
- **표면 우회로 무시 위장**: memory 무시칸을 실 표면(config.memories) 대신 브로커 표면으로 배선해 IGNORE.
  실 표면으로 검증하니 정반대(플랫폼 회상 발동)가 진실이었다.
- **공유 상태 누수로 vacuous 참**: memory는 유저 단위 공유 → 앞 셀 프라이밍이 누수돼 config.memories
  없이도 회상 hit>0 가능. → **인과 대조**(같은 impl, 배선 없으면 신호 0)로 못 박아야 참이 됨.
**교훈: 발동 신호는 "존재"가 아니라 "그 배선이 원인이고 실제로 성공했나"를 증명해야 한다. 대조군(무배선→
무신호)이 false-green 최후 방어선. [[ui-verification-must-be-functional]]의 e2e 판.**

### 2. 자가검증(서브에이전트 포함)은 상상한 성공만 본다 — 적대 타자가 여집합을 친다
서브에이전트가 정직하게 "결함 0"을 냈지만, 그건 *자기가 설계한 신호*가 다 떴다는 뜻일 뿐. codex는 "발동
안 했는데 초록 날 경로"(여집합)를 물어 3건을 팠다. **다자 초록을 겹쳐도 자가검증이면 같은 사각을 공유한다
— 반드시 적대 타자(codex)로 rung3.** [[use-codex-for-adversarial-verification]]·[[verification-ladder-three-rungs]].

### 3. 예측을 실측이 반증하면 실측이 맞다 — memory는 impl-게이트가 아니라 플랫폼 레벨
매트릭스를 19/29로 예측(memory가 impl consumes로 게이트된다 가정)했으나 실측은 22/26. `config.memories`
회상은 impl 실행 *전* 플랫폼 선처리라 consumes(폼 힌트, 스펙 206)와 무관하게 발동 — artifact도 회상.
**교훈: consumes 같은 "선언"을 런타임 게이트로 착각 말 것. "기능이 타입별로 게이트된다"는 깔끔한 모델이
틀릴 수 있다 — 조합 전수 실측이 그 가정을 깬다.** [[probe-deeper-before-concluding]].

## 다음에 적용
- 발동 테스트: 신호 존재+성공 필드+무배선 대조(인과) 3겹. 공유 상태(per-user memory 등)는 누수 경계.
- 하네스도 자가검증이다 — 초록 나면 codex에 "false-green 경로"를 물어라(특히 노드/플래그를 성공으로 읽는 곳).
- 능력×타입 조합은 실측이 스펙 예측을 정정한다(선언≠런타임).
