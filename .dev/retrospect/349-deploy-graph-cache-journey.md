# 349 — 스펙 421 회고: 배포 그래프 캐시 완주(설계 교정 3번의 기록)

## 무엇을 했나
6유형 중 5유형(default 기편입 + route·plan·orchestrate·pipeline)을 버전 그래프 캐시에 편입 —
전 유형 graph 빌드 0.00ms(요청당 → 버전당 1회). artifact만 정직 제외. 커밋 4개(P1·P3·P2·복잡도).

## 설계가 3번 교정됐다 — 매번 같은 방향(불변식이 메커니즘을 소멸)

1. **"프롬프트 런타임 주입" 제안 → 구남님 "버전 고정인데 왜 가변?"** — 프롬프트는 가변이 아니라
   캐시 키 입력. 주입 메커니즘 자체가 불필요해짐. → [[find-invariant-before-mechanism]] 메모리 탄생.
2. **순수-promptless 설계 → codex "eval 경로 프롬프트 유실"** — "모든 invoke 경로가 seed를 넣어야
   한다"는 전제가 amnesiac-actor 함정. → **이중 모드**(주입=기본 안전동작, promptless는 캐시 관문
   한 곳만)로 재설계. 이후 P2/P3가 이 패턴을 그대로 재사용(재설계 비용이 복리로 회수됨).
3. **재개 promptless를 지문으로 판정 → codex "배포 경계 레거시 유실"** — 지문은 *현재 코드의 추측*.
   → **체크포인트 상태 실물(seed 유무)로 판정** — 레거시/신규 구분 자체가 소멸하고 371 시절 default
   구멍도 함께 닫힘. "재개 그래프의 모양은 상태가 결정한다"는 불변식.

## 배운 것

- **적대 검증의 값**: codex 4라운드가 결함 5건(eval 유실·call_tool config·HIL 삼킴·caps rename·
  레거시 재개)을 잡았고, 셋은 내 자가 검증(verify_421 초록)이 절대 못 잡는 경로였다(eval·discovery·
  배포 경계). 자가 그물은 상상한 실패만 본다 — 여집합은 타자에게.
- **fail-safe 방향 설계**: 캐시 빌드를 스트립+스텁으로 지으면 "주입을 잊은 미래 경로"의 실패 모드가
  누출(silent)이 아니라 기능 생략/정직 실패(loud-ish)가 된다. 실수 가능성을 없애는 게 아니라 실수의
  **결과를 안전한 방향으로** 미리 접는 것 — amnesiac-actor 원칙의 실전형.
- **측정 잣대의 신뢰 구간**: 프로세스 CPU 델타는 dev 서버 노이즈(초기화·자기-호출·백그라운드)에
  흔들린다(런 간 route 10↔27ms). 트레이스 스톱워치(buildMs.graph)는 6런 내내 0.00 재현 — 잣대를
  고를 때 "무엇이 섞여 들어오나"부터. 자기-호스팅 mock으론 동시성 측정 금지(learning 398).
- **내 실수 기록**: 측정 중 서버 재기동(net-runs-are-exclusive 위반, 운 좋게 무해)·F821(thread_id
  스코프 — 재개 500, verify_101이 즉시 잡음)·테스트 자체 결함 2건(mock config 주입 애노테이션,
  agentId vs uuid). 배터리가 넓어서 전부 커밋 전에 잡혔다 — 그물 폭이 곧 실수 허용량.

## 다음에 적용
- 캐시/공유 구조 설계 시: ① 버전이 정하는 값 vs 같은 버전에서 요청마다 다른 값 분류 → ② 후자는
  config-우선 이중 모드 → ③ 캐시 빌드는 스트립+스텁 → ④ 재개류 재구성은 상태 실물로 판정.
- 새 impl 저자는 manifest 선언 2개(cacheable·seed_prompt)만 옳게 쓰면 캐시가 안전 — 선언을 잊으면
  기본값이 비캐시(안전)라 실수 방향이 느림이지 누출이 아니다.
