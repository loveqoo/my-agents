# 회고 209 — "모드 전환"이 도구 전체를 갈아치우면 Segmented 아니라 Tabs (스펙 219)

## 무엇을 했나
메모리 [일치/유사도]를 Segmented→Tabs로 통일(상위 기억 Tabs와 시각 일관, 사용자 지적). 원래 스펙 212서
"검색 모드=Segmented"로 분류했으나, 실제로 일치=편집 목록·유사도=회상 시험 패널이라 서로 다른 도구 →
Tabs가 규칙(내용 자체 전환)에도 부합. 자매 두 패널(에이전트·유저) 동시 처리. 검증 브라우저 role=tab.

## 배운 것

### 1. "모드 전환"이라는 이름에 속지 말 것 — 바뀌는 게 표현이냐 도구냐로 가른다
Segmented 규칙("같은 목록의 필터·모드")의 함정: *이름이* "모드"라고 다 Segmented가 아니다. 판별 기준은
**전환 후 바뀌는 것이 같은 데이터의 표현(정렬·필터·랭킹)인가, 아니면 화면/도구 전체(다른 위젯·다른
액션)인가**다. 일치/유사도는 편집 목록 ↔ 회상 시험이라 도구가 통째로 바뀐다 → Tabs. 나는 "검색 모드"라는
라벨에 이끌려 Segmented로 분류했다. **교훈: 컨트롤 종류는 라벨(모드/필터/종류)이 아니라 *전환이 무엇을
갈아치우는지*로 정한다. 표현만 바뀌면 Segmented, 도구·내용이 바뀌면 Tabs.** (스펙 212 규칙의 정밀화 —
회고 204 lesson1 "시각 일관"의 근거를 규칙 언어로 확정.)

### 2. 규칙의 예시가 실제와 어긋나면 규칙 예시를 고쳐라(코드만 고치고 규칙 방치 금지)
admin/CLAUDE.md가 일치/유사도를 Segmented 예시로 명시하고 있었다. 코드만 Tabs로 바꾸고 규칙 예시를
두면 다음에 이 규칙을 읽는 사람(나 포함)이 다시 Segmented로 되돌린다. **교훈: 분류를 바꾸면 그 분류를
성문화한 규칙 문서의 *예시*까지 같은 변경에서 갱신 — 규칙과 구현의 드리프트는 곧 재발이다.**

## 다음에 적용
- 탭 vs 세그먼트는 "전환이 표현을 바꾸나(Segmented) / 도구·내용을 바꾸나(Tabs)"로 판정 — 라벨 무시.
- 분류 변경 시 규칙 문서 예시도 동반 갱신(코드-규칙 드리프트 0).
- 자매 화면(에이전트/유저 패널) 동시 처리.
