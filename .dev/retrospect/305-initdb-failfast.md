# 305 — init_db create_all 폴백 제거: fail-fast (스펙 330)

## 무엇을 했나

329가 실증한 "조용한 마이그레이션 우회"를 근원 제거 — alembic 실패 시 warning+create_all+head
스탬프하던 폴백을 걷어내고, 원인 후보·진단 명령을 담은 메시지로 부팅 중단. alembic = 스키마 단일
진실. 사용자 결정은 3안 중 완전 제거(virgin 한정 폴백도 "새 DB에서 고장난 마이그레이션을 계속
가림" — 어제의 일회용 DB가 정확히 그 케이스라 기각).

## 핵심 배운 것

### 1) 폐기 경로의 행동 집합 열거(learning 060)가 이번에도 P2를 3개 잡았다
폴백이 지탱하던 행동 5종(①pgvector 확장 보장 ②빈 DB 스키마 생성 ③head 스탬프 ④seed provider
블록 도달 ⑤연결예외 이중 throw 방지)을 codex에 열거시켜 승계 3·의식적 폐기 2로 전수 판정.
잡힌 것: 폴백 에러 메시지에만 있던 **pgvector 권한 안내가 새 메시지에서 누락**(관리형 PG
비수퍼유저가 엉뚱한 축을 디버깅하게 됨), README의 구 계약 3곳. "코드만 지우면 끝"이 아니라
**메시지·문서가 나르던 행동**까지가 폐기 대상이다.

### 2) 검증 인프라가 검증 대상을 선점하면 그 보장은 검증 안 된 것이다
F2(virgin 부팅)가 "마이그레이션이 확장을 보장한다"를 실증한다고 믿었지만, `_create()`가 DB 생성
직후 **확장을 선설치**해 마이그레이션의 CREATE EXTENSION이 삭제돼도 F2는 계속 초록(codex P2).
→ 선설치 없는 DB 경로(F4)를 별도로 둬야 보장이 실측된다. 328의 "단위 직접호출은 디스패치
게이트를 안 탄다"와 같은 족보 — **검증 경로가 제품 경로의 전제조건을 미리 채워주면 안 된다**.

### 3) 소스 문자열 단언 테스트는 리팩터의 숨은 소비자다
verify_058이 `inspect.getsource(init_db)`로 폴백 내부 순서("engine.begin 앞에 preflight",
"확장이 create_all 앞")를 고정하고 있어 폴백 제거 즉시 크래시할 운명이었다(사전 grep으로 발견).
소스 단언은 라이브 인프라 없이 계약을 고정하는 값싼 수단이지만, **대상 코드가 사라지는 리팩터의
소비자 목록에 "소스를 읽는 테스트"도 넣어야** 한다(심볼 참조 grep에 안 걸린다 — index()는 문자열).

### 4) "실패를 삼키고 대체하는" 복원력은 시간이 지나면 부채가 된다
폴백은 스펙 059 시절 정당한 첫 설치 복원력이었지만, 마이그레이션 체인이 virgin DB를 완주하게 된
뒤로는 **발동 조건 = 진짜 고장**뿐이라 순수 은폐 장치로 퇴화했다. 복원력 장치에는 "이게 언제
정당한가"의 만료 조건을 함께 적어두는 게 좋다(330의 fail-fast에는 그 자체로 만료가 없음 — 실패를
가리지 않는 건 퇴화하지 않는다).
