# 회고 185 — '능력 부여' UI 개편 (스펙 200, 199 진단의 구현)

## 무엇을 했나
스펙 199 진단(자유입력·코드노출·대상혼재·맥락부족) + 추가 발견 P5(기억 3종이 UI에 없어 부여 불가)를
한 번에 구현. 자유입력→카탈로그 Select(판정 키=value)·`capability:…`→문장 미리보기(코드는 작은
회색/툴팁)·역할/유저 Segmented 분리·도입 문장·종류 6종 완성. 백엔드 무변경(프론트만). e2e 18/18
(옵션 수=실 자원 수 측정 포함)·tsc0·스샷.

## 배운 것

### 1. 카탈로그 Select의 급소는 목록이 아니라 "value=판정 키" 일치다
자유입력을 Select로 바꾸는 것 자체는 쉽다. 급소는 **Select의 value가 백엔드 판정 키와 정확히 같아야**
한다는 것 — agent는 이름(name)이 아니라 외부 id(`agt_…`)가 브로커 판정 키(`_cap_resource`)였다.
이름을 value로 썼으면 겉보기엔 부여됐는데 **영영 매칭 안 되는 무효 부여**가 됐을 것이다(자유입력
오타와 동일 결과 — 형태만 바뀐 같은 버그). 구현 전에 백엔드 판정 코드에서 kind별 키(mcp=서버 name·
rag=컬렉션 name·agent=agentId)를 역산해 value를 정했고, e2e로 선택→코드 라인이 `agt_…`인지 확인했다.
**교훈: 자유입력→Select 전환은 "목록 보여주기"가 아니라 "판정 키를 value로 박기"다. 판정하는 쪽
코드를 먼저 읽고 키를 확정한 뒤 UI를 만든다.**

### 2. UI의 닫힌 목록은 코드의 전체 집합과 대조한다 — 좁으면 기능이 조용히 죽는다
종류 Select에 mcp/rag/agent 3종만 있었는데 코드(broker)의 kind는 6종 — 기억 3종은 **UI로 부여할
방법이 아예 없었다**(에러도 안 나고 그냥 불가능). 진단(199)엔 없던 문제를 구현 착수 시 kind 상수
전수 대조로 발견했다. **교훈: UI에 하드코딩된 닫힌 목록(종류·상태·옵션)을 만지면 소스 코드의 전체
집합과 개수 대조부터 — 부분집합이면 빠진 것들이 조용히 불가능해져 있다.**

### 3. "진단만" 스펙을 별도로 남기면 구현 착수가 싸진다
사용자가 처음엔 "진단만, 구현 나중"(199)을 골랐고 다음 날 "수정해봅시다"로 이어졌다. 진단이 스펙
파일로 남아 있어 구현 스펙(200)은 진단 요약+설계만으로 짧게, 착수는 즉시였다. 문제 정리와 해법
구현 사이에 사용자 결정 지점을 두는 이 분리는 "긴 답=실패"인 사용자와의 합의 리듬에도 맞았다.
**교훈: 사용자가 범위를 결정 못 한 개선 요구는 진단 스펙을 먼저 커밋해 결정 재료로 두고, 구현은
별도 스펙으로 — 진단이 자산으로 남아 다음 턴 착수 비용이 0에 가깝다.**
