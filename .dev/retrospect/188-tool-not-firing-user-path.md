# 회고 188 — "아무리 해도 발동 안 됨": 내 실증과 사용자 경로의 괴리 (스펙 201 후속2)

## 무엇을 했나
사용자가 위키 도구 발동 실패 보고 → 근인 두 겹 진단: (1) 능력 부여≠에이전트 배선인데 어떤 에이전트에도
web-fetch 미배선 — **내 실증은 매번 플그 오버라이드(임시 연결)로 성공**한 것, (2) 사용자가 배선해 본
plan-execute-demo는 도구를 안 쓰는 예제 플로우인데 폼이 배선을 수용(조용한 무시). 처방: research-assistant
영구 배선(편집=초안이라 활성화까지)+죽은 배선 원복+무오버라이드 재검증 2문항(둘 다 wiki 발동, mock 안 뺏김).

## 배운 것

### 1. "된다"의 실증은 사용자 기본 경로로 — 시연 편의 장치가 실증을 오염시킨다
web-fetch 시연에서 나는 오버라이드로 도구를 임시 연결해 "된다"고 보고했다. 하지만 오버라이드는 그
세션·그 화면 한정 — 사용자 기본 경로(에이전트 저장 설정)엔 배선이 0이었다. 사용자가 실패를 보고하고서야
괴리를 봤다. **교훈: 기능 실증에 임시 조치(오버라이드·수동 시드·직접 API)를 썼다면 그 실증은 "임시
조치 포함 경로"의 실증일 뿐이다 — 출하 판정은 사용자 기본 경로(저장 설정, 무보정)로 한 번 더.
[[probe-deeper-before-concluding]]의 사전 버전: 사용자 보고 전에 기본 경로를 내가 먼저 밟는다.**

### 2. 권리(능력 부여)와 배선(에이전트 설정)은 별개 축 — 사용자에겐 한 덩어리로 보인다
관리자가 능력을 부여하고 도구가 공개돼도, 에이전트 config.mcps에 연결이 없으면 아무 일도 안 일어난다.
가이드(스펙 189)의 "권한 세 층"이 이 구분을 문서로는 갖고 있지만, 실제 사용자 흐름(부여했으니 되겠지)
과는 멀다. **교훈: "쓸 수 있게 하기"가 다층(권한→배선→발동 조건)일 때, 마지막 층까지 이어지는 기본
경로 하나(예: 대표 에이전트에 기본 배선)를 만들어야 기능이 "존재"한다 — 층마다 옳아도 이어지지 않으면
사용자에겐 없는 기능.**

### 3. 편집=초안 저장, 활성화는 별도 — API 직접 갱신도 이 계약을 따른다
PUT /agents가 200을 줘도 반영이 안 됐다 — 편집은 draft 버전에 저장되고 activate까지 해야 유효(스펙
011 버저닝). UI는 이 흐름을 태우지만 API를 직접 칠 땐 잊기 쉽다. 회고 186의 "체크≠적용"과 같은 결 —
**저장형 시스템에서 쓰기 200은 "반영"이 아니라 "접수"일 수 있다. 갱신 후엔 반드시 읽기로 실효를 확인.**

## 다음에 적용
- 기능 실증에 임시 조치를 썼으면 출하 전 사용자 기본 경로(무보정)로 재실증(1).
- 다층 기능은 끝까지 이어진 기본 경로 1개 확보 후 "완료" 선언(2).
- 직접 API 갱신 후 읽기로 실효 확인(편집=초안 계약)(3).
