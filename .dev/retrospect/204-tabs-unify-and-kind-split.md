# 회고 204 — 탭 UI 통일 + RAG/평가 kind 분리 (스펙 212)

## 무엇을 했나
사용자 UI 배치 8·9·10번. 탭 패턴 기준 명문화(admin/CLAUDE.md): **데이터 집합 전환=Tabs / 같은 목록
필터=Segmented / Radio.Group 탭용도 금지**. 정렬: 승인 Segmented→Tabs(대기/처리=다른 집합)·세션
Radio→Segmented(상태 필터=같은 목록). RAG 컬렉션 문서/엔티티 Tabs(kind 클라 필터·생성 프리셀렉트·
배지 제거). 평가 문제집 에이전트/RAG Segmented(상위 Tabs 안이라 중첩 회피, 백엔드 kind 파라미터로
서버 필터=페이징 정합). 검증=브라우저 6/6·tsc0. fast-worker 2기 병렬(승인·세션·규칙 / RAG 탭).

## 배운 것

### 1. 같은 개념(kind 분리)도 맥락이 렌더 형태를 가른다 — 규칙은 형태가 아니라 역할에 걸어야
RAG는 상위 탭이 없어 kind를 **Tabs**로 깔끔히 얹었지만, 평가는 이미 상위 Tabs(문제집/격자/이력) 안이라
같은 kind 분리를 Tabs로 하면 "탭 속 탭"이 된다 → **Segmented 필터**로. 사용자는 둘 다 "탭으로"라
했지만, 통일 기준(항목 9)의 정신은 "형태 일치"가 아니라 "역할별 일관"이다: 평가 kind는 *같은 문제집
목록의 부분집합 선택*이라 Segmented가 규칙 부합. **교훈: "탭으로 나눠줘"를 컴포넌트가 아니라 역할로
번역한다(데이터 집합 전환이냐 목록 필터냐). 상위 컨테이너가 이미 Tabs면 하위 kind는 Segmented가 중첩을
피하며 규칙도 지킨다. 형태를 못박으면 맥락 다른 화면에서 규칙이 깨진다.**

### 2. 서버 페이징 목록의 필터는 클라 필터가 아니라 서버 파라미터로 — 페이징 정합
평가 문제집은 PagedListShell(서버 페이징)이라 kind를 클라에서 거르면 페이지·총계가 어긋난다. 백엔드
list_datasets에 `kind` 쿼리 파라미터를 더해 WHERE로 걸었다(총계·페이징 정합). RAG 컬렉션은 전량 클라
보유(listCollections 무페이징)라 클라 필터로 충분 — **자료 소스의 페이징 여부가 필터 위치를 정한다.**

### 3. 스크린샷 확정 체크포인트를 스펙에 미리 박아두면 판단 이탈을 사용자가 싸게 검수
스펙 212에 "평가 중첩은 스샷 확인 1회"를 미리 적어둬, Segmented로 이탈한 판단을 구현 후 스샷으로
바로 제시할 수 있었다. **교훈: 구현 중 판단이 갈릴 지점을 스펙 작성 시 "여기서 스샷 확인"으로 표시하면,
완료 후 되돌리기 대신 그 지점만 사용자가 검수한다(값싼 확정).**

## 다음에 적용
- UI 통일 요청은 컴포넌트가 아니라 역할로 번역 후 규칙 적용(중첩 컨테이너 고려).
- 서버 페이징 목록의 새 필터축은 서버 파라미터로(클라 필터는 무페이징 목록만).
- 판단 갈림 지점은 스펙에 "스샷 확인" 체크포인트로 선표시.
