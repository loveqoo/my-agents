# 회고 180 — 채점 기준 편집 UX: 문장형 인라인 폼 + lte 확장 (스펙 194)

## 무엇을 했나
실사용 문의: 평가 케이스의 채점 기준(assert) 편집이 어렵다 — (a) 유형마다 입력 UI가 달라 뭘 넣을지
모름, (b) 기준들이 AND인지 OR인지 안 보임. 채점은 실제로 전부 AND(`all(ok…)`). → **문장형 인라인
폼**(사용자 제안): 각 기준을 읽으면 그대로 자연어가 되게("검색 결과가 [3]건 [이상▾] 여야 통과"),
숫자 비교형은 연산자(이상/이하) select. **AND 배지 + "그리고" 커넥터**로 조건 관계 명시. 저장된 케이스
카드도 `assertLabel` 한 함수로 편집과 같은 문장 어휘 공유. "이하"가 실동작하도록 백엔드 `rag_hits_lte`·
`rag_score_lte` 확장. 단위 15/15·e2e 18/18·tsc 0·스샷 확인.

## 배운 것

### 1. UI에 반대 선택지("이하")를 노출하면 그 반대편도 실제 채점돼야 하고, 단순 반전이 아니다
연산자 select에 "이상/이하"를 넣는 순간, "이하"(lte)가 백엔드에 없으면 **select에 있는데 동작 안 하는
거짓 UI**가 된다(learning 119 "조용한 초록"의 UI판). 그래서 `rag_hits_lte`·`rag_score_lte`를 추가했는데,
여기 함정: **lte는 gte의 단순 `>=`→`<=` 반전이 아니다.** gte는 `len(hits) >= N`이라 agent 런(rag 관측
부재)이면 빈 리스트 `0 >= N`(N≥1)이 자연히 False(fail-closed). 그런데 lte는 `len([]) <= N`이 **항상
참** — 부재 관측을 통과로 위장한다. 그래서 lte만 **명시적 부재 체크**(`"hits" not in rag → False`)를
넣어 대칭을 맞췄다. score_lte도 `top_score is None → False`. 단위에서 "부재 → False"를 못박음.
**교훈: 비교 연산자에 반대 방향을 추가할 때 "부재/빈 관측"의 진리값을 각 방향마다 따로 확인한다 —
`>=`는 빈 값에 fail-closed지만 `<=`는 vacuously true라 fail-open이다. UI가 여는 선택지는 백엔드에서
같은 fail-closed 규율로 닫아야 정직하다.** ([[verification-ladder-three-rungs]]의 fail-closed 대칭판)

### 2. 사용자의 UI 제안이 내 첫 설계보다 나았다 — 내 안에 고착하지 않는다
나는 "유형별 안내 카드"(아이콘+설명+맞춤 위젯)를 제안했다. 사용자가 "RAG 결과 {number}개 {이상/이하}
문장형으로"를 제안했고, 그게 **읽으면 그대로 자연어**가 되는 더 나은 형태였다(카드는 여전히 "설명을
읽고 입력칸을 이해"해야 하지만, 문장형은 입력칸이 문장의 빈칸이라 이해 단계가 없다). 바로 채택하고 내
안을 접었다. **교훈: 사용자가 구체적 UI 형태를 제시하면 내 초안을 방어하지 말고 그 형태의 장점을 먼저
평가한다 — 사용자는 그 화면을 매일 쓸 사람이라 도메인 감각이 있다.** ([[explain-plainly-not-one-sided]])

### 3. 편집과 표시가 같은 어휘를 쓰려면 순수 함수 하나로 공유한다
저장된 카드가 `no_error` 원문을 노출한 건 편집 UI와 표시가 **다른 코드 경로**였기 때문. `assertLabel(a)`
순수 함수를 편집 폼·카드가 공유해 드리프트 0(회고 179의 `_dataset_out` 헬퍼와 동형 — "같은 값을 두 곳이
만들면 한쪽이 샌다"). **교훈: "편집한 것과 보이는 것이 다르다"류 불일치는 대개 두 경로가 같은 변환을
각자 구현해서다 — 변환을 순수 함수 하나로 뽑아 양쪽이 호출하게 한다.**
